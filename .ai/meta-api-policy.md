> Связано с: architecture.md §6 (CAPI — единственный серверный отправитель — Spring), §15.15 (ротация токенов, аудит),
> §15.20 (priority queue, two-contour rules), §16.3 (цепочка CAPI v2), vision §6.8 (pixel pollution), §12.1b, §19.4.

> **v1.2 (2026-10-21):** §6 — создание объявлений на паузе выделено в класс `CREATE_AD_PAUSED` (с GUARDED_WRITES); ручная заливка креативов больше не считается вариантом — см. `.ai/creative-publishing.md` и roadmap Phase 11.

## 1. Коротко

- **CAPI (Conversions API) — необходим и безопасен**, если отправляются только реальные события из CRM. Это и есть механизм, которым мы улучшаем аудиторию, которую даёт Meta.
- **Marketing API: чтение — всегда безопасно, запись — включаем постепенно** и в «человеческом» темпе.
- **Бан-риск живёт не в API**, а в контенте объявлений (инвестиционная тематика) и в качестве данных (выдуманные события, PII без согласия).

## 2. Почему CAPI нужен именно нам

| Причина | Что без CAPI | Что с CAPI |
|---|---|---|
| Ключевые события воронки (BOOKED, CALL_HELD, ACCRED_VERIFIED, FUNDS_RECEIVED) существуют только на сервере и в CRM | Meta оптимизирует на отправку формы — на «загрязняющих» лидов, от которых клиент уже пострадал | Meta оптимизирует на запись/состоявшийся звонок (`Schedule`, `CompleteRegistration`) |
| iOS, ATT, блокировщики режут 30–40 % браузерных событий | Пиксель видит неполную картину | Серверная отправка с общим `event_id` → дедупликация, события возвращаются без двойного счёта |
| Value-оптимизация (ценность по тикету × аккредитация) | Все лиды равны | Advantage+ ищет похожих на тех, кто дошёл до звонка и прошёл проверку, а не на тех, кто нажал кнопку |

## 3. Где у CAPI реальный риск (и как мы его закрываем)

| Риск | Последствие | Наша защита |
|---|---|---|
| Выдуманные / завышенные события (Purchase без денег, Schedule без записи) | Нарушение политики, проверка аккаунта | Каждое событие берётся из факта в CRM (GHL webhook / polling); `capi_event_map` только из подтверждённых стадий; Purchase один на лид и только по FUNDS_RECEIVED |
| PII без согласия или без хеширования | GDPR/CCPA, политика Meta | Уровни согласия (`consent_level`), SHA-256 для email/phone, Limited Data Use для Калифорнии, right to erasure |
| Низкое Event Match Quality | Не бан, но деньги на ветер | EMQ pre-check в онбординге, `external_id` после согласия, мониторинг EMQ с первого дня |
| Неаккредитованные лиды в инвестиционном пикселе | Загрязнение алгоритма | Маршрутизация по пикселям: `self_accredited = false` → только `future_regcf` |

**Правило, которое нельзя нарушать:** CAPI-событие отправляется только когда соответствующий факт записан в CRM/БД. Никаких «прогнозных» Purchase. Прогнозная ценность (`predicted_value`) допустима только как `value` у `Lead`/`Schedule`, не как факт события.

## 4. Marketing API: чтение и запись — разный риск

**Чтение** (инсайты, статусы, learning phase, `ad_review_feedback`) — безопасно всегда. Нужно для стоп-лоссов, якорных креативов, детектора обвала CVR, probe-модерации.

**Запись** (пауза, бюджет, запуск, создание объявлений) — Meta не запрещает, это делают все агентские инструменты. Аккаунты отключают за:
- политику контента (для нас — главный фактор, см. §5);
- платёжные проблемы;
- подозрительную активность: массовое создание объявлений, частые переключения статусов, десятки ad accounts из одного приложения, изменения во время learning phase.

## 5. Инвестиционная реклама — главный источник бан-риска

Обещания доходности, конкретные цифры без оговорок, обращение к личным атрибутам («ты аккредитованный инвестор?») блокируют и объявление, и аккаунт. Поэтому:
- compliance-проверка до запуска (META_FINANCIAL, META_PERSONAL_ATTR, SEC_506C, CLIENT_LEGAL) — обязательный шаг, аппрув заблокирован без PASS или явного override с причиной;
- генерация контента только из одобренных фраз (`approved_phrases`);
- probe-модерация: новый батч создаётся на паузе, вердикт Meta читается до включения;
- reviewer-persona META_REVIEWER — совет, не блокировка, но её прогноз сверяется с фактом модерации.

## 6. План включения по этапам

| Этап | CAPI | Marketing API | Страховка |
|---|---|---|---|
| **Месяц 1** | Включён: `Lead(value)` → `Schedule` → `CompleteRegistration` → `Purchase`; `AccreditationVerified` как custom event для аудиторий | Только чтение | Automated Rules и Account Spending Limit в самом Meta (настраивает клиент при онбординге); паузы и бюджеты вручную в Ads Manager |
| **Месяц 2+** | То же + value-оптимизация на `Schedule` после калибровки k_ticket | Запись по порогам: пауза при стоп-лоссе (L1/L3), бюджет ±20 %; только после прохождения OPE-gate (SEMI_AUTOPILOT) | Не трогать ad set в learning phase; не более нескольких изменений в час на аккаунт; каждая запись — в `meta_api_audit` |
| **Месяц 2+ (дополнение v1.2)** | То же | **Создание объявления на паузе** — отдельный класс записи `CREATE_AD_PAUSED`, разрешён с GUARDED_WRITES: ничего не тратит и не включает; включение — `RESUME` из кабинета после вердикта probe-модерации | Креатив попадает в Meta **только через платформу** (`.ai/creative-publishing.md`); объявление, созданное руками, — «неуправляемое», вне обучения и пар |
| **Позже** | Переход оптимизации на `CompleteRegistration` при ≥ 50/нед | AUTOPILOT — после повторного OPE PASS | ~~Если клиент нервничает — креативы заливаются руками, система остаётся «мозгом», а не «рукой»~~ **v1.2:** ручная заливка не вариант — теряется связка «креатив → лендинг → путь»; если клиент не даёт запись, платформа сверяет объявления по чтению и привязывает их вручную в кабинете (roadmap 11-4), но такие объявления помечены как неуправляемые |

Уровни автономии в платформе уже соответствуют этим этапам: OBSERVER → ADVISOR (по умолчанию) → SEMI_AUTOPILOT → AUTOPILOT; переход выше ADVISOR — только через OPE PASS ≤ 7 дней (`PUT /tenants/me/autonomy`), истёкший токен автоматически роняет уровень в OBSERVER.

## 6a. Как это закреплено в коде (roadmap 9-19)

Правила §6 — не регламент, а политика, которую проверяет одна точка кода перед любой записью в Meta:

| Элемент | Где |
|---|---|
| Стадия клиента `READ_ONLY → GUARDED_WRITES → FULL` | `tenants.meta_write_stage` (V133); меняется через `PUT /tenants/me/meta-write/stage` |
| Условия перехода (про данные, не про даты) | `MetaWriteStageService`: → GUARDED: токен OK, ≥ 50 отправленных CAPI-событий за ≥ 14 дней, EMQ pre-check PASS, клиент подтвердил Automated Rules + Spending Limit; → FULL: ≥ 14 дней в GUARDED, OPE PASS ≤ 7 дней, автономия ≥ SEMI_AUTOPILOT, ни одного отказа за 7 дней. Понижение — всегда; принудительный переход — только с причиной, в журнал |
| Классы записей | `MetaWriteAction`: PAUSE (защитная — никогда не блокируется), RESUME, BUDGET_CHANGE, LAUNCH, CREATE_AD_SET, CREATE_CAMPAIGN, AUDIENCE_UPDATE, **CREATE_AD_PAUSED** (v1.2, roadmap 11-3: создание объявления на паузе, разрешено с GUARDED_WRITES; `MetaWriteGuardTest` проверяет и загрузку видео/изображения, создание креатива и объявления, смену статуса объявления) |
| Таблица решений | `MetaWritePolicy` (чистая логика, `MetaWritePolicyTest`): стадия → автономия для джоб (SEMI_AUTOPILOT / AUTOPILOT) → learning-phase lock → бюджет ≤ 20 % за шаг и ≥ 24 ч между шагами → ≤ 10 записей в час. Превышение порога = RECOMMEND (запись в `autopilot_actions` для человека, HTTP 409), нарушение стадии = DENY (403) |
| Единая точка | `MetaWriteGate.assertAllowed` перед каждым из 9 вызовов `MetaApiService`, в `MetaApiClient.enqueue` и `AutonomyService.checkAndExecute`; `MetaWriteGuardTest` сканирует исходники — новый путь записи без gate валит сборку |
| Override | `POST /tenants/me/meta-write/overrides`: одноразовый, ≤ 4 ч, причина ≥ 10 символов, обязательно в журнале; не обходит learning-phase lock для бюджета |
| Журнал | `meta_write_decisions` — каждое решение (ALLOW / DENY / RECOMMEND) с инициатором (USER / JOB), стадией и причиной; админ-страница `/meta-write` |

| Линковка креативов (v1.2, roadmap 11-4) | `LinkageHealthService`: активное объявление без карты или без `mai_c` в url_tags, либо расхождение (DRIFT) → `LAUNCH` запрещён, пункт `linkage` в онбординг-чеклисте красный; `MetaAdReconcileScheduler` раз в час читает объявления аккаунта |

## 7. Инфраструктурный чек-лист

- Приложение Meta создаётся в Business Manager **клиента**, токен — System User с минимальными scope (`ads_management`, `ads_read`, `business_management`); scope фиксируются в `tenants.oauth_scopes`.
- Домен лендинга верифицирован в BM; Aggregated Event Measurement настроен (приоритет событий: `Schedule` выше `Lead`).
- Перед боевой отправкой — Test Events в Events Manager; проверить дедупликацию пиксель/CAPI по `event_id`.
- Токены: хранятся запечатанными (`ENCRYPTION_KEY`), ротация на 50-й день, INVALID на 58-й (пауза записей, алерт).
- Rate limits: все вызовы через priority queue (P0 — circuit breaker, P1 — обычные, P2 — фон); никаких прямых вызовов мимо `MetaApiClient`.
- Каждый вызов Marketing API и CAPI — строка в `meta_api_audit` (append-only).

## 8. Чего мы не делаем

- Не отправляем в CAPI события, которых не было (и не «докручиваем» ценность задним числом без факта).
- Не создаём аудитории из неаккредитованного сегмента до снятия заморозки OI-3.
- Не запускаем и не редактируем объявления через API без человека, пока уровень автономии ниже SEMI_AUTOPILOT.
- Не используем sGTM параллельно со Spring — один серверный отправитель, иначе двойной счёт событий.
