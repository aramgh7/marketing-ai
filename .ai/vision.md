## 1. Миссия

Замкнутая ИИ-система, которая управляет полным циклом performance-маркетинга:
**генерация креативов → тестирование → анализ причин → самообучение → персонализация воронки** —
с единственной целью: **максимальный ROI** (не CTR, не число лидов, а маржинальная прибыль / предсказанный LTV).

Первый канал: **Meta (Facebook / Instagram)**. Архитектура с первого дня заточена на добавление других каналов.

## 3. Целевая метрика и иерархия метрик

### 3.1. Главная метрика — маржинальная прибыль / предсказанный LTV

**НЕ CTR, НЕ CPL, НЕ первая покупка.** Система оптимизирует:

```
North Star (мониторинг) = Σ (Revenue × Margin − Ad Spend) / Ad Spend
```

**Важно: ROI vs прибыль в разных контекстах.** North Star как **мониторинговая метрика** — нормально. Но как **reward для Thompson Sampling** ROI (отношение) толкает к недорасходу (максимальный ROI при минимальном бюджете). Поэтому:
- **Reward для TS в тестовом контуре**: profit per impression при равной экспозиции (прибыль на показ)
- **Для масштабирования**: максимум абсолютной прибыли при условии, что marginal ROAS ≥ порога (кривая из §8.4)
- Это определяет, **когда система останавливает масштабирование**: когда следующий доллар приносит меньше порога

С защитными метриками:
- Возвраты / отказы (protection against кликбейт)
- Качество лидов (если B2B / high-ticket — обратная связь от продаж)
- Quality Score креатива (внутренний, см. раздел 12.2)
- Частота показов (protection against выгорания)

### 3.2. Диагностическая карта метрик по этапу воронки

Каждая метрика привязана к этапу и указывает на конкретный "атом" для оптимизации:

| Симптом | Диагноз | Действие системы |
|---------|---------|------------------|
| Низкий Hook Rate (3-сек просмотры / показы) | Хук не цепляет | Перегенерировать хук, оставить тело |
| Хороший hook, падение досмотра | Тело ролика не оправдывает обещание хука | Перемонтировать середину |
| Досматривают, но CTR низкий | Слабый CTA или оффер неубедителен | Тестировать CTA и оффер |
| CTR хороший, но Landing Page Views << Clicks | Медленная загрузка или потеря трекинга | Проверить PageSpeed + пиксель |
| Лендинг открыли, высокий bounce, нет скролла | Message mismatch: обещание ≠ реальность | Синхронизировать заголовок лендинга с хуком |
| Скроллят, но не конвертируются | Проблема в оффере, цене или доверии | Heatmap + анализ блоков (отзывы, гарантии, цена) |
| Форму начали, но бросили | Трение в форме (поля, шаги) | Разбор по полям, упрощение |
| Конверсия ОК, но возвраты / плохие лиды | Креатив обещает лишнее (кликбейт) | Снизить Quality Score, штрафовать в графе |
| Всё падает одновременно | Внешний фактор (CPM spike, конкурент, сезон) | Модуль внешних сигналов (см. раздел 11) |

**Принципы диагностики:**
- Сравнивать с **собственным базовым уровнем** по плейсменту, устройству, аудитории (риск парадокса Симпсона)
- Промежуточные метрики — **индикаторы**, не цель: связь «метрика → ROI» обучается отдельно для каждой ниши
- Выводы — только после **минимального объёма данных**, с поправкой на множественные сравнения
- Генерируемые лендинги **сразу содержат событийную разметку блоков** (каждый блок — свой ID + event)

## 4. Creative DNA — декомпозиция креативов на атомы

### 4.1. Зачем

Анализировать не "видео A лучше видео B", а **почему**: какие конкретные элементы работают для конкретной аудитории. Это общий язык между генерацией, анализом и графом решений.

### 4.2. Атомы видео

| Атом | Примеры значений | Как извлекается |
|------|-------------------|-----------------|
| Hook (первые 3 сек) | Вопрос, шок, социальное доказательство, прямое обращение | Vision LLM + классификатор |
| Структура | Hook→Problem→Solution→Proof→CTA, Testimonial, Demo | LLM по транскрипту |
| Темп монтажа | Быстрый (< 2 сек/сцена), средний, медленный | Автоматический scene detection |
| Наличие лица | Да/нет, говорящая голова, B-roll | Vision model |
| Субтитры/текст | Есть/нет, стиль, размер | OCR + Vision |
| Эмоциональный тон | Срочность, спокойствие, юмор, авторитетность | LLM-классификация |
| Тип доказательства | Отзыв, статистика, демонстрация, авторитет | LLM |
| Музыка/звук | Тип, темп, громкость | Audio analysis |
| Длительность | 15s, 30s, 60s+ | Метаданные |
| CTA | Текст, визуал, позиция | Vision + OCR |
| Production style | Studio, UGC polished, UGC raw, screen recording | Vision LLM-классификация |

### 4.3. Атомы лендинга

| Атом | Примеры значений |
|------|-------------------|
| Headline-формула | Benefit-first, problem-agitate, question, social proof |
| Структура блоков | [Hero → Problem → Solution → Proof → Pricing → CTA] |
| Тип социального доказательства | Отзывы, логотипы, числа, case study |
| Позиция CTA | Above fold, after proof, sticky, multiple |
| Цветовая схема | Тёплая, холодная, контрастная |

| Наличие видео на странице | Да/нет, автоплей, тип |
| Тип оффера | Скидка, бесплатный пробный, гарантия, бонус, рассрочка |
| Urgency-элементы | Таймер, ограниченное количество, нет |

#### 4.3a. Суб-атомы оффера (Dynamic Offer Explorer)

«Тип оффера» из таблицы выше — один категориальный признак. На практике оффер = комбинация из **шести независимых измерений**, каждое из которых влияет на конверсию по-разному для разных аудиторий:

| Суб-атом | Примеры значений | Что тестируется |
|----------|------------------|-----------------|
| Тип скидки | Процент, фиксированная сумма, бесплатная доставка, подарок, нет | Психология восприятия ("−20%" vs "−$40" — одно и то же, эффект разный) |
| Глубина скидки | 5%, 10%, 20%, 30%+ | Баланс CVR ↔ маржинальная прибыль |
| Тип гарантии | Money-back 14/30 дней, пожизненная, без гарантии | Снятие возражения "а если не подойдёт" |
| Бонус | Дополнительный продукт, контент, консультация, нет | Perceived value без скидки |
| Urgency-механика | **Только реальные**: дедлайн из инвентарной системы, реальные остатки, сезонное окно. **Нет**: фейковые таймеры, ложная ограниченность | Ускорение решения (vs раздражение) |
| Условия оплаты | Полная, рассрочка 3/6/12 мес, trial, freemium | Снижение барьера входа |

**⚠️ Urgency: только реальная срочность.** Фейковые таймеры и ложное "осталось 3 штуки" = dark patterns. EU Digital Services Act и US FTC квалифицируют их как обманные практики. Система **не генерирует и не тестирует** искусственную срочность — только реальные дедлайны и остатки из инвентарной системы клиента.

**⚠️ Рассрочка**: в ряде юрисдикций (ЕС, UK) подпадает под правила потребительского кредита. Если клиент предлагает рассрочку — вопрос юристу до включения в тестирование.

**Иерархическое кодирование суб-атомов**: суб-атомы **вложенные**, не независимые. "Глубина скидки" не имеет смысла при "тип скидки = нет". Кодирование в модели:
- Если `discount_type = "нет"` → `discount_depth` автоматически = 0 (не участвует)
- Если `guarantee_type = "нет"` → срок гарантии = N/A
- Невалидные комбинации исключаются до попадания в Thompson Sampling

**В модели (§15.3)** вместо одного `offer_type` используются суб-атомы с иерархическим кодированием. Аддитивная модель + shrinkage (§15.4) справляется — эффект каждого суб-атома оценивается с partial pooling. Невалидные комбинации отсечены на уровне генерации кандидатов.

Пример кодирования одного оффера в вектор признаков модели:
```
Оффер: "−20%, money-back 30 дней, бесплатная консультация, дедлайн из CRM"
→ discount_type    = one-hot [0, 1, 0, 0, 0]  (percent)
  discount_depth   = 0.20                       (нормализовано, валидно: discount_type ≠ "нет")
  guarantee_type   = one-hot [0, 1, 0, 0]       (money-back)
  guarantee_days   = 30 / 365                   (нормализовано, валидно: guarantee ≠ "нет")
  bonus            = one-hot [0, 0, 1, 0]       (консультация)
  urgency          = binary 1                   (реальный дедлайн)
  urgency_days_left = 7 / 30                    (нормализовано)
  payment_terms    = one-hot [1, 0, 0, 0]       (полная оплата)
```
Маска валидности: `discount_depth` и `guarantee_days` автоматически обнуляются, если родительский суб-атом = "нет".

**⚠️ Жёсткое ограничение — защита от эрозии маржи**: система **не должна** бесконечно увеличивать глубину скидки ради роста CVR, если это нарушает юнит-экономику. Constraint в модели: reward = profit per impression (§3.1) уже штрафует за глубокие скидки (маржа падает). Дополнительно — **жёсткий floor**: маржинальная прибыль варианта ≥ минимума, заданного маркетологом. Варианты ниже floor не участвуют в Thompson Sampling.

**⚠️ Тестирование офферов на уровне креатива ≠ чистый эксперимент.** Если оффер указан в самом видео/баннере (Message Match, §5.3), Meta покажет креативы с разными офферами **разным** сегментам аудитории (auction bias). Вы сравниваете не "оффер A vs оффер B на одной аудитории", а "оффер A на аудитории, которую Meta подобрала под A, vs оффер B на аудитории под B". **Решение**: тестировать офферы **на лендинге** (наш контроль, рандомизация на сайте) при одинаковом креативе. Варьировать оффер на креативе — только после подтверждения на лендинге.

**Связь с §18 (Message-Market Fit)**: когда §18.2 диагностирует "проблема в оффере, не в креативе" → Dynamic Offer Explorer генерирует альтернативные комбинации суб-атомов и предлагает маркетологу набор для тестирования (см. §18.5).

**Тестирование базовой цены (scope note):** если клиент предоставляет **допустимый диапазон цен**, система может тестировать цену как суб-атом оффера через существующий механизм Dynamic Offer Explorer. Однако full price elasticity modeling (кривые спроса по сегментам, динамическое ценообразование в реальном времени) — **за scope рекламной платформы**: (а) price discrimination регулируется EU Consumer Rights Directive и Robinson-Patman Act; (б) для B2B цена = предмет переговоров, не лендинга; (в) это отдельный продукт с собственной экспертизой. Платформа оптимизирует рекламу и конверсию, не ценообразование клиента.

### 4.4. Ключевой принцип

Новые креативы генерируются **рекомбинацией лучших атомов**, а не копированием целых "победителей". Хук из видео A + темп из C + CTA из D = новый креатив с предсказуемо высокой вероятностью успеха.

## 5. Генерация креативов

### 5.1. Лендинги — конструктор, не свободная генерация

- Библиотека **модульных блоков** с текстовыми слотами (hero, problem, solution, proof, pricing, CTA, FAQ)
- LLM заполняет слоты на основе: исходных данных продукта, целевой аудитории, лучших атомов из графа
- Варианты **сравнимы между собой** (одинаковая структура, разный контент → чистый тест)
- Каждый блок имеет уникальный **event ID** для гранулярной аналитики
- **Message Match**: заголовок лендинга генерируется в паре с хуком видео (не раздельно)

### 5.2. Видео — шаблонный монтаж с вариациями

**MVP-подход (реалистичный):**
1. Пользователь загружает исходные видеоролики (футажи)
2. Whisper транскрибирует, Vision LLM тегирует сцены
3. LLM-«режиссёр» составляет монтажный план по шаблону: `Hook → Problem → Solution → Proof → CTA`
4. Подбирает сцены из футажей по тегам и транскрипту
5. Рендер через FFmpeg / Remotion, форматы 9:16, 4:5, 1:1
6. **Главный рычаг**: много вариантов хука на одном теле ролика (3 хука × 1 тело × 3 CTA = 9 креативов)
7. **Low-hanging fruit**: субтитры, текстовые оверлеи, цветокоррекция — одно видео + 5 вариантов overlay = 5 "разных" креативов с минимальными затратами

**Два потока генерации (критически важно):**
- **Поток вариаций**: хук × тело × CTA на одном фреймворке — тестирует отдельные атомы
- **Поток концепций**: принципиально разные идеи (другой угол, другая эмоция, другой формат) — обеспечивает разнообразие, без которого система застрянет в локальном оптимуме

**Ограничения (честные):**
- Meta НЕ отклоняет за "плохой монтаж" — отклонение идёт за нарушения политики и техтребования. Слабый ролик просто хуже доставляется алгоритмом
- **Нативный UGC-стиль часто работает лучше "профессионального"**. Критерий — "нативность", не "гладкость"
- Для первого цикла: **шаблоны с заменяемыми блоками**, не свободная генерация
- Человек (маркетолог/креативщик) утверждает финальный вариант перед запуском

**Phase 5+ — AI Avatars & Text-to-Video (генеративное видео):**

Когда модель определяет высокопотенциальную комбинацию атомов (§15.3), но готового футажа нет, система может сгенерировать базовый ролик через API генеративных видеоплатформ (HeyGen, Synthesia, Runway и др.):
- LLM формирует скрипт из Creator Brief (§5.5)
- API генерирует видео с AI-аватаром или text-to-video
- FFmpeg/Remotion рендерит финальный ролик с оверлеями
- Маркетолог обязательно апрувит перед запуском

**⚠️ Ограничения (Phase 5+, не раньше):**
- **Audience acceptance varies by niche**: в B2B industrial (гидрогели, химия) аудитория (инженеры, закупщики) скептична к AI-видео — обязателен A/B тест audience acceptance перед deployment
- **Uncanny valley**: текущее качество AI-аватаров может вредить доверию к бренду
- **Meta AI content policy** (§25 п.11): AI-generated контент разрешён с маркировкой, но enforcement ужесточается
- Использовать только после подтверждённого спроса от клиентов и положительного A/B теста

**Voice-as-Atom (синтетическая озвучка):** в рамках того же генеративного стека — голос становится тестируемым атомом наравне с текстом хука. Интонация (удивление, авторитетность, срочность), темп речи, тембр — параметры, которые система варьирует и оценивает через Thompson Sampling. Мультиязычная озвучка без повторных съёмок. ⚠️ Дополнительные юридические ограничения: EU AI Act классифицирует voice cloning как high-risk AI (требуется disclosure); FTC deepfake rules; Meta может ужесточить политику по синтетическому аудио. Voice cloning только с письменного согласия владельца голоса.

### 5.3. Генерация пар, а не единиц

Всегда генерировать **креатив + лендинг как пару** с единым сообщением. Обещание в видео == заголовок лендинга == оффер. Рассогласование убивает конверсию.

### 5.4. Техническая архитектура сборки лендингов

#### 5.4.1. Три процесса (критически важно не путать)

**Процесс 1 — Создание лендингов (офлайн, с апрувом маркетолога):**

```
LLM генерирует варианты контента (текст блоков, заголовки, офферы)
  → варианты попадают в админ-панель
    → маркетолог просматривает, правит, утверждает
      → утверждённый вариант сохраняется в БД со статусом "active"
```

Ни один лендинг не уходит в продакшен без апрува (см. §12.4 — уровень "Советник"). LLM — черновик, маркетолог — редактор, Thompson Sampling — дистрибьютор.

**Процесс 2 — Выбор лендинга для посетителя (реалтайм, автоматический):**

```
Посетитель кликает рекламу
  → Thompson Sampling выбирает один из ЗАРАНЕЕ УТВЕРЖДЁННЫХ вариантов
    → Next.js SSR рендерит его
```

Никакой генерации в реальном времени. Система распределяет трафик между готовыми, утверждёнными вариантами — как A/B тест.

**Процесс 3 — Персонализация порядка блоков (Phase 5, в рамках утверждённого):**

```
Посетитель скроллит к цене → система определяет "ищет цену"
  → переставляет блоки: прайсинг наверх, отзывы вниз
```

Переставляются **только утверждённые блоки**. Система не генерирует новый текст — меняет **порядок** готовых блоков. Маркетолог заранее утверждает набор блоков и допустимые правила перестановки.

#### 5.4.2. Общая схема

```
Посетитель кликает рекламу (?creative_id=video-7)
  → Edge Middleware (Next.js / Vercel Edge) перехватывает запрос
    → вызывает Thompson Sampling API (FastAPI + Redis, ~5-15ms)
      → API возвращает: variant_id + block_order
        → Next.js SSR рендерит страницу из React-компонентов
          → блоки и контент берутся из PostgreSQL (JSON)
```

#### 5.4.3. Хранение блоков — два уровня

**Шаблоны блоков** = React-компоненты в коде:

`<HeroBlock>`, `<ProblemBlock>`, `<ProofBlock>`, `<PricingBlock>`, `<CTABlock>`, `<FAQBlock>`

Каждый компонент автоматически рендерит `data-block-id={eventId}` — аналитика из коробки (см. §3.2).

**Контент блоков** = JSON-записи в PostgreSQL:

```json
{
  "id": "variant-42",
  "creative_id": "video-7",
  "status": "active",
  "blocks": [
    {"type": "hero", "headline": "...", "subhead": "...", "event_id": "blk_001"},
    {"type": "proof", "testimonials": [...], "event_id": "blk_002"},
    {"type": "pricing", "plans": [...], "event_id": "blk_003"}
  ],
  "block_order": ["hero", "proof", "pricing", "cta"]
}
```

**Деплой нового варианта** = новая запись в БД. Не нужен редеплой приложения. LLM сгенерировал → маркетолог утвердил → статус "active" → Thompson начинает направлять трафик.

#### 5.4.4. Почему НЕ Headless CMS (Strapi / Sanity / Contentful)

Контент генерирует LLM, вариант выбирает Thompson Sampling. CMS — редакторский инструмент для людей, здесь он добавляет лишний слой между генератором и рендером. Для ручной правки маркетологом достаточно простой admin-панели в самом Next.js.

#### 5.4.5. PageSpeed

- Edge middleware + SSR = первый байт за **50-100ms**
- Блоки — лёгкие React-компоненты, не SPA с тяжёлым бандлом
- Статика (изображения, стили) — CDN
- ISR для «холодных» вариантов, SSR для персонализированных

#### 5.4.6. Стек для лендингов

| Компонент | Технология | Назначение |
|-----------|-----------|-----------|
| Рендер блоков | **Next.js** (SSR) | React-компоненты с event ID |
| Выбор варианта | **Edge Middleware** (Next.js / Vercel) | Перехват запроса, маршрутизация к варианту |
| Thompson Sampling | **FastAPI + Redis** (см. §15.10) | Выбор варианта по апостериорам |
| Хранение контента | **PostgreSQL** | JSON-записи утверждённых вариантов |
| Аналитика блоков | Event ID на каждом блоке | Сбор в Phase 0 пайплайн |
| Персонализация внутри сессии | React state (клиентский JS) | Перестановка блоков без перезагрузки (Phase 5) |
| Admin-панель | Next.js | Просмотр, правка и апрув вариантов маркетологом |

### 5.5. Creator Brief Generator — data-driven ТЗ для контент-мейкеров

#### 5.5.1. Проблема

§5.2 описывает LLM-«режиссёра», который монтирует **уже загруженные** футажи. Но кто-то должен их **снять**. Система накапливает знания ("хук-вопрос + лицо крупным планом + быстрый темп = hook rate 12% для мам 25-35"), но эти знания остаются внутри модели. Контент-мейкер получает текстовое сообщение "сними что-нибудь про продукт" — и это gap между ИИ-знаниями и человеческим производством.

#### 5.5.2. Решение — структурированный бриф из апостериоров модели

```
Входные данные:
├── Апостериоры модели (§15.3) → лучшие атомы для целевой аудитории
├── «Кладбище» провалов (§13) → что НЕ делать (антипаттерны с пост-мортемами)
├── Ad Library + прошлые успешные ролики клиента (§9.1) → визуальные референсы
└── Суб-атомы оффера (§4.3a) → какой оффер должен быть в CTA

LLM генерирует структурированный бриф:
├── Формат: 9:16, 30 сек
├── Хук (0-3 сек): тип "вопрос" — "Вы тоже устали от...?"
│   говорящая голова, крупный план, прямой взгляд в камеру
├── Середина (3-20 сек): демо продукта, 3 сцены по 4 сек, быстрый темп
│   эмоциональный тон: тёплый, UGC-стиль (не "студийный")
├── Доказательство: отзыв клиента или демонстрация результата
├── CTA (25-30 сек): "Попробуйте бесплатно" — текст overlay + голос
├── ❌ НЕ ДЕЛАТЬ: [из кладбища] шоковые хуки с таймерами — кликбейт-сигнатура
│   (данные: CTR +40%, но CVR −60%, ROAS отрицательный)
├── 📎 РЕФЕРЕНСЫ:
│   • [из Ad Library] Конкурент X: ролик крутится 6+ недель (proxy на прибыльность),
│     формат 9:16, говорящая голова, похожий стиль хука
│     ⚠️ Ad Library НЕ даёт CTR/hook rate/конверсии — только креатив и срок жизни
│   • [из архива клиента] Собственный ролик #12: лучший за квартал, hook rate 11.2%,
│     тот же формат (наши данные, не Ad Library)
└── 📊 БЕНЧМАРК: hook rate ~10-12%, CTR ~1.2-1.5% (по данным НАШЕЙ модели для этой аудитории)
```

#### 5.5.3. Ключевые принципы

- **Data-driven, не generic**: каждый элемент брифа подкреплён статистикой из модели, а не "лучшими практиками из интернета"
- **Визуальные референсы**: автоматический подбор из Ad Library (§9.1) и прошлых успешных роликов клиента — контент-мейкер видит не только текст, но и желаемый темп и подачу
- **Антипаттерны из кладбища (§13)**: бриф явно указывает, чего избегать, с данными почему
- **Версионирование**: бриф привязывается к результату финального ролика → система учится, какие формулировки в брифе приводят к хорошим роликам
- **Парный бриф**: видео-бриф генерируется вместе с лендинг-брифом (§5.3 — message match)
- **Free Concept слот**: каждый бриф содержит раздел "Свободная идея" — контент-мейкер может предложить собственную концепцию вне рамок брифа. Система трекает результаты свободных концепций отдельно. Причина: (а) prescriptive-only бриф убивает креативность, (б) лучшие идеи часто приходят от людей, а не от модели, (в) это дополнительный exploration канал (§6.4)
- **Creator random effect**: в модели (§15.3) добавляется random effect по контент-мейкеру — одни и те же инструкции дают разный результат у разных создателей. Это позволяет системе учитывать "талант" без наказания за формальные отклонения от брифа

#### 5.5.4. Фазирование

| Фаза | Что доступно |
|------|-------------|
| Phase 1 (скелет) | Шаблонный бриф: маркетолог заполняет вручную на основе описательной аналитики (§23 Phase 1) |
| Phase 3-4 (полный) | Data-driven бриф из апостериоров модели + кладбище + Ad Library + бенчмарки |
| Phase 5+ | Бриф адаптируется под сегмент аудитории; отдельные брифы для разных аудиторий одного клиента |
| Phase 6+ | **Autonomous Creator Marketplace Seeding**: API-интеграция с Creator Marketplaces (TikTok Creator Marketplace, Instagram Creator APIs) для автоматической рассылки data-driven брифов подходящим микро-инфлюенсерам. Готовые ролики проходят авто-проверку (Face Detection §12.1a + Creative DNA §4.2) → тестовый контур (§6.5). ⚠️ Зависит от зрелости Creator APIs (TikTok API — approval-gated, Instagram — не поддерживает автоматическую рассылку на 2026). Юридические контракты с creators нельзя автоматизировать. Для B2B ниш UGC от инфлюенсеров менее релевантен. Скелет интеграции проектируется при планировании Phase 6 |

## 6. Граф решений и Thompson Sampling

### 6.1. Базовая реализация из Sales-ai (что есть)

В проекте Sales-ai реализовано:
- **Граф разговора**: узлы = состояния, рёбра = варианты
- **DgEdge**: weight (0.01–0.99), successes, failures, totalTraversals
- **Маршрутизация**: взвешенный случайный выбор по нормализованным весам (EMA)
- **Thompson Sampler**: Beta(α=successes+1, β=failures+1), метод Марсальи-Цанга, написан но НЕ управляет маршрутизацией
- **Затухание**: ежедневный сдвиг весов на 1% к 0.5
- **Режимы**: TRAINING (α=0.30, быстрое обучение) и PRODUCTION (α=0.10, стабильность)

### 6.2. Критика текущей реализации для нового контекста

| Проблема | Почему критично | Решение |
|----------|-----------------|---------|
| EMA не знает объём данных | Ребро с 3 наблюдениями выглядит как с 3000 | Переключить маршрутизацию на настоящий Thompson Sampling |
| Сигнал оценка/5 не опускается ниже 0.2 | Слабое ребро получает ~18% трафика (0.2/(0.2+0.9)) — в рекламе это деньги | Thompson с β-распределением решает это естественно |
| Затухание сдвигает вес к 0.5 | Не учитывает неопределённость | Затухать **счётчики α и β** (×0.99/сут): старый опыт теряет вес, неопределённость растёт |
| Обратная связь от людей (оценки 1-5) | В маркетинге — числовые метрики | Hurdle-модель: Binomial(конверсия) × Lognormal(чек) — см. §6.3a |
| Оценка приходит сразу | В маркетинге — часы/дни задержки | Промежуточные сигналы как временная награда с пересчётом по финалу |
| Одна оценка = одно ребро | В воронке покупка одна на несколько рёбер | Credit assignment: Markov attribution / Shapley values |
| Веса глобальны | Нужно "для ЭТОЙ аудитории" | Иерархический/контекстный бандит: сегмент подтягивается к общему, пока своих данных мало |

### 6.3. Архитектура графа для маркетинга

```
Узел = состояние пользователя в воронке:
  [Ad Impression] → [Ad Click] → [Landing Page] → [Engagement] → [Lead/Cart] → [Purchase]

Ребро = решение системы:
  Какое видео показать? Какой лендинг? Какой блок выделить? Какой оффер? Какой follow-up?

Контекст = аудитория + поведение:
  Сегмент Meta, устройство, время суток, поведенческий профиль (если есть данные сессии)
```

**Иерархия графа:**
```
Уровень 1: Аудитория → Какой месседж?
Уровень 2: Месседж → Какой креатив (хук × тело × CTA)?
Уровень 3: Креатив → Какой лендинг (headline × блоки × оффер)?
Уровень 4: Лендинг → Персонализация в реальном времени (порядок блоков, оффер)
```

**Важно**: четыре "независимых бандита" по уровням были бы нестационарны друг для друга (выбор на уровне 2 меняет распределение награды на уровне 3). Поэтому используется **единая модель** (см. 6.3a ниже).

### 6.3a. Единая модель: аддитивная → Томпсон → граф

В документе описаны три механизма — аддитивная байесовская модель (§14), Thompson Sampling (§6), граф решений (§6.2). Вот как они связаны:

```
┌─────────────────────────────────────────────────┐
│  ГРАФ — задаёт СТРУКТУРУ                        │
│  Какие решения доступны на каком шаге воронки    │
│  (узлы = этапы, рёбра = варианты)               │
│                     ↕                            │
│  BAYESIAN GLM — оценивает ЭФФЕКТЫ               │
│  По этапам воронки (logit link + Binomial):      │
│  • Атомы видео → влияют на CTR (hook rate       │
│    как диагностика, не в chain)                  │
│  • Атомы лендинга → влияют на CVR               │
│  • На стыке: явный признак match_score           │
│  • Hurdle: Binomial(конверсия) × Lognormal(чек) │
│                     ↕                            │
│  THOMPSON SAMPLING — ВЫБИРАЕТ из апостериора    │
│  Сэмплирует из распределения модели             │
│  → выбранный вариант идёт в тест/показ          │
└─────────────────────────────────────────────────┘
```

**Почему hurdle-модель, а не Normal-Gamma**: награда в рекламе почти всегда нулевая (показ без покупки) с редкими покупками на разные суммы. Binomial для факта покупки + Lognormal для чека моделирует это точнее. Конверсии — бинарные исходы, поэтому logit link + Binomial likelihood (не log + Gaussian), что корректно работает при малых n и нулевых конверсиях.

**Мультипликативная цепочка**: Revenue per impression = CTR × CVR × AOV. На лог-шкале это сумма: log(Revenue) = log(CTR) + log(CVR) + log(AOV). Аддитивность на логах = мультипликативность в оригинале. Hook rate — диагностика и предиктор CTR, не отдельный этап в произведении. Message match — это **взаимодействие** (рассогласование убивает конверсию), поэтому это явный признак в модели, а не неявный эффект.

**Сегменты в модели**: случайные эффекты сегмента (аудитории) + взаимодействия «атом × сегмент» со shrinkage (подробнее в §15.4). Без этого модель не сможет различать "хук X хорош глобально" и "хук X хорош только для мам 25-35".

**⚠️ match_score — шумный признак**: вычисляется LLM, не числовой сигнал. Необходима калибровка на реальных конверсиях (LLM говорит "match 0.9", а CVR не выше среднего → калибруем). До калибровки — широкий приор, низкий вес.

### 6.4. Четыре механизма постоянного исследования

Критическое требование: **система НЕ ДОЛЖНА залипать на победителях**.

1. **Природа Thompson Sampling** — сэмплирование из распределения автоматически даёт exploration пропорционально неопределённости
2. **Фиксированная доля трафика** (10–20%) на чистые эксперименты — новые комбинации, которые ещё не тестировались
3. **Генератор с оптимистичным приором** — новые варианты стартуют с широким распределением (высокая неопределённость = больше шансов быть выбранным); если "геном" похож на успешные — чуть оптимистичнее
4. **Бандит по атомам** — статистика делится между комбинациями через общие атомы (хук X хороший → все комбинации с хуком X получают бонус)

**Усиление exploration через Universal Cross-Niche Model (см. §15.12):**

Все четыре механизма становятся эффективнее при наличии кросс-нишевой модели:

1. **Thompson + Universal Prior**: неопределённость **перераспределяется**. Атомы с кросс-нишевым опытом получают узкий приор → Thompson реже выбирает их "для проверки". Реально новые, неисследованные комбинации сохраняют широкий приор → Thompson выбирает их чаще. Exploration фокусируется на **реально неизвестном**, а не на переоткрытии уже известных провалов
2. **Exploration budget + ранжирование кандидатов**: те же 10-20% бюджета, но кандидаты для эксперимента **ранжированы** кросс-нишевым опытом. Из 10 экспериментов 5-6 реально полезных вместо 3 случайных. КПД exploration растёт без увеличения бюджета
3. **Информированный приор вместо одинаково широкого**: новые варианты стартуют с **разными** приорами на основе кросс-нишевого опыта ("хук-шок + CTA-гарантия" = позитивный приор по 30 кейсам; "хук-шок + CTA-таймер" = негативный приор, кликбейт-сигнатура). Перспективные комбинации получают больше шансов, токсичные — меньше
4. **Кросс-клиентский бандит по атомам**: статистика атомов делится не только внутри клиента (30 тестов), а по всей платформе (5000+ тестов по нише). Атомы приходят **предобученными** — бандит работает с первого дня

**Ключевой принцип**: universal model **не уменьшает** exploration, а **повышает его КПД**. Те же деньги — больше информации. Образно: без universal model exploration = фонарик, светящий во все стороны; с universal model — тот же фонарик, но мы знаем где стены (тупики) и светим туда, где ещё не были

**Робастность приоров**: universal prior должен быть **робастным** — t-распределение (ν = 3-5) вместо Gaussian для коэффициентов атомов. Причина: Gaussian-приор с малой дисперсией подавляет outlier-клиентов, которые реально отличаются от ниши. Тяжёлые хвосты t-распределения позволяют клиентским данным "перекричать" приор, если свидетельства достаточно сильны. На практике: `pm.StudentT(nu=4, mu=niche_prior, sigma=...)` вместо `pm.Normal(...)` для коэффициентов в §15.3.

**Expected Value of Information (EVI)**: вместо равномерного 10-20% exploration budget, ранжировать эксперименты по **ожидаемой ценности информации** — насколько сузится неопределённость ключевых решений, если запустить этот тест. Приоритет тестам, которые разрешают «ничью» между кандидатами или проверяют гипотезу с высоким потенциальным upside. Аппроксимация: Thompson Sampling с `n_samples > 1` (top-two Thompson) — дёшево и эффективно для задач ранжирования.

### 6.5. Двухконтурная структура (ключевое архитектурное решение)

**Проблема**: Meta сама оптимизирует доставку. Два оптимизатора конфликтуют. Хуже того: добавление новых объявлений в активный ad set **может сбросить Learning Phase** (~50 событий оптимизации за 7 дней). Help Center включает это в "significant edits", хотя тесты практиков показали, что одно объявление в большом ad set не всегда перезапускает learning (см. §25 п.8). Система, которая постоянно подкладывает свежие креативы, рискует сбрасывать обучение. Кроме того, Meta внутри одного ad set концентрирует показы на 1-2 объявлениях (подтверждено практиками; Meta в 2025 выпустила Creative Testing tool как ответ — см. §25 п.14).

**Решение — два контура:**

```
┌─────────────────────────────────────────────────────────┐
│  ТЕСТОВЫЙ КОНТУР                                        │
│  Изолированные ячейки (отдельные ad sets)               │
│  Новые креативы запускаются ПАЧКАМИ (не по одному)       │
│  Равные бюджеты для чистого сравнения                    │
│  Граф решений + Thompson Sampling управляют отбором      │
│                                                         │
│  Победители ──────────────→ переезжают в ↓              │
│                                                         │
│  МАСШТАБИРУЮЩИЙ КОНТУР                                  │
│  Консолидированные кампании (Advantage+ / CBO)          │
│  Почти не трогаем — Meta оптимизирует доставку          │
│  Только ротация выгоревших креативов                     │
└─────────────────────────────────────────────────────────┘
```

**Правила взаимодействия с Meta:**

| Правило | Почему |
|---------|--------|
| Не трогать Learning Phase (~50 конверсий за 7 дней) | "Learning Limited" = Meta показывает хуже |
| Не менять бюджет > 20% за шаг | Рост > ~20% может сбросить обучение |
| Новые креативы → в новый ad set или через Creative Testing tool | Добавление в живой ad set может сбросить learning; Creative Testing tool (2025) — альтернатива |
| Логировать статус learning до/после каждого запуска | Реальное поведение не всегда совпадает с документацией |
| Решения по бюджету только после выхода из learning | Данных до этого недостаточно |
| На сайте — полный контроль в реальном времени | Meta не видит, что происходит на лендинге; нет конфликта оптимизаторов |

**Winner's curse (проклятие победителя):** лучший из 9 креативов в тестовом контуре частично выиграл шумом. В масштабе он откатится к среднему. Митигация:
- **Shrinkage** в иерархической модели: оценка подтягивается к среднему группы, и тем сильнее, чем меньше данных
- **Подтверждающий прогон**: перед переносом в scale — короткий прогон с увеличенным бюджетом, чтобы проверить, что результат воспроизводится
- **Опционально: Bid Cap при soft launch** — дублировать победителя в scale-кампанию с предельной ставкой (Bid Cap ≈ целевой CPA × 1.2). Сильный креатив получит показы; случайный победитель — нет, и бюджет не сгорит. ⚠️ Слишком тугой Bid Cap = Meta не открутит бюджет вообще; использовать как страховку, не как основной механизм

Это естественный скелет для графа решений: тестовый контур = exploration, масштабирующий = exploitation.

### 6.6. Обратная связь в Meta через CAPI

Отправлять в Meta через Conversions API **ценность** (маржу, предсказанный LTV, квалификацию лида), а не просто событие "покупка". Это позволяет алгоритму Meta оптимизироваться под **наш ROI**, а не под количество конверсий.

### 6.7. Delayed Churn Penalty — ретроспективная коррекция по оттоку

**Проблема**: hurdle-модель (§6.3a) терминируется на покупке/лиде. Система не видит, что происходит **после** конверсии. Если креатив A привлекает покупателей с высоким чеком, но через 60 дней они массово возвращают товар (или в B2B: лид квалифицируется, но сделка срывается) — система продолжает масштабировать A, оптимизируя «краткосрочный хайп», а не долгосрочный ROI.

**Механизм**:
1. CRM отправляет webhook по событиям `churn`, `refund`, `deal_lost`, `subscription_cancelled`
2. Система связывает событие с когортой → атомами креатива и лендинга, которые привлекли эту когорту
3. Ретроспективное обновление апостериоров: α (successes) корректируется вниз пропорционально churn rate когорты
4. Атомы с аномально высоким churn получают **penalty** в Thompson Sampling — система реже их предлагает

**Параметры**:
- **Окно наблюдения**: 90–180 дней (для B2B с длинным циклом сделки). Для e-commerce: 30–60 дней
- **Decay weight**: недавний churn весит больше, чем churn год назад (экспоненциальный decay, λ = 0.02/день)
- **Защита от over-correction**: штраф ≤ 30% от текущего posterior weight атома за один пересчёт — иначе единичная волна возвратов может убить хороший креатив
- **Минимальный размер когорты**: пересчёт запускается при ≥ 20 конверсий в когорте (при n < 20 churn rate слишком шумный)

**Связь с Quality Score (§4.2)**: Quality Score ловит **явный** кликбейт (обещание ≠ факт). Delayed Churn Penalty ловит **скрытое** несоответствие ожиданий — когда креатив технически правдив, но создаёт завышенные ожидания, которые проявляются только через месяцы.

**Фазирование**: Phase 3+ (требует CRM-интеграцию и накопление данных по retention). Для B2B клиентов с Proxy Value Bidding (§16.1) — **Phase 3 mandatory**, т.к. без churn penalty система будет систематически переоценивать proxy value «tire kickers».

### 6.8. Pixel Pollution Protection — защита пикселя от загрязнения

**Проблема**: некорректная рекламная кампания (неправильный заголовок, кликбейтный текст, нерелевантная аудитория) привлекает нецелевых пользователей. Их клики и конверсии обучают алгоритм Meta Pixel оптимизировать доставку под неправильный профиль. Результат: даже после исправления креатива пиксель продолжает привлекать нецелевую аудиторию. «Загрязнение» пикселя = деградация всех последующих кампаний. Для B2B с малыми объёмами (десятки конверсий/неделю) проблема особенно острая — каждый ложный сигнал весит значительно.

**Три уровня защиты:**

**Уровень 1 — CAPI Quality Gate (наш контроль, день 1)**:
Система фильтрует, какие конверсии отправляются в Meta через CAPI. CRM (GoHighLevel) предоставляет обратную связь по качеству лида:
- Форма отправлена, но лид не ответил на звонок и не пришёл на встречу (7 дней) → событие **НЕ отправляется** в CAPI
- Лид ответил на звонок (GHL call tracking) → отправляется с proxy value (низкий)
- Лид пришёл на встречу (GHL `appointment.completed` / Google Calendar) → отправляется с proxy value (высокий) — **основной сигнал качества**
- Сделка закрыта (GHL `opportunity.won`) → отправляется с реальной ценностью

Пиксель учится только на лидах, которые **ответили на звонок или пришли на встречу**. Плохая кампания привела мусорные лиды → они не ответили → CAPI ничего не отправил → пиксель не загрязнён.

**Уровень 2 — Multi-Pixel Architecture (изоляция рисков)**:
Поддержка нескольких пикселей на аккаунт с разным назначением:

| Пиксель | Назначение | Кампании |
|---------|-----------|----------|
| Primary | «Чистый» — только подтверждённые конверсии из CRM | Масштабирующий контур (§6.5) |
| Test | Для тестового контура — экспериментальные кампании | Новые креативы, новые аудитории |
| Product-specific | Для разных продуктов/сегментов | Если продукты привлекают разные аудитории |

Если тестовый пиксель «загрязнён» плохой кампанией — primary чистый. Создаём новый тестовый и продолжаем. Привязка пиксель → кампания управляется через admin-панель.

**Уровень 3 — Автодетекция загрязнения (Phase 3+)**:
Мониторинг сигналов загрязнения в реальном времени:
- Резкое падение lead quality rate (из CRM) при стабильном volume → алерт
- Рост мусорных лидов с конкретной кампании → автопауза (Circuit Breaker §12.5a)
- Аномальный CTR (слишком высокий) + низкая конверсия в CRM = кликбейтный креатив → не кормить пиксель этими данными
- Сравнение профиля новых лидов с профилем подтверждённых клиентов из CRM → drift detection

**Связь с другими механизмами**:
- **Quality Score (§12.2)**: ловит кликбейт ДО загрязнения пикселя
- **Delayed Churn Penalty (§6.7)**: ловит загрязнение ПОСЛЕ (ретроспективно, через CRM)
- **Pixel Protection** заполняет промежуток: ловит загрязнение В РЕАЛЬНОМ ВРЕМЕНИ через CAPI-фильтрацию

**Фазирование**: Уровень 1 (CAPI Quality Gate) — Phase 0, обязателен с первого дня. Уровень 2 (Multi-Pixel) — Phase 0, архитектурно заложен с первого дня. Уровень 3 (Автодетекция) — Phase 3+.

## 7. Модель поведения клиента и персонализация

### 7.1. Что предсказываем

**НЕ "характер"**, а вероятностный вектор:
- P(покупка) — вероятность конверсии
- Главное возражение (цена / доверие / непонимание продукта / нет срочности)
- Ожидаемая ценность (predicted revenue)
- **Uplift** — кому наше воздействие реально меняет решение (а не кто и так купит)

### 7.2. Сигналы поведения (собираемые в реальном времени)

| Сигнал | Что говорит |
|--------|-------------|
| Какой креатив привёл | Вероятно, самая сильная подсказка о намерении |
| Scroll velocity и паттерн | Быстро пролистал = не зацепило; медленно на конкретном блоке = интерес |
| Первый клик / hover | Что важнее всего: цена? отзывы? гарантии? фичи? |
| Время на блоках цены, отзывов, гарантий, FAQ | Карта возражений |
| Паттерн возврата | Ушёл и вернулся = сравнивал с конкурентами |
| Взаимодействие с квизом/калькулятором | Уровень вовлечённости и конкретные ответы |
| Досмотр видео на странице | Глубина интереса |
| Устройство, время суток, гео | Контекст сессии |
| Повторные визиты | Стадия принятия решения |
| Форма: какие поля заполнены, где бросил | Точка трения |

### 7.3. Этапы реализации

**Этап 1 — Правила и кластеры (день 1):**
- Кластеризация сессий без учителя на 5–8 архетипов:
  - "Изучающий" (долго читает всё)
  - "Ищущий цену" (сразу скроллит к прайсу)
  - "Ищущий доказательства" (первым делом — отзывы)
  - "Готовый купить" (быстро к CTA)
  - "Случайный" (bounce < 10 сек)
- LLM подписывает кластеры и генерирует гипотезы

**Этап 2 — Модель склонности:**
- Градиентный бустинг по признакам сессии
- Последовательностные модели (RNN/Transformer) — когда тысячи сессий

**Этап 3 — Uplift + контекстный бандит:**
- Uplift-модель: кому воздействие реально помогает
- Контекстный бандит для выбора: блок, оффер (скидка / гарантия / рассрочка / бонус), видео на странице
- **Исследование не прекращается** (exploration budget)

**Этап 4 — Адаптация внутри сессии:**
- Старт с приором по источнику (креатив → ожидаемый профиль)
- Уточнение по ходу сессии (первые 3-5 действий)
- Перестановка блоков на лету: "скептику" → отзывы наверх; "импульсивному" → CTA + urgency

**Этап 5 — Обратная петля в Meta:**
- Поведенческие сегменты → Custom Audiences через CAPI
- Custom/Lookalike на основе поведенческих профилей (✅ ПРОВЕРЕНО: Advantage+ audience трактует кастомные аудитории как **подсказки**, не жёсткий таргет — Meta может показывать за пределами. Ограничить можно только выключив Advantage+. См. §25 п.12)
- Пример: "смотрел цену и ушёл" → показываем видео про рассрочку / окупаемость

### 7.4. Ограничения (заложить сразу)

- **Тысячи сессий** с исходами нужны для обучения → на старте работают правила и архетипы
- **Постоянная контрольная группа** 5–10% со стандартным опытом (иначе система подтверждает свои же решения)
- Посетитель **анонимен** — работаем на уровне сессии (first-party cookie с согласием; fingerprinting юридически рискован по GDPR/ePrivacy — не используем)
- **Cross-device identity resolution** (Phase 2+): пользователь видит рекламу на мобильном (Сессия 1) → возвращается с ноутбука (Сессия 2). Без склейки — это два анонима, Сессия 1 записывается как bounce, персонализация в Сессии 2 сбрасывается. **Решение**:
  - При микро-конверсии (email, телефон, отправка формы, авторизация) → связать `anonymous_cookie_id` с `crm_user_id`
  - Передавать хэшированный `external_id` через CAPI (стандартная практика Meta, совместима с Advanced Matching)
  - **Только после consent** (§12.1a CMP) — без согласия сессия остаётся анонимной
  - На пре-конверсионном этапе (до ввода email) склейка **невозможна** без fingerprinting → это ограничение, не баг
  - Ретроспективная коррекция: при склейке система пересчитывает Сессию 1 как "вернулся и конвертировал" (не bounce)
- **GDPR / ePrivacy**: согласие на трекинг, право на забвение, отказ от чувствительных признаков
- **Meta "Personal Attributes" policy**: нельзя таргетировать по здоровью, финансам, и т.д.
- **Ограничения по марже**: не приучать клиентов ждать скидку (если "скептикам" всегда давать скидку — все станут "скептиками")
- **Персональные цены** юридически рискованны в ряде юрисдикций

## 8. Прогнозирование и предиктивный слой

### 8.1. Прогноз выгорания креатива

Паттерн: Frequency ↑ → Hook Rate начинает снижаться → CTR падает → CPA растёт

Система обнаруживает **ранние сигналы** (micro-drop в Hook Rate при росте Frequency) и **заранее готовит замену** до того, как ROAS упадёт. Thompson Sampling с затуханием счётчиков автоматически снижает "уверенность" в старых креативах.

### 8.2. Прогноз аудиторного насыщения

Отдельно от creative fatigue — **audience fatigue**. Когда конкретный сегмент перенасыщен, даже новые креативы будут показывать слабый результат. Система должна обнаруживать это и рекомендовать: расширить аудиторию, пауза на сегмент, или сменить канал.

**Ключевой детектор**: d(Reach) / d(Spend). Если охват перестаёт расти пропорционально тратам, а частота (frequency) резко растёт — это audience saturation, не creative burnout. Замена креатива здесь **не поможет** (вы потратите деньги на тест, который провалится по причине, не связанной с креативом).

| Сигнал | Диагноз | Действие |
|--------|---------|----------|
| Hook rate ↓ + Frequency ↑ + Reach растёт | Creative fatigue | Ротация креатива |
| Hook rate ↓ + Frequency ↑ + Reach стагнирует | Audience saturation | Расширить аудиторию / сменить таргетинг |
| Hook rate ↓ + Frequency стабильна + Reach стабилен | Рыночный сдвиг (сезонность, конкуренты) | Проверить якорный креатив (§23 Phase 0) |

### 8.3. Предсказание до запуска

**Честно**: на холодном старте точность скромная. Использовать как **ранжирование** ("какие 5 из 30 вариантов тестировать первыми"), а не замену теста.

Источники приора:
- Creative DNA похожих успешных креативов
- Исторические данные по атомам
- "Синтетические аудитории" на LLM — **слабый приор**, не истина
- Экспертная оценка маркетолога (см. раздел 12.4)

### 8.4. Предиктивная бюджетная кривая

"Если увеличить бюджет до $X, CPA вырастет на Y%" — кривая маржинальной эффективности. Большинство маркетологов летят вслепую здесь. Система моделирует эту кривую и рекомендует оптимальный уровень расходов на каждую комбинацию аудитория × креатив.

### 8.5. Портфельная оптимизация бюджета (⚠️ ПОЗЖЕ / ПРОВЕРИТЬ)

> **Конфликт**: §10.2 говорит, что Meta управляет распределением бюджета (CBO). Mean-variance оптимизация на шумных оценках доходности ad sets нестабильна. Идею не убираем, но **переносим в Phase 6+** — когда будет достаточно данных для робастных оценок ковариационной матрицы и понятно, на каком уровне (campaign? channel?) это применимо без конфликта с Meta CBO.

Концепция: трактовать ad sets как финансовые активы, использовать подход Марковица для оптимального распределения бюджета с учётом корреляций (каннибализация между ad sets).

## 10. Account Structure Strategy (Meta)

**Это не деталь, а фундамент.** Как структурированы кампании — определяет, что может оптимизировать система.

### 10.1. Подход

Meta двигается к консолидации (Advantage+). Система должна учитывать это:

- **CBO (Campaign Budget Optimization)**: Meta сама распределяет бюджет между ad sets. Наш слой НЕ должен дублировать это — конфликт оптимизаторов.
- **Advantage+ Shopping Campaigns**: максимальная автоматизация Meta. Наша роль — **подбор и ротация креативов**, не управление ставками.
- Структура аккаунта — **мета-решение**, которое тоже принимает граф (сколько кампаний? какая группировка аудиторий?)
- Реализуется через **двухконтурную структуру** (см. раздел 6.5): тестовый контур (изолированные ячейки) + масштабирующий (консолидированный)

### 10.2. Практическое разделение

| Мы управляем | Meta управляет |
|--------------|----------------|
| Какие креативы создавать и тестировать | Кому показывать (алгоритм доставки) |
| Когда переносить победителя в scale-контур | Оптимизация ставок |
| Когда убирать выгоревший креатив из scale | Распределение бюджета внутри CBO |
| Ценность конверсии (CAPI) | Auction bidding |
| Контент на лендинге (полный контроль) | — |
| Структура аккаунта (мета-решение) | — |

### 10.3. Meta API Rate Limits (критично при масштабировании)

**Проблема**: Meta Marketing API имеет скользящие лимиты вызовов (Application-level и User-App-level). При обслуживании десятков клиентов с сотнями тестов система делает тысячи вызовов/час: проверка Learning Phase, изменение бюджетов, паузы ad sets, CAPI-события. Превышение лимита → ошибка 17/613, блокировка на 15-60 минут.

**Почему это опасно**: если в момент блокировки срабатывает Circuit Breaker (§12.5a L2/L3), система **не сможет отправить команду паузы**. Бюджет продолжит тратиться.

**Архитектура rate management:**

```
┌─────────────────────────────────────────────────┐
│  Priority Queue                                  │
│                                                  │
│  P0 (мгновенно, вне очереди):                   │
│  ├── Circuit Breaker pause/resume                │
│  ├── Site Health Guard autopause                 │
│  └── Budget ceiling enforcement                  │
│                                                  │
│  P1 (нормальный поток):                         │
│  ├── Создание/пауза ad sets                     │
│  ├── Изменение бюджетов                         │
│  └── CAPI events                                │
│                                                  │
│  P2 (фоновый, throttled):                       │
│  ├── Проверка Learning Phase status             │
│  ├── Чтение метрик (insights)                   │
│  └── Ad Library polling                          │
│                                                  │
│  Rate Limiter: token bucket per app/user token   │
│  При приближении к лимиту → P2 приостанавливается│
│  P0 выполняется ВСЕГДА (резерв 10% квоты)       │
└─────────────────────────────────────────────────┘
```

**Реализация**: rate-aware API wrapper с встроенным token bucket (не требует отдельного Celery/RabbitMQ — достаточно in-process rate limiter + async queue в FastAPI). Метрики: текущее потребление квоты, время до восстановления, количество отложенных P2 запросов.

**Fallback при полной блокировке токена**: Meta Automated Rules (§12.5a) работают на стороне Meta и **не зависят от нашего API-доступа**. Это последний рубеж.

## 11. Модуль внешних сигналов

### 11.1. Зачем

Система моделирует стационарный мир. Реальность — нет. Без этого модуля система будет принимать ошибочные решения:
- Ноябрь: CPM вырос в 3x → система решает "креатив выгорел" → заменяет работающий креатив = потеря денег
- Конкурент запустил агрессивную акцию → все метрики упали → это не проблема креатива

### 11.2. Якорные креативы (простое и эффективное решение)

В аккаунте постоянно живут **два референсных креатива-"якоря"** — проверенных, стабильных.

**Правила размещения:**
- Якори идут **в той же пачке и на той же аудитории**, что тестовые ячейки (иначе сравнение некорректно)
- Якорь занимает одну ячейку бюджета — это осознанная цена
- Два якоря для надёжности (один может выгореть)

**Принятие решений:**
- Если оба якоря упали одновременно с тестовыми → **рынок**, не креатив → не менять креативы
- Если тестовые упали, якоря держатся → **креативы** → ротация
- Решение по **статистическому порогу** (P(разница > X) > 0.9), не на глаз

Варианты всегда сравниваются одновременно — это снимает большую часть проблемы сезонности. Внешние сигналы (CPM-индекс, календарь) остаются дополнением.

### 11.3. Дополнительные сигналы

| Сигнал | Источник | Как влияет |
|--------|----------|------------|
| CPM-индекс по нише | Meta API / бенчмарки | Нормализация стоимости |
| Календарь событий | Внутренний | Black Friday, праздники, отраслевые события |
| Конкурентная активность | Ad Library | Новые акции конкурентов |
| Погода (для отдельных ниш) | Weather API | E-commerce, доставка, путешествия |
| Новостной фон | News API / LLM | Контекст восприятия рекламы |
| Аномалии в базовых метриках | Внутренняя детекция | Отличить "наш креатив ослаб" от "весь рынок дорогой" |

### 11.4. Site Health Guard — мониторинг технических сбоев на стороне сайта

**Проблема**: якорные креативы (§11.2) отлавливают **рыночные** шоки, но **технический сбой сайта** — другой класс проблемы. Если упал платёжный шлюз или форма возвращает ошибку 500:
- Конверсия падает до нуля за минуты
- Якоря тоже падают (ведут на тот же сайт) → система решает "рынок упал" → **правильно не меняет креативы**, но...
- ...продолжает **тратить бюджет** на рекламу, которая ведёт на сломанный сайт

**Решение — три слоя мониторинга:**

| Проверка | Метод | Действие |
|----------|-------|----------|
| HTTP-статус лендингов | Health check каждые 1-5 мин (HEAD/GET + проверка статуса) | Автопауза рекламы при 5xx/timeout |
| Форма / платёжный шлюз | Синтетический мониторинг: headless browser заполняет форму периодически | Алерт + автопауза рекламы |
| Резкое падение конверсии при стабильном трафике | Аномалия: CTR стабилен, но CVR → 0 за < 1 час | Автопауза + срочный алерт маркетологу |

**Отличие от §11.2 (якорные креативы):**
- Якоря определяют: "проблема в креативе или на рынке?" → решение: менять или не менять креативы
- Site Health Guard определяет: "сайт вообще работает?" → решение: **остановить трату бюджета** до починки

**Правила автопаузы:**
- Пауза автоматическая, без подтверждения маркетолога (каждая минута простоя = потерянные деньги на рекламу)
- Возобновление — после подтверждения, что сайт снова работает (health check проходит 3 раза подряд)
- Все паузы и причины логируются в алертах

## 12. Защитные механизмы

### 12.1. Compliance — автопроверка на правила Meta

**Бан рекламного аккаунта убьёт всю систему.** Перед каждым запуском:
- Проверка на запрещённые обещания (результат "до/после", здоровье, финансы)
- Проверка на "personal attributes" в таргетинге
- Проверка на кликбейт и misleading claims
- LLM-ревьюер с промптом из Meta Advertising Policies

### 12.1a. Consent Management и защита интеллектуальной собственности

#### 12.1b. Server-Side First & First-Party Data Architecture

**Проблема**: классический client-side трекинг (Pixel, JavaScript-теги) деградирует. iOS ATT блокирует ~40-50% трекинга на мобильных, браузерные ad-blockers — ещё 15-25%, Third-Party Cookie Phaseout в Chrome завершается. Без server-side сбора CAPI получает неполные данные → Bayesian модель обучается на biased 60-70% выборке → posteriors смещены → решения системы субоптимальны.

**Решение — обязательный элемент Phase 0:**
- **Server-Side GTM (sGTM)** или собственный server-side proxy для каждого клиента
- Все события конверсии собираются server-side (first-party домен клиента → наш сервер → CAPI Meta)
- Pixel остаётся как дедупликация и fallback, **не как primary source**
- Server-side сбор обходит большинство ограничений ATT и ad-blockers, т.к. запросы идут с first-party домена
- CMP-consent (см. ниже) проверяется server-side до записи события

**Архитектура**:
```
Браузер/приложение → First-party endpoint (subdomain клиента)
     → Server-side GTM / наш proxy
          → CAPI Meta (с event_id для дедупликации с Pixel)
          → Наша база событий (для Bayesian модели)
          → CRM (для Proxy Value Bidding, §16.1)
```

#### CMP-интеграция (Consent Management Platform)

**Проблема**: динамическая персонализация лендингов (§7, Этапы 3-4) требует трекинга поведения на сайте — скролл, hover, клики, время на блоках. Но трекинг требует согласия пользователя (GDPR, ePrivacy Directive, CCPA). Если пользователь отклонил cookies, персонализация **невозможна**, и система должна это понимать.

**Решение — интеграция с CMP (Cookiebot, OneTrust или аналог):**

- Система проверяет статус согласия **до запуска трекинга и персонализации**
- Три режима работы в зависимости от согласия:

| Статус согласия | Трекинг | Персонализация лендинга | Thompson Sampling |
|----------------|---------|------------------------|-------------------|
| Полное согласие | Все события | Полная (перестановка блоков, адаптация) | С контекстом сессии |
| Только необходимые | Только конверсии (first-party, без куков поведения) | Нет — показываем дефолтный вариант | Без контекста сессии |
| Отказ от всего | Ничего | Нет | Нет |

- **Критично**: отказ от cookies ≠ bounce. Система **не должна** считать таких посетителей как "не заинтересованных" — это искажает данные для модели
- Доля отказов от cookies (обычно 20-40% в EU) должна учитываться при расчёте минимальных объёмов данных (§24 калькулятор мощности)

#### Защита от использования чужой интеллектуальной собственности

**Проблема**: генерируемый контент (текст лендингов от LLM, видеомонтаж из футажей) может непреднамеренно включать:
- Чужие товарные знаки или слоганы в тексте
- Узнаваемые лица (знаменитости, конкуренты) в видеофутажах
- Музыку, защищённую авторским правом (уже в §22)
- Дизайн-элементы, скопированные из конкурентных лендингов

**Решение — двухуровневая проверка перед апрувом маркетологом:**

| Уровень | Что проверяется | Как | Когда |
|---------|----------------|-----|-------|
| Автоматический | Товарные знаки в тексте | LLM проверяет текст против базы зарегистрированных ТМ в нише клиента | При генерации текста |
| Автоматический | Лица в видео | Face detection + сверка с базой публичных лиц (celebrities, конкуренты) | При монтаже видео |
| Автоматический | Музыка | Проверка на royalty-free лицензию (уже в §22) | При добавлении аудио |
| Ручной (маркетолог) | Общий compliance-обзор | Чеклист в admin-панели перед финальным апрувом | Перед запуском |

**Важно**: автоматическая проверка — предфильтр, не замена человеческого апрува (см. §12.4). LLM может пропустить нюансы (например, пародию на конкурентный слоган, которая формально не совпадает, но узнаваема). Маркетолог остаётся финальным контролёром.

### 12.2. Антикликбейт — двойная защита

**Основная защита** — правильная целевая функция. Если Thompson Sampling оптимизирует **прибыль с учётом возвратов и реального исхода** (а не CTR), кликбейт наказывается автоматически: высокий CTR + высокие возвраты = низкий profit = низкий reward.

**Проблема**: возвраты приходят через недели. В этом окне кликбейт выглядит как победитель и получает бюджет.

**Решение — Quality Score как опережающий индикатор** (пока финальные данные не пришли):

```
Quality Score = f(Message Match Score, Bounce Rate, Scroll Depth, Form Completion Rate)
```

- Работает как **ранний сигнал** до прихода данных о возвратах/LTV
- После прихода финальных данных — основной reward пересчитывается по прибыли, Quality Score теряет вес
- **Предзапусковая сверка**: LLM проверяет обещания в креативе против базы фактов о продукте — ловит и кликбейт, и нарушения правил Meta одновременно

### 12.3. Staged Gates (последовательное исключение)

Вместо дискретных бюджетных прыжков — **фиксированный равный бюджет на ячейку** (ad set). Ворота = **контрольные точки по накопленному расходу**, а не повышения бюджета. "Kill" = пауза ad set. Выжившие продолжают набирать данные в том же ad set (данные накапливаются, Meta Learning Phase не сбрасывается).

| Gate | Порог | Формула стоимости | Метрика | Решение |
|------|-------|-------------------|---------|---------|
| **Gate 1: Hook** | ~5-8K показов, не ранее 2-3 суток с запуска | показы / 1000 × CPM | Hook Rate (3-сек просмотры) | Kill / Continue |
| **Gate 2: Click + Landing** | ~300+ кликов (≈ сессий) | клики × CPC | CTR, CPC, Bounce Rate, Scroll Depth | Kill / Continue |
| **Gate 3: Conversion** | ~50 конверсий (выход из learning) | CPA × 50 | CPA, ROAS | Kill / Scale |

Gates 2 и 3 (из v1.4) объединены: клики ≈ сессии, пороги совпадали. Три ворот вместо четырёх — проще и без дублирования.

**Пороги ворот 1-2 определяются объёмом данных (показы, клики), а не бюджетом.** Стоимость прохождения зависит от CPM/CPC ниши. Только Gate 3 привязан к CPA.

**Минимальная длительность**: Gate 1 — не ранее 2-3 суток с запуска (первые часы доставки нерепрезентативны: Meta исследует аудиторию). Остальные ворота — по накоплению данных.

**Почему фиксированный бюджет, а не прыжки**: дискретные прыжки ($50 → $200 → $2000) конфликтуют с правилом §6.5 (не более 20% за шаг) и сбрасывают learning phase. При фиксированном бюджете Meta работает стабильно, а мы наблюдаем, как накапливаются данные, и отсеиваем проигравших на каждом пороге.

**Принципы принятия решений на воротах:**
- **НЕ жёсткие пороги на точечных оценках** (порог "выше медианы" убивает 50% по построению, включая хорошие)
- Решать по **апостериорной вероятности**: убивать, если P(метрика выше базовой) < 10%
- Gate 3 (conversion): сравнивать **относительно якоря в той же пачке**, а не с абсолютным целевым CPA (CPA в learning phase обычно на 20-50% выше, чем после выхода из обучения)
- Пороги калибровать по связи «метрика → ROI» (как требует §3.2), а не задавать константами
- По сути — **байесовские правила остановки** (sequential testing): после каждого gate обновляем апостериор и решаем, продолжать ли

**Томпсон в тестовом контуре**: остаётся для ранжирования кандидатов и решений на сайте (выбор лендинга). На уровне Meta ad sets — последовательное исключение с равным бюджетом. Томпсон и ворота не конфликтуют: Томпсон ранжирует → ворота отсеивают.

**Лимит максимальных потерь на креатив**: фиксированная сумма ($X), после которой стоп вне зависимости от gate.

### 12.4. Роль человека

| Уровень автономности | Что делает система | Что делает маркетолог |
|---------------------|--------------------|-----------------------|
| **Наблюдатель** (старт) | Показывает аналитику и рекомендации | Всё решает сам |
| **Советник** | Рекомендует креативы, бюджет, ротацию | Утверждает каждое действие |
| **Полуавтопилот** | Автоматически тестирует и ротирует в рамках лимитов | Утверждает новые концепции, устанавливает лимиты |
| **Автопилот** | Полный цикл в рамках установленных ограничений | Мониторит, устанавливает стратегию и ограничения |

**Начинаем с "Советника"**. Маркетологи не примут чёрный ящик.

Экспертные оценки до запуска (бренд, уместность) → **приор или вето** в графе решений.

### 12.5. Автопилот с ограничителями и Financial Circuit Breaker

Базовые правила:
- Лимит изменения бюджета за шаг (max 20%)
- Ручное подтверждение запусков на старте
- **Off-policy evaluation** движка решений на собственных логах с propensity weights **до допуска к реальным деньгам** (бэктест на "исторических данных Meta" невозможен — нет counterfactual; только на наших логах, где записаны кандидаты и вероятности выбора)

#### 12.5a. Financial Circuit Breaker — трёхуровневая система предохранителей

**Проблема**: разрозненные упоминания stop-loss (§12.3, §12.5) не образуют единой защитной системы. Для перехода к "Автопилоту" (§12.4) необходим формализованный механизм с иерархией защит, каскадной логикой и протоколом восстановления. **Ни один CMO не доверит автоматизированной системе бюджет** без жёстких финансовых рамок с мгновенными алертами.

**Принцип триггеров: байесовские правила, не жёсткие пороги.** Наивные пороги ("CPA > 2× за 4 часа") дают ложные срабатывания каждые 2 дня при типичных объёмах ($50K/мес, CPA $40 ≈ 1.7 конверсии/час → Poisson(7) за 4ч → P(≤3) ≈ 8%). Аналогично, "3 провала подряд" при win rate 20% случается в 51% пачек. Триггеры должны быть **байесовскими** — апостериорная вероятность, что метрика хуже порога, а не сравнение точечных оценок.

**Три уровня предохранителей:**

| Уровень | Триггер (байесовский) | Действие | Алерт |
|---------|----------------------|----------|-------|
| **L1: Per-creative** | Расход на один креатив > лимита $X (из §12.3) **ИЛИ** P(CPA > 2× target \| данные ad set) > 0.90 | Пауза ad set этого креатива | Запись в лог; алерт в dashboard |
| **L2: Per-campaign** | P(blended CPA тестового контура > 1.5× target \| данные 48ч) > 0.85 с поправкой на базовую win rate **ИЛИ** дневной расход > 80% ceiling за первые 8 часов **ИЛИ** аномальный CPM spike (z-score > 3 от 14-дневного скользящего) | 🟡 **Throttle**: пауза новых запусков в тестовом контуре | **Push в Telegram/Slack** маркетологу с причиной, P-значением и рекомендацией |
| **L3: Per-account** | P(ROAS < breakeven \| данные 7 дней) > 0.90 для **тестового контура** **ИЛИ** P(ROAS < breakeven \| данные 7 дней) > 0.90 для **scale-контура** **ИЛИ** месячный budget ceiling достигнут | 🔴 **Автопауза**: при проблеме в тестовом → пауза тестовых; при проблеме в scale → пауза scale + срочная эскалация; при ceiling → пауза всего | **Срочный push** в Telegram/Slack + email с причиной и диагностическим отчётом |

**⚠️ L3 покрывает и scale-контур**: предыдущая версия оставляла scale работать при любом L3. Но если убыточен scale (главный расходчик), предохранитель обязан его остановить. Различие: проблема в тестовом → пауза тестовых (scale продолжает); проблема в scale → пауза scale + эскалация маркетологу.

**⚠️ Поправка на базовую win rate**: при win rate 20% серия из 3 провалов — норма (P = 51%). Триггер L2 учитывает ожидаемую долю провалов: сигнал — когда **доля провалов значимо выше базовой** (P > 0.85 по Beta-Binomial), а не абсолютное число.

**Fallback на стороне Meta (критически важно):**

Если наш сервис упадёт **или** Meta API заблокирует наш токен из-за rate limit (§10.3), программный circuit breaker бесполезен. **Второй рубеж** — настройки на стороне Meta, которые работают **независимо от нашего API-доступа**:
- **Account Spending Limit** в Meta Business Manager = жёсткий monthly ceiling
- **Automated Rules** в Meta: "если CPA > X за последние Y часов → пауза campaign" — исполняется на серверах Meta
- Эти правила задаются при онбординге и **не управляются нашей системой** — они страхуют от нашего сбоя, rate limit блокировки и любого другого отказа платформы
- **⚠️ Обязательно при онбординге каждого клиента**: настроить Automated Rules ДО запуска первых тестов

**Правила каскадирования:**
- L1 → L2: если 3+ ad sets сработали L1 за 24 часа → автоматический переход на L2
- L2 → L3: если L2 не разрешён маркетологом за 48 часов → автоматический переход на L3
- При срабатывании L2 или L3 система **не молчит** — мгновенный push/alert с причиной и байесовскими метриками

#### 12.5b. Протокол восстановления

**После срабатывания L2 или L3:**

```
1. ДИАГНОСТИКА (автоматический пост-мортем):
   Что вызвало срабатывание?
   ├── Внешний фактор (CPM spike, сезон) → §11.2 якорные креативы подтвердят
   ├── Технический сбой → §11.4 Site Health Guard подтвердит
   ├── Проблема в оффере → §18 диагностика message-market fit
   ├── Фрод → §12.6 детектор подтвердит
   └── Каскадный провал креативов → §13 кладбище + анализ общих атомов

2. УСТРАНЕНИЕ ПРИЧИНЫ:
   Маркетолог подтверждает причину и план действий в admin-панели

3. ВОЗОБНОВЛЕНИЕ ПАРТИЯМИ (не процентный ramp-up!):
   ⚠️ Скачки бюджета 50%→75%→100% нарушают правило ≤20% за шаг (§6.5)
   и могут сбросить Learning Phase. Правильный протокол:
   
   Шаг 1: Возобновить 2-3 лучших ad sets с ПРЕЖНИМ бюджетом каждого
   Шаг 2 (+24ч): Если метрики в норме → добавить ещё 2-3 ad sets
   Шаг 3 (+48ч): Возобновить оставшиеся
   
   ⚠️ Пауза > 7 дней сбрасывает Learning Phase (§25 п.8).
   Если пауза затянулась → возобновлять как новые ad sets (с учётом
   нового прохождения ~50 событий за 7 дней).
   
   При повторном срабатывании в период восстановления: откат на L3 + ручной разбор

4. ЛОГИРОВАНИЕ:
   Каждое срабатывание + причина + длительность паузы + исход
   → в dashboard (§21) + в историю для калибровки порогов
```

**Жёсткий budget ceiling**: месячный потолок расходов на уровне аккаунта. Задаётся маркетологом при онбординге. Не превышается ни при каких условиях — даже если все метрики отличные. Дублируется в **Meta Account Spending Limit** как независимый fallback. Это **юридическая защита**, а не оптимизационная.

### 12.6. Защита от фрода и бот-трафика (Ad Fraud & Click Farm Protection)

#### 12.6.1. Проблема

Все модели системы (Thompson Sampling §6, Bayesian GLM §15.3, hurdle-модель §15.5) предполагают, что входящий трафик — **настоящие люди**. Если боты или клик-фермы генерируют 5-15% кликов:

- Фиктивные клики **раздувают CTR**, но конверсия нулевая → модель думает "хороший CTR, плохой лендинг" → **оптимизирует не то**
- Ботовые сессии с быстрым bounce портят паттерны поведения (§7.2) → кластеризация (§7.3) загрязнена
- Якорные креативы (§11.2) тоже получают ботовый трафик → система не может отличить рыночный шок от фрода
- Thompson Sampling обучается на отравленных данных → **решения системы деградируют незаметно**
- Фрод невидим: без специального детектора система будет тихо тратить бюджет на оптимизацию под ботов

#### 12.6.2. Решение — четыре слоя защиты

**Слой 1 — Edge-фильтрация (до создания сессии):**

Фильтрация на уровне **Edge Middleware** (Next.js / Vercel Edge), **до** того как бот создаст сессию в БД и запросит расчёт у Thompson Sampling. Интеграция с готовыми решениями:
- **Primary: Cloudflare Bot Management** — работает на edge, **нулевой JS на странице** → не влияет на загрузку и конверсию
- **Secondary: reCAPTCHA Enterprise (invisible, v3)** — дополнительный score на уровне формы. **Только invisible mode** (никаких галочек и пазлов). Пользователь ничего не видит — score вычисляется в фоне. ⚠️ Добавляет ~150KB JS → +200-400ms на медленном мобильном; если Cloudflare достаточен — reCAPTCHA не обязательна
- Bot score < порога → блокировка до создания сессии
- **⚠️ Ни в коем случае не ставить reCAPTCHA v2 (challenge-based)** — убивает 10-30% конверсии на формах. Вся фрод-защита должна быть invisible для реального пользователя

**Слой 2 — Поведенческий фильтр сессий (реалтайм):**

**⚠️ Основной трафик Meta — мобильный (in-app browser).** Правила не должны ложно срабатывать на мобильных пользователях: нет мыши, случайные тапы — норма, CGNAT (много пользователей на одном IP) — норма.

| Паттерн | Что означает | Действие | ⚠️ Mobile-safe? |
|---------|-------------|----------|-----------------|
| Нулевой скролл + < 1 сек + **нет touch-событий** (мобайл) или нет движения мыши (десктоп) | Бот или accidental tap | Пометить как suspicious | ✅ Разделяем touch и mouse |
| Одинаковые тайминги между действиями (σ < 50ms) | Автоматизированный клик | Пометить + алерт | ✅ Работает на любом устройстве |
| Линейный скролл без пауз (scroll velocity = const, нет acceleration) | Бот (программный скролл) | Пометить | ✅ Реальный палец даёт переменную скорость |
| IP-кластер: 50+ сессий с одного IP + **одинаковый UA + одинаковый viewport** за час | Click farm (не CGNAT — у реальных пользователей разные устройства) | Пометить IP + UA комбинацию | ✅ CGNAT-safe: проверяем IP+UA+viewport, не только IP |
| User-Agent в списке известных ботов | Известный бот | Блокировать на Edge | ⚠️ Allowlist для краулеров Meta (facebookexternalhit) |

**⚠️ Accidental taps vs кликбейт**: нулевой скролл + мгновенный уход на мобильном — часто реальный случайный тап, а не бот. Эти сессии **исключаются из обучения эффектов** (атомы), но **остаются в знаменателе** profit/impression. Иначе теряется сигнатура кликбейта из §15.3 (высокий CTR + мгновенный bounce).

**⚠️ Edge-фильтр vs расход**: Edge-фильтрация защищает **наши данные и сервер** от бот-трафика, но **не спасает от расходов** — Meta списывает деньги за клик на своей стороне. Фильтр предотвращает отравление модели, а не waste на рекламу. Запускать Edge-фильтр **сначала в режиме "только лог"** (2-4 недели), с allowlist для краулеров Meta и in-app browser, чтобы не заблокировать реальных пользователей.

**Слой 3 — Аномалии в воронке (ежечасная проверка):**

- Резкий рост CTR без роста конверсий из конкретного гео/плейсмента → подозрение на фрод
- Всплеск кликов в нерабочие часы целевого гео (**07:00-12:00 UTC для US** = 02:00-07:00 ET = реальная ночь; **не** 3:00-5:00 UTC, это вечер ET)
- CTR отдельного ad set аномально выше остальных при одинаковом креативе → подозрительный трафик
- При обнаружении аномалии → алерт маркетологу + автоисключение подозрительных сессий из обучения модели

**Слой 4 — Очистка данных модели (перед обновлением апостериоров):**

- Сессии с флагом `suspicious` исключаются из обучения **эффектов атомов** (§15.3), но **остаются в расходной базе** (знаменатель profit/impression). Иначе модель не видит waste от кликбейта
- Мониторинг доли подозрительных сессий: если > 10% → алерт + анализ источника
- ⚠️ **Meta Invalid Click Rate через API**: подтверждения программного доступа в официальной документации Meta Marketing API не найдено (есть в Ads Manager UI). Пометить как ⚠️ ПРОВЕРИТЬ. Альтернатива: сравнивать наш счётчик кликов (first-party) с кликами из Meta API — дельта ≈ invalid clicks

#### 12.6.3. Взаимодействие с другими модулями

| Модуль | Как связан с фрод-защитой |
|--------|--------------------------|
| Thompson Sampling (§6) | Обучается только на clean sessions |
| Якорные креативы (§11.2) | Фрод-фильтр снимает до якорного сравнения — если якори и тестовые упали одновременно, но фрод высокий, это не "рынок" |
| Site Health Guard (§11.4) | Разные сигналы: SHG → "сайт сломан", Fraud → "трафик фальшивый" |
| Financial Circuit Breaker (§12.5a) | Фрод-spike может вызвать срабатывание L2 (рост CPC без конверсий); диагностика Circuit Breaker проверяет фрод как одну из причин |
| Поведенческие кластеры (§7.3) | Ботовые сессии исключаются из кластеризации |

### 12.7. Multi-tenant Security (изоляция данных и токенов клиентов)

**Проблема**: для режимов «Советник» и «Автопилот» (§12.4) клиенты предоставляют доступ к Meta Ads Manager, CAPI, Pixel, CRM. Это долгоживущие OAuth-токены с правами на управление бюджетами. Компрометация базы = доступ ко всем рекламным аккаунтам и бюджетам всех клиентов.

**Принципы:**

| Уровень | Что защищаем | Как |
|---------|-------------|-----|
| **Хранение токенов** | OAuth tokens, API keys | Шифрование at rest (AES-256). MVP: зашифрованные поля в PostgreSQL с отдельным ключом на клиента. Scale: HashiCorp Vault / AWS KMS с аппаратным шифрованием |
| **Изоляция данных** | Данные клиента A не видны клиенту B | Row Level Security (RLS) в PostgreSQL: `tenant_id` на каждой таблице, политики SELECT/INSERT/UPDATE/DELETE по `current_setting('app.tenant_id')` |
| **Минимальные привилегии** | Токен клиента имеет только нужные permissions | При OAuth-авторизации запрашивать минимальный scope: `ads_management`, `ads_read`, `business_management` — не больше |
| **Ротация токенов** | Снижение окна уязвимости | Long-lived tokens обновляются каждые 60 дней (Meta позволяет exchange). Алерт при неуспешном обновлении |
| **Audit log** | Кто когда что сделал с аккаунтом клиента | Каждый API-вызов к Meta логируется: timestamp, action, client_id, результат. Immutable log |

**⚠️ P0 при онбординге**: безопасное хранение токенов — не Phase 3+ фича, а требование с первого клиента. Без RLS и шифрования — не запускать.

## 13. Negative Learning — "Кладбище" провалов

### 13.1. Зачем

Знать, что НЕ работает — не менее важно, чем знать, что работает. Без этого система будет заново генерировать похожие на провалившиеся креативы.

### 13.2. Реализация

- Каждый провалившийся креатив разбирается на атомы с пометкой "failed" и контекстом (для какой аудитории, в какой период)
- При генерации новых вариантов: **проверка на похожесть** с кладбищем
- LLM генерирует **пост-мортем**: "Почему не сработало" — гипотеза сохраняется
- Периодический пересмотр: возможно, провал был из-за внешних факторов, и идею стоит попробовать снова

### 13.3. RLHA — обучение из правок маркетолога (Reinforcement Learning from Human Approvals)

**Проблема**: маркетолог регулярно правит output системы — переписывает заголовок лендинга, корректирует бриф, меняет CTA. Сейчас эти правки = факт отклонения. Система **не учится** из них и в следующий раз генерирует тот же стилистически чуждый текст. Маркетолог устаёт от повторных ошибок → теряет доверие к системе.

**Механизм — накопление delta (разницы между сгенерированным и утверждённым)**:

1. При каждой правке маркетолога система сохраняет пару: `(generated_text, approved_text)` + контекст (клиент, тип контента, аудитория)
2. Delta анализируется: что изменено? (тон? длина? конкретные слова? структура?)
3. Пары накапливаются в **client-specific correction store**
4. При следующей генерации — пары используются как few-shot примеры в промпте LLM:
   *"Для этого клиента ты раньше написал X, маркетолог исправил на Y. Учти этот стиль."*

**Что система учится понимать**:
- **Tone of voice клиента**: формальный vs разговорный, "вы" vs "ты", технический язык vs простой
- **Запрещённые формулировки**: "бесплатно" (клиент не хочет), "уникальный" (банально для ниши)
- **Структурные предпочтения**: короткие заголовки vs длинные, bullet points vs сплошной текст
- **Бренд-контекст**: как клиент позиционирует себя vs как LLM по умолчанию описывает продукт

**Реализация (Phase 2+)**:
- Объём правок: 5-10 в неделю на клиента — достаточно для few-shot learning, недостаточно для fine-tuning
- Few-shot подход правильный для MVP: не требует GPU, работает с любым LLM, мгновенно адаптируется
- Phase 5+: при накоплении 200+ пар по нише — возможность LoRA fine-tuning нишевого adapter для LLM
- **Метрика качества**: % генераций, утверждённых без правок (target: рост с 30% до 70%+ за 3 месяца)

## 14. Эволюционный алгоритм поверх атомов

### 14.1. Проблема комбинаторного взрыва

10 типов хуков × 5 типов тела × 5 CTA × 8 headline × 6 блоков лендинга × 4 оффера = **48,000 комбинаций**. Thompson Sampling в лоб не справится — данных на каждую ячейку будет мало.

### 14.2. Решение — аддитивная байесовская модель + LLM-генератор

**Важно**: эволюционный подход используется **как генератор кандидатов**, а не как самостоятельный селектор (каждая "оценка" = реальные деньги на рекламу, поэтому позволить себе тысячи оценок нельзя).

**Bayesian GLM по атомам** (та же модель из §6.3a и §15.3):
- Каждый атом имеет свой эффект (атомы видео → CTR; атомы лендинга → CVR; match_score на стыке; hook rate — диагностика, не в chain)
- Мультипликативность: CTR × CVR × AOV = revenue per impression
- Logit link + Binomial likelihood для конверсий (не log + Gaussian)
- Это позволяет оценивать **новые комбинации без тестирования** — по известным эффектам их атомов
- Hurdle: Binomial(конверсия) × Lognormal(чек)
- Неопределённость в оценке каждого атома учитывается при ранжировании

**Генерация кандидатов (LLM как "мутация"):**
1. **Рекомбинация**: лучшие атомы скрещиваются (хук от A + CTA от B)
2. **Проверка связности**: LLM проверяет, что хук от A и тело от B склеиваются по смыслу (message match). Если нет — редактирует для согласованности
3. **Мутация**: LLM генерирует вариацию атома (другой стиль хука на ту же тему)
4. **Элитизм**: лучшие 20% защищены от замены
5. **Ранжирование**: аддитивная модель ранжирует кандидатов → лучшие уходят в тестовый контур

Это масштабируется лучше, чем полный перебор, **сохраняет exploration** через мутации, и не тратит бюджет на заведомо слабые комбинации.

## 15. Predictive Model Architecture — полная схема предсказательной модели

### 15.1. Общая схема: 5 слоёв

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│  ВИДЕО + ЛЕНДИНГ (сырые)                                     │
│         ↓                                                    │
│  Слой 1: Creative DNA (LLM извлекает атомы)                  │
│         ↓                                                    │
│  {hook: "question", face: true, pace: "fast", ...}           │
│  {headline: "benefit-first", proof: "testimonial", ...}      │
│         ↓                                                    │
│  Слой 2: Bayesian GLM по этапам воронки                      │
│  logit(CTR) = Σ β_j × atom_j + γ × match_score              │
│  logit(CVR) = Σ β_k × atom_k                                │
│  log(AOV) = Σ β_l × atom_l                                  │
│  (hook rate — диагностика, не в chain)                       │
│         ↓                                                    │
│  Слой 3: Байесовский (каждый β — распределение, не число)    │
│         ↓                                                    │
│  Слой 4: Hurdle (Binomial × Lognormal → E[Profit])          │
│         ↓                                                    │
│  Слой 5: Thompson Sampling (сэмпл → выбор → тест)           │
│         ↓                                                    │
│  РЕШЕНИЕ: "тестировать этот креатив" / "не тестировать"       │
│                                                              │
│  После теста: обновляем апостериоры β → модель точнее         │
│  → следующее предсказание лучше (замкнутый цикл)             │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 15.2. Слой 1: Извлечение признаков (Creative DNA)

Не предсказание — входной пайплайн. Превращает видео и лендинг в вектор числовых/категориальных признаков.

```
Видео "Мама с ребёнком, вопрос в первые 3 сек, быстрый монтаж, отзыв"
                              ↓
                   Multimodal LLM (Claude Vision / GPT-4V)
                   + Whisper (транскрипция) + Audio analysis
                              ↓
{hook_type: "question", has_face: true, pace: "fast",
 proof_type: "testimonial", emotion: "warm", duration: 30,
 subtitle_style: "large_bold", cta_text: "try_free", ...}
```

**Технология**: существующие мультимодальные LLM. Ничего не изобретаем — применяем готовое. Нужен промпт-инжиниринг + валидация (LLM может галлюцинировать атомы).

### 15.3. Слой 2: Модель по этапам воронки (ядро предсказания)

Три этапа воронки с разными likelihoods:

```
Конверсия (бинарные исходы → Binomial likelihood, logit link):

  logit(CTR)  = μ₀ + β₁×hook_type + β₂×has_face + β₃×pace + β₄×emotion
                   + β₅×cta_type + β₆×proof_type + β₇×duration
                   + γ×match_score + эффекты_сегмента
  клики ~ Binomial(показы, CTR)

  logit(CVR)  = μ₀ + β₈×headline_formula + β₉×social_proof_type
                   + β₁₀×offer_type + β₁₁×form_length + эффекты_сегмента
  конверсии ~ Binomial(клики, CVR)

Сумма чека (непрерывная → Lognormal likelihood):

  log(AOV)    = μ₀ + β₁₂×offer_type + β₁₃×urgency + ε

Диагностика (не входит в chain, но предсказывает CTR):

  logit(Hook Rate) = μ₀ + β_h₁×hook_type + β_h₂×has_face + β_h₃×pace + ...
  3sec_views ~ Binomial(показы, Hook Rate)
```

**Hook rate — диагностика, а не отдельный этап в произведении.** Раньше использовали `Revenue = Hook Rate × CTR × CVR × AOV`, но это двойной счёт: CTR уже определён на показы, Hook Rate тоже. Правильная цепочка:

```
Revenue per impression = CTR × CVR × AOV

На лог-шкале:
log(Revenue) = log(CTR) + log(CVR) + log(AOV)

Аддитивность на логах = мультипликативность в реальности
```

Hook rate — ранний сигнал для Gate 1 (когда кликов ещё мало) и предиктор CTR (корреляция). Он моделируется отдельно для ранней диагностики, но не входит в revenue chain.

**Почему logit + Binomial, а не log + Gaussian**: конверсии — дискретные бинарные события. На малых выборках log(0) не определён. Binomial likelihood с logit link — стандарт для бинарных данных в байесовской статистике, корректно работает при малых n.

**Овердисперсия — Beta-Binomial по умолчанию**: чистая Binomial предполагает независимые показы. В реальности есть дни недели, плейсменты, динамика доставки — дисперсия выше биномиальной. **Beta-Binomial используется по умолчанию** (добавляет параметр дисперсии). При отсутствии овердисперсии он вырождается в обычную Binomial (параметр дисперсии → 0), а при наличии — автоматически расширяет CI. Даже 1.3× биномиальной дисперсии при n≈80K заметно расширяет интервалы и предотвращает ложную уверенность. Альтернатива: **random effects «ad_set × день»** в иерархической модели.

**Связь hook rate → CTR → CVR**: сейчас модели по этапам независимы, и данные Gate 1 не обновляют оценку CTR/CVR. Правильнее: **латентные эффекты креатива** с оцениваемой корреляцией между этапами:

```
Креатив c имеет эффект:
  z_c[hook_rate]  ~ ...
  z_c[CTR]        ~ ...      ← положительная корреляция с hook rate (обычно)
  z_c[CVR]        ~ ...      ← может быть отрицательно коррелирован с CTR

Корреляционная матрица между z_c[hook], z_c[CTR], z_c[CVR] оценивается из данных.
```

Это даёт два бонуса: (1) раннее наблюдение за hook rate информирует оценку CTR, и (2) **отрицательная корреляция z_c[CTR] vs z_c[CVR] — сигнатура кликбейта** (высокий CTR, низкий CVR = обещание не совпадает с лендингом). Один общий фактор этого не ловит — нужны отдельные эффекты с оцениваемой корреляцией.

**Малые выборки**: корреляционная матрица 3×3 плохо оценивается при 9-30 креативах. Решение: **LKJ prior** (стандарт для корреляционных матриц в PyMC/Stan) + простое правило-детектор до оценки матрицы: если CTR креатива выше якоря, а CVR или bounce хуже якоря → подозрение на кликбейт, отметить и отслеживать.

Это позволяет **складывать эффекты атомов** и получать предсказание для комбинаций, которые **никогда не тестировались**.

**match_score** — явный признак на стыке "видео → лендинг". Рассогласование убивает CVR. Это **взаимодействие**, которое моделируем явно.

**Тип модели**: байесовская обобщённая линейная модель (GLM). Стандарт с 1970-х.

### 15.4. Слой 3: Байесовский слой (неопределённость)

Каждый коэффициент β — **не число, а распределение**:

```
β₁ (hook "вопрос") ~ Normal(μ=0.35, σ=0.05)   ← хорошо изучен, 50+ наблюдений
β₈ (headline "новая") ~ Normal(μ=0.10, σ=0.30)  ← 3 наблюдения, высокая неопределённость
```

Три суперсилы:
1. **Знаем, чему доверяем**: узкий σ = уверены; широкий σ = не знаем
2. **Новые атомы автоматически исследуются**: широкий σ → высокая дисперсия сэмплов Thompson → шанс на тест
3. **Shrinkage (сжатие к среднему)**: атом с 3 наблюдениями подтягивается к среднему по группе, не даёт шуму управлять решениями

**Иерархичность** (перенос между уровнями — три уровня partial pooling):

```
Уровень 3 (universal — все клиенты, все ниши):
  β_hook_вопрос_UNIVERSAL ~ Normal(0, σ²_universal_prior)
  → "что мы знаем о хуках-вопросах вообще, по всем нишам"

Уровень 2 (ниша — e-com, B2B, education):
  β_hook_вопрос_NICHE[ниша_k] ~ Normal(β_hook_вопрос_UNIVERSAL, σ²_between_niches)
  → "что мы знаем об этом хуке в конкретной нише"

Уровень 1 (клиент → аудитория):
  β_hook_вопрос[клиент_j] ~ Normal(β_hook_вопрос_NICHE[ниша_j], σ²_between_clients)
  β_hook_вопрос[аудитория_i] ~ Normal(β_hook_вопрос[клиент_j], σ²_between_audiences)
  → "что мы знаем для этого клиента / этой аудитории"
```

Механика partial pooling на каждом уровне:
- Новый клиент (мало данных) → подтягивается к нишевому среднему → cold start за дни, не месяцы
- Новая ниша (мало клиентов) → подтягивается к universal среднему → первый клиент в нише сразу получает полезный приор
- Зрелый клиент (много данных) → "отпускается" к собственной оценке → специфика продукта учтена

**Flywheel**: каждый новый клиент обновляет universal и niche уровни → все остальные клиенты (особенно новые) получают более точные приоры. Это **сетевой эффект на уровне данных** — data moat, который растёт с каждым клиентом. Подробнее см. §15.12.

**Тип модели**: иерархическая байесовская модель (3 уровня). Решается через PyMC / Stan / NumPyro.

### 15.5. Слой 4: Hurdle-модель для revenue

**Проблема**: 99% показов дают $0 revenue. 1% даёт покупку на разную сумму. Нормальное распределение не подходит.

**Hurdle = слой 2 (CTR × CVR) + слой чека (AOV)**. Это не отдельная модель, а объединение:

```
Revenue per impression = CTR × CVR × AOV

Где:
  CTR  — из Binomial GLM слоя 2 (logit link)
  CVR  — из Binomial GLM слоя 2 (logit link)
  AOV  — из Lognormal слоя 2

"Hurdle" = бинарный исход (купит/нет) + непрерывный (сколько)
```

Hurdle-модель разделяет "купит ли" и "сколько потратит" — два разных вопроса с разными драйверами:
- Скептик, убеждённый отзывами → купит, но дешёвый вариант
- Импульсивный покупатель с urgency → возьмёт дорогой

**Тип модели**: hurdle-модель (two-part model). Стандарт в страховании и медицине. Здесь оба компонента определены в слое 2 — слой 4 описывает *как они соединяются* в ожидаемый revenue.

### 15.6. Слой 5: Thompson Sampling для выбора действия

Адаптация из Sales-ai. Но вместо Beta(successes, failures) — **сэмплируем из апостериоров слоя 3**:

```
Для каждого кандидата:
  1. Сэмплируй все β из их апостериорных распределений
  2. Подставь атомы кандидата в формулы слоя 2
  3. Вычисли сэмплированный E[Profit per impression] через hurdle-модель
     Profit = Revenue × Margin − Cost_per_impression
     (см. §3.1: reward = profit per impression, не revenue)
  4. Выбери кандидата с наибольшим сэмплированным Profit

Повтори при каждом решении → разные сэмплы → разные выборы → exploration
```

**⚠️ Модель стоимости**: CPM зависит от креатива через аукцион Meta (качественные креативы получают ниже CPM). В MVP — наблюдаемый CPM per ad set. В Phase 4+ — отдельная модель log(CPM) = f(atoms) для полного предсказания profit до запуска.

Автоматический баланс explore/exploit: неизученные комбинации → высокая дисперсия → иногда "выигрывают" → получают тест.

### 15.7. Что существует vs что нужно строить

| Компонент | Статус | Что нужно |
|-----------|--------|-----------|
| Извлечение атомов (Creative DNA) | Готовые LLM (Claude Vision, GPT-4V, Whisper) | Промпт-инжиниринг + валидация |
| Bayesian GLM (logit + Binomial) | Учебник, PyMC/Stan | Настроить приоры под маркетинг |
| Hurdle-модель (Binomial × Lognormal) | Стандарт, PyMC | Имплементация + калибровка |
| Thompson Sampling | Уже реализован в Sales-ai | Адаптация: сэмплинг из регрессии вместо Beta |
| Иерархическая модель (transfer между аудиториями) | PyMC/Stan/NumPyro | Архитектура + convergence tuning |
| Модель взаимодействий атомов | BART / interaction terms | Feature selection |
| Модель выгорания (temporal decay) | Survival models (Cox PH) | Адаптация под маркетинг |
| Креативный эмбеддинг (Phase 6+) | VAE / contrastive learning | ML research |

**Вывод**: новые модели изобретать не нужно. Каждый компонент существует. Новизна — в комбинации и калибровке под маркетинг.

### 15.8. Четыре задачи для математиков/ML-специалистов

**Задача 1: Модель взаимодействий атомов** (средняя сложность, Phase 3-4)

Аддитивная модель предполагает: эффект хука одинаков при любом CTA. Не всегда так. Хук "шок" + CTA "гарантия" может работать лучше суммы (шок → тревога → гарантия снимает).

Подход: начать с аддитивной модели, добавлять interaction terms по Bayes factor. Или BART (Bayesian Additive Regression Trees) — находит взаимодействия автоматически.

**Задача 2: Модель выгорания** (средняя сложность, Phase 4-5)

Предсказать, **когда** креатив выгорит. Время жизни как функция от: начального ROAS, Frequency, типа аудитории, сезона.

Подход: survival model (Cox Proportional Hazards или Bayesian survival). Хорошо изучены в медицине/страховании — адаптация, не изобретение.

**Задача 3: Перенос знаний между аудиториями** (средне-высокая сложность, Phase 3-5)

Хук работает для "мам 25-35". Будет ли для "мам 35-45"? Иерархическая модель с partial pooling.

Концептуально проста, но трудна в оптимизации (convergence issues в MCMC). Нужен человек с опытом PyMC/Stan.

**Задача 4: Эмбеддинг "креативного пространства"** (высокая сложность, Phase 6+)

После сотен тестов: непрерывное пространство, где похожие по эффективности креативы расположены рядом. "Сгенерируй похожий, но для другой аудитории" = перемещение в пространстве.

Подход: VAE или contrastive learning. Это ML research. Не для MVP.

### 15.11. Стадии усложнения модели

```
Phase 1-2 (MVP):
  Слой 1: LLM извлекает атомы (промпт-инжиниринг)
  Слой 2: Простая байесовская регрессия по атомам (одна аудитория)
  Слой 3: Независимые приоры (без иерархии)
  Слой 4: Простая Binomial для конверсии
  Слой 5: Thompson Sampling из Sales-ai
  → Уже полезно: фильтрация очевидных лузеров

Phase 3-4 (рабочая модель):
  + Иерархия по аудиториям (partial pooling)
  + Hurdle-модель (Binomial × Lognormal)
  + Interaction terms (задача 1)
  + Модель выгорания (задача 2)
  + LightGBM как второе мнение (ensemble)
  → Целевое: precision@5 значимо выше случайного выбора
    (если базовая доля прохождения Gate 3 = 40%, то precision@5 > 65%
     = +25 п.п. lift; если базовая 20%, то precision@5 > 45%)
    и rank correlation > 0.5
    (⚠️ ГИПОТЕЗА — измерить в MVP через A/B: модель vs случайный выбор)

Phase 5-6 (зрелая система):
  + Перенос между аудиториями (задача 3)
  + Контекстный бандит (признаки сессии → выбор лендинга)
  + Uplift-моделирование
  → Персонализация в реальном времени

Phase 7+ (research):
  + Креативный эмбеддинг (задача 4)
  + Генерация креативов направляемая моделью
  + Автоматическое обнаружение новых атомов
  → Система генерирует и оценивает сама

Universal Cross-Niche Model (нарастает параллельно):
  Phase 0.5:  Сбор агрегированных паттернов поведения + нишевые бенчмарки
  Phase 1-2:  Universal prior = простые red flags (bounce, micro-конверсии)
              + нишевые бенчмарки CTR/CVR; early kill за 50-100 визитов
  Phase 3-4:  + Двухуровневая иерархия universal → niche → client
              + Кросс-клиентский бандит по атомам (статистика атомов по всей платформе)
              + Информированные приоры для exploration (§6.4)
  Phase 5-6:  + Трёхуровневый partial pooling (universal → niche → client → audience)
              + Embedding поведенческих сессий (кросс-нишевый)
              + Feature store агрегированных паттернов (решает приватность)
  Phase 7+:   + Мета-обучение (learn to learn): после нескольких тестов модель адаптируется
              + Кросс-канальный universal prior
              → Каждый новый клиент усиливает модель для всех = data moat
```

### 15.12. Universal Cross-Niche Model (кросс-нишевая модель)

#### 15.12.1. Проблема: cold start — главная боль системы

Все расчёты §20 показывают: первые 1-2 месяца ценность минимальна. Клиент платит $3K/мес и получает +8% ROAS в первый месяц ($4.7K доп. прибыли) — это **неотличимо от шума**. Клиент не чувствует ценность → риск churn.

Причина: модель начинает с нуля. Слабый приор, широкая неопределённость, нужны тысячи сессий.

#### 15.12.2. Решение: единая модель, обученная на данных всей платформы

**Идея**: вместо того чтобы каждый клиент начинал с нуля, существует **общая ИИ-модель**, которая:
- Обучена на агрегированных данных десятков/сотен клиентов из разных ниш
- Накопила универсальные паттерны поведения пользователей
- По ранним сигналам (50-100 визитов) определяет: связка "креатив + лендинг" рабочая или мёртвая
- С каждым новым клиентом становится точнее для всех остальных

#### 15.12.3. Трёхуровневая иерархия

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  Уровень 3: UNIVERSAL PRIOR                                    │
│  Обучен на агрегированных данных всех клиентов                 │
│  Знает: универсальные паттерны поведения, базовые бенчмарки,   │
│  "красные флаги" мёртвых связок, сигнатуры кликбейта          │
│  → Даёт сильный приор для нового клиента с первого дня        │
│                                                                 │
│  Уровень 2: NICHE MODEL                                       │
│  Обучен на данных клиентов из одной ниши                       │
│  Знает: бенчмарки ниши, специфику цикла решения,              │
│  какие атомы работают в этой нише, нормы CVR/CTR              │
│  → Уточняет приор для ниши клиента                            │
│                                                                 │
│  Уровень 1: CLIENT MODEL                                      │
│  Обучен на данных конкретного клиента                          │
│  Знает: специфику продукта, аудитории, бренда                 │
│  → Уточняет приор для этого конкретного клиента               │
│                                                                 │
│  Механика: partial pooling (shrinkage) на каждом уровне        │
│  Мало своих данных → тянет к niche/universal                   │
│  Много своих данных → "отпускается" к собственной оценке       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

Математически это естественное расширение иерархической модели из §15.4 — добавляется ещё один уровень сверху. Не новая модель, а расширение существующей.

#### 15.12.4. Универсальные паттерны, которые переносятся между нишами

Некоторые закономерности **не зависят от ниши** и могут быть выучены на больших объёмах:

| Паттерн поведения | Что означает | Универсальность |
|-------------------|-------------|-----------------|
| Клик на креатив → bounce < 3 сек | Message mismatch: обещание ≠ реальность | Работает везде |
| Быстрый скролл к цене → долгий hover → уход | Цена не совпала с ожиданием из креатива | E-com, SaaS, education, B2B |
| Глубокий скролл, чтение отзывов, возврат через день | Скептик, сравнивает с конкурентами | Работает везде |
| Прямой путь к CTA без скролла | Горячий лид, уже решил | Работает везде |
| Прочитал FAQ → заполнил форму | Нужно было снять конкретное возражение | Работает везде |
| Высокий CTR + высокий bounce | Кликбейт (креатив обещает лишнее) | Работает везде |

**⚠️ Не все паттерны универсальны.** Нишевые различия существенны:

| Аспект | E-commerce | B2B SaaS | High-ticket |
|--------|-----------|----------|-------------|
| Цикл решения | Минуты | Недели-месяцы | Месяцы |
| CVR бенчмарк | 2-5% | 0.5-2% | 0.1-0.5% |
| "Быстрый уход" = | Мёртвая связка | Возможно скачал whitepaper | Вернётся позже |

Поэтому модель **обязана знать нишу** и иметь нишевый уровень иерархии. Universal prior — это не "всё одинаково", а "что одинаково, а что нет".

#### 15.12.5. Два типа быстрых предсказаний

**Тип 1: "Kill быстро" (50-100 визитов) — применимо к лендингам на нашем сайте**

**⚠️ Scope**: ранний kill по 50-100 визитам корректен для **лендингов**, где мы контролируем рандомизацию трафика. Для **креативов в Meta** первые клики — исследование доставки Meta, и сам документ требует 2-3 суток до Gate 1 (§12.3). Universal model для креативов ценна **ранжированием до запуска** и **предсказанием исхода Gate 3 по ранним сигналам**, а не ранним kill.

Модель определяет **заведомо мёртвые связки лендингов** по ранним сигналам (эвристики до валидации, не жёсткие правила):

**⚠️ Пороги — относительные, не фиксированные.** Фиксированный порог "bounce >70% на 50 визитах" убьёт нормальную связку в ~23% случаев, если реальный bounce 65% (биномиальный шум). Правильный подход:
- Порог = z-score от **нишевого бенчмарка × плейсмент × устройство** (не абсолютное число)
- Решение по **апостериорной вероятности**: kill если P(bounce > нишевый_порог | данные) > 0.90
- **Калибровка на логах**: измерять FPR (false positive rate) на исторических данных; целевой FPR < 5%
- До накопления нишевых бенчмарков — честно называть red flags **эвристиками** (не "правилами")

Сигналы для раннего kill:
- Bounce значимо выше нишевого бенчмарка для данного плейсмента/устройства
- Нулевые микроконверсии (ни одного клика по CTA при 100+ визитах)
- Паттерн "кликбейт" (высокий CTR + мгновенный уход)
- Средний скролл значимо ниже нишевого бенчмарка

Сравнение со staged gates: Gates 1-2 (§12.3) уже убирают проигравшего за ~$50-300 (при CPM $10 и CPC $0.4). Universal model экономит **$50-100 на креатив** (ранний kill лендинга до Gate 2), а не $500-2000. Основная ценность — **калиброванное предсказание исхода Gate 3** по ранним сигналам и **ранжирование кандидатов до запуска**. Метрика успеха: calibration + AUC на логах, а не "убили за $20".

**Тип 2: "Scale с уверенностью" (200-500 визитов, $80-200)**

Модель подтверждает **рабочие связки** и прогнозирует ROAS:
- Сравнение с нишевым бенчмарком (из universal/niche levels)
- Bayesian updating с сильным приором → быстрее сходится
- Прогноз по микроконверсиям (до финальной конверсии)

Без universal: 1000+ сессий для уверенного решения. С universal: 200-500 (в 3-5 раз быстрее).

**⚠️ Реалистичные ожидания**: определить рабочую связку по 5-10 кликам невозможно даже с идеальной моделью (при n=10 доверительный интервал конверсии = 0.3%-44%). 50-100 визитов — реалистичный минимум для kill-решения.

#### 15.12.6. Flywheel-эффект (data moat)

```
Клиент 1   → данные → модель чуть точнее
Клиент 10  → модель уже неплохая → cold start быстрее
Клиент 100 → модель сильная → ценность с первого дня
Клиент 1000 → модель = конкурентное преимущество, невозможное к копированию
```

Каждый новый клиент **усиливает модель для всех остальных** — сетевой эффект на уровне данных. Конкурент может скопировать архитектуру, но не может скопировать 1000 клиентов × 6 месяцев данных.

Это превращает SaaS-инструмент в **платформу**.

#### 15.12.7. Приватность и data sharing

**Фундаментальное требование**: модель учится на **агрегированных паттернах**, не на сырых данных клиентов.

✅ Допустимо: "в нише e-commerce bounce rate < 40% коррелирует с прохождением Gate 2 в 87% случаев"
❌ Недопустимо: "у клиента А конверсия 4.2% на лендинге с таймером"

Юридические вопросы:
- GDPR/CCPA: агрегированные паттерны (не персональные данные) — допустимо, но нужна юридическая проверка
- Конкуренты в одной нише: модель, обученная на данных A, не должна утекать к B — решается агрегацией + **минимальный размер агрегата ≥5 клиентов** (иначе нишевый "бенчмарк" фактически раскрывает данные конкурента)
- Договор с клиентом: явное согласие на использование агрегированных данных для обучения общей модели — **с клиента №1**

**⚠️ КРИТИЧНО — Meta Platform Terms (ПРОВЕРИТЬ В ПЕРВОИСТОЧНИКЕ, см. §25 п.19):**

По стороннему пересказу Meta Advertising Policies, смешивание данных кампаний нескольких рекламодателей перечислено среди ограничений. Это напрямую касается universal model. **Два класса данных с разным уровнем риска:**

| Класс данных | Источник | Риск | Пример |
|-------------|---------|------|--------|
| **First-party события сайта** | Наш код на лендинге | **Низкий** — это наши данные, собранные на наших сайтах | Bounce, скролл, микроконверсии, время на блоках |
| **Данные из Meta Marketing API** | Meta API | **Высокий** — возможно подпадает под ограничения Platform Terms | CTR, hook rate, CPM, CPC, impressions, конверсии из API |

**Безопасный путь (MVP)**: universal model строится **только на first-party событиях** (bounce, scroll depth, CTA clicks, micro-conversions). Нишевые бенчмарки CTR/CPM из Meta API — только после юридической проверки.

**Решение**: feature store агрегированных паттернов — хранит статистики, не сырые данные. Формулировки вроде "Hook type X работает в 73% случаев" корректнее заменить на **размеры эффектов из иерархической модели** (effect size + credible interval), а не сырой win-rate, который смешивает качество клиента и качество приёма.

#### 15.12.8. Влияние на exploration (связь с §6.4)

Universal model **не уменьшает** exploration, а **повышает его КПД**:

| Аспект | Без universal | С universal |
|--------|--------------|-------------|
| На что тратится exploration budget | На всё подряд, включая известные провалы | На реально неизвестные территории |
| Скорость kill-решения по лузерам | 300+ кликов (Gate 2) | 50-100 визитов (early kill) |
| Сэкономленный бюджет от быстрого kill | — | Направляется на **ещё больше** exploration |
| Качество новых кандидатов | Случайные рекомбинации | Ранжированы кросс-нишевым опытом |

Thompson Sampling исследует пропорционально **неопределённости**. Universal model снижает неопределённость на известных паттернах → exploration концентрируется на реально новых идеях. Подробнее см. §6.4.

#### 15.12.9. Влияние на экономику (связь с §20)

**⚠️ Baseline = система со Staged Gates (§12.3), но без universal model.** Staged Gates уже снижают стоимость kill-решения с $2000+ (полный тест до learning phase) до $50-300. Universal model даёт **инкрементальную** экономию поверх этого — ранний kill лендинга до Gate 2, ранжирование до запуска, ускорение cold start.

| Метрика | Без universal (но со Staged Gates) | С universal |
|---------|--------------------------------------|------------------------|
| Время до первого полезного инсайта | 2-4 недели | 1-3 дня |
| Время до надёжной предфильтрации | 3-4 месяца | 2-4 недели |
| Стоимость kill-решения (лендинг) | $50-300 (Gate 1-2, §12.3) | $20-50 (ранний kill, §15.12.5) |
| Стоимость kill-решения (креатив) | $50-300 (Gate 1-2) | ~$50-300 (те же ворота, но кандидаты ранжированы → меньше провалов) |
| ROAS в первый месяц | +8% | +12-18% (⚠️ гипотеза) |
| Клиент чувствует ценность | Месяц 2-3 | Неделя 1-2 |

**⚠️ Цифры "с universal" — экспертные гипотезы.** Реальные значения зависят от количества клиентов в платформе и качества агрегированных данных. Первые 5-10 клиентов не получат существенного преимущества — flywheel начинает работать после ~20-30 клиентов в нише. Оценка ROAS скорректирована с +15-20% до +12-18% — экстраполяция от +8% базового с учётом более сильного приора, а не радикально иного механизма.

#### 15.12.10. Что нужно строить (техническая реализация)

| Компонент | Назначение | Фаза |
|-----------|-----------|------|
| Feature store агрегированных паттернов | Хранит нишевые бенчмарки и универсальные паттерны, не сырые данные | Phase 0.5 |
| Red flags детектор | Ранний kill по универсальным паттернам (bounce, micro-конверсии) | Phase 0.5 |
| Нишевые бенчмарки | CTR, CVR, bounce, scroll depth — по нишам из данных платформы | Phase 1-2 |
| Кросс-клиентская иерархическая модель | Расширение §15.4 до 3 уровней partial pooling | Phase 3-4 |
| Embedding поведенческих сессий | Превращает сырой поток событий в вектор "профиля сессии", обучается кросс-нишево | Phase 5-6 |
| Юридическая модель data sharing | Согласие клиентов, разделение агрегированных и сырых данных | Phase 0.5 |
| Taxonomy Alignment Layer | Единая таксономия атомов через embedding-кластеры (не жёсткие текстовые категории) | Phase 1-2 |

#### 15.12.11. Taxonomy Alignment Layer (защита от дрейфа таксономии)

**Проблема**: атомы извлекает LLM (§4.2). Со временем LLM может по-разному тегировать одни и те же сущности у разных клиентов или в разные месяцы (taxonomy drift). "hook_question" у клиента A ≠ "hook_rhetorical_question" у клиента B, хотя это один и тот же приём. Результат: матрица признаков разреженная, shrinkage не стягивает нужные узлы, universal model деградирует.

**Решение**: вместо жёстких текстовых категорий — embedding-based alignment:

1. LLM извлекает атом → текстовое описание + embedding (e.g. sentence-transformers)
2. Embedding ищет ближайший кластер в **глобальном реестре атомов платформы**
3. Если cosine similarity > порога → привязка к существующему глобальному ID
4. Если ниже → создаётся новый кластер (кандидат), подтверждается после N повторных появлений
5. Периодическая рекалибровка: пересчёт кластеров, слияние дрейфующих дублей

**Инфраструктура**: vector store (pgvector в PostgreSQL или отдельный Qdrant/Pinecone). Размер невелик — тысячи атомов, не миллионы. Основная сложность — порог слияния: слишком агрессивный = теряем гранулярность, слишком мягкий = не решаем проблему.

#### 15.12.12. Synthetic Persona Sandboxing (пре-тестирование на синтетической аудитории)

**Гипотеза**: перед запуском реальных тестов в Meta прогнать сгенерированные креативы и лендинги через LLM-based Persona Agents, эмулирующих целевую аудиторию клиента.

**Как работает**:
1. На основе CRM-истории, отзывов и Ad Library данных платформа строит набор синтетических персон (e.g. "скептичный инженер-закупщик", "CFO с бюджетным давлением", "технический директор-новатор")
2. LLM-агенты оценивают варианты хуков/офферов с позиции каждой персоны: релевантность, доверие, вероятность клика
3. Заведомо провальные комбинации отсеиваются до реального запуска (сужение пространства поиска)
4. В тестовый контур (§6.5) попадают только top-кандидаты с высоким синтетическим потенциалом

**⚠️ Критическое ограничение — обязательная A/B валидация:**
Синтетические оценки НЕ заменяют реальные тесты и не являются доказательством эффективности. LLM-персона не знает, как реальный человек скроллит ленту в 7 утра.

**Протокол запуска (Phase 3+)**:
- Первые 3 месяца — **A/B тест самого метода**: 50% кампаний запускаются с синтетическим пре-фильтром, 50% — без (полный пул кандидатов в Thompson Sampling). Измеряем: (а) cost-to-find-winner, (б) ROAS победителей, (в) процент ложных отсевов (креатив отфильтрован синтетикой, но сработал бы в реальности)
- Если A/B не покажет статистически значимого преимущества пре-фильтра — модуль отключается
- Если покажет — калибруем порог отсечения по реальным данным, а не по LLM-уверенности
- Синтетический скоринг логируется, но **не блокирует** запуск в реальный тестовый контур до подтверждения A/B результатов

**Связь с Universal Model (§15.12)**: синтетические персоны инициализируются из нишевых приоров universal model (не с нуля). Это потенциально улучшает качество эмуляции для ниш с большим объёмом накопленных данных.

## 16. Feedback Loop с продажами (B2B / High-ticket)

Если есть отдел продаж:
- Лид уходит в CRM → менеджер закрывает / не закрывает → **обратная связь** в систему
- "Этот лид — мусор" vs "Закрылся на $50K" — корректирует ROAS в реальности, а не по proxy
- Без этого система оптимизирует **количество заявок**, а не **выручку**
- Отложенная обратная связь (цикл продажи = недели/месяцы) → промежуточные сигналы (SQL, MQL, Opportunity) как временная награда

### 16.1. Proxy Value Bidding (критично для B2B)

**Проблема**: Meta Value Optimization требует ~100 конверсий с ценностью за 7 дней. В B2B (цикл сделки = месяцы) событие "Closed Won $50K", отправленное через 45 дней, Meta почти проигнорирует — алгоритм оптимизирует под конверсии первых 24-72 часов.

**Решение**: многоступенчатая отправка ценности в Meta через CAPI по мере подтверждения качества лида. Не одноразовое предсказание, а **эскалация value** при каждом событии качества:

```
Конкретная цепочка для B2B клиента (гидрогели, GoHighLevel CRM):

Форма (день 0)
    → CAPI: НЕ отправляем (ещё не подтверждённый лид)
    → Thompson: ждём (ни α, ни β не обновляем)

Ответил на звонок (день 1-2, GHL call tracking)
    → CAPI: Purchase(value = proxy_low) — сигнал Meta "этот лид живой"
    → Thompson: partial reward (α += 0.3)

Пришёл на встречу (день 3-7, GHL appointment.completed / Google Calendar)
    → CAPI: Purchase(value = proxy_high) — ключевой сигнал качества
    → Thompson: full reward (α += 1.0)
    → Это ОСНОВНОЕ событие качества для данного клиента

Сделка закрыта (день 30-90, GHL opportunity.won)
    → CAPI: Purchase(value = deal_value) — финальная коррекция
    → Thompson: revenue_mu обновляется реальной суммой

Не ответил + не пришёл (7 дней без ответа)
    → CAPI: ничего (пиксель НЕ загрязняется мусорным лидом)
    → Thompson: β += 1.0 (failure)
```

**Почему "пришёл на встречу" — ключевое событие**: (а) происходит через 3-7 дней (в окне Meta-оптимизации 24-72 часа → 7 дней), а не через 30-90 дней как закрытие сделки; (б) сильно коррелирует с итоговой конверсией (кто пришёл на встречу — серьёзный покупатель); (в) наблюдаемо автоматически через GHL/Google Calendar (не зависит от ручной квалификации менеджером).

**Источники данных**: GoHighLevel отправляет webhook `appointment.completed` и call tracking events. Если GHL не отслеживает факт присутствия (только назначение) — дополнительно интегрируем Google Calendar API для проверки статуса встречи.

**Калибровка**: еженедельно сверять предсказанные значения с реальными исходами из CRM. Если модель систематически завышает — Meta будет переплачивать за трафик. Обязательна A/B проверка: когорта с proxy value vs когорта с фиксированным value.

## 17. Multi-Touch Attribution

### 17.1. Проблема

Воронка не линейная. Пользователь видит 3-5 рекламных касаний разных типов (видео, карусель, stories, ретаргетинг) прежде чем кликнуть и купить.

### 17.2. Реалистичные ограничения

**Полную пользовательскую MTA построить нельзя**: Meta не отдаёт путь по показам (impression-level data). Мы видим только клик→конверсию, а не "пользователь видел 5 объявлений до клика".

### 17.3. Что реально можно сделать

- **First-party данные**: UTM, creative ID в URL, события на сайте — это наше и мы контролируем
- **Incrementality tests**: holdout-группы ("показываем рекламу всем кроме 10%") — золотой стандарт причинного вывода
- **Meta Experiments API**: встроенные A/B тесты с контрольными группами
- **Markov / Shapley по first-party путям**: для тех касаний, которые мы видим (клики, email, retargeting)
- **Geo-Lift testing (Phase 5+)**: для Enterprise-клиентов с достаточным geographic scale — отключить рекламу в гео A (контроль), оставить в сопоставимом гео B (тест), измерить причинный инкремент по данным продаж клиента (не пикселя). Алгоритм: CausalImpact (Google) или синтетический контроль. Самый надёжный метод incrementality, но требует объёма (достаточный трафик/продажи в каждом гео)
- **Честное признание шума**: атрибуция между показами — оценка, не факт. Система должна показывать credible intervals

**Phase 7+: Bayesian Media Mix Modeling (MMM) при мульти-канальном масштабировании.**
При подключении Google/TikTok/YouTube (§23 Phase 7) цифровая атрибуция каждой платформы будет конфликтовать (каждая over-claims последнюю конверсию). Решение: Bayesian MMM с инкрементальными priors, объединяющий быстрые digital-сигналы (MTA) с медленными, но причинными Geo-Lift результатами (§17.3). Модель строит кривые насыщения медиа-эффектов (diminishing returns per channel) для оптимального распределения бюджета между каналами. Инструменты: Meta Meridian / Google LightweightMMM / собственная реализация на PyMC. ⚠️ Проектирование — при планировании Phase 7 (не раньше): архитектура MMM зависит от набора подключённых каналов, а данные для calibration требуют 6-12 месяцев мультиканальной работы.

## 18. Message-Market Fit — мета-уровень

### 18.1. Проблема

Вся система предполагает: продукт/оффер фиксирован, оптимизируем креативы. Но иногда проблема — в **самом предложении**.

### 18.2. Измеримый критерий

Message-market fit определяется количественно через апостериорные вероятности (не точечные оценки, которые на малых выборках — шум):

- **Основной критерий**: P(хотя бы один вариант выше breakeven ROAS) < 10% — то есть с 90% уверенностью ничего не работает
- **Малый разброс между вариантами**: межвариантная дисперсия из иерархической модели мала (атомы не объясняют разницу → проблема не в креативе)
- Если оба условия выполнены → проблема в оффере, не в креативе

### 18.3. Дополнительные сигналы

Система должна уметь диагностировать:
- "Все креативы для аудитории X дают CPA выше порога" → проблема не в креативе, а в оффере для этой аудитории
- "Высокий CTR, высокий bounce rate по ВСЕМ лендингам" → продукт не соответствует ожиданиям
- "Конверсии есть, но LTV низкий / возвраты высокие" → привлекаем не тех

### 18.4. Действие

Система формулирует рекомендации маркетологу:
- "Для аудитории X рекомендуем изменить оффер (текущий не конвертирует при любом креативе)"
- "Рассмотрите изменение ценообразования для сегмента Y"
- Это **стратегический инсайт**, выходящий за рамки тактической оптимизации креативов

### 18.5. Dynamic Offer Explorer — систематический поиск рабочего оффера

**Когда §18.2 диагностирует "проблема в оффере"** → система не просто говорит "измените оффер", а генерирует **конкретные альтернативы** из суб-атомов (§4.3a):

```
Диагностика §18.2: P(ROAS > breakeven) < 10% при ЛЮБОМ креативе для аудитории "мамы 25-35"
                    + межвариантная дисперсия мала → проблема в оффере

Dynamic Offer Explorer генерирует кандидатов:
├── Текущий оффер:     скидка 10% + без гарантии + полная оплата
├── Альтернатива A:    без скидки + money-back 30 дней + полная оплата
│   (гипотеза: аудитории нужна гарантия, а не скидка)
├── Альтернатива B:    без скидки + без гарантии + рассрочка 3 мес
│   (гипотеза: барьер — единовременная сумма)
├── Альтернатива C:    бесплатная доставка + бонус-консультация
│   (гипотеза: perceived value важнее скидки)
└── Ранжирование: кросс-нишевой опыт (§15.12) → "рассрочка работает в 73% случаев
    для high-ticket в этой нише" → Альтернатива B первая в очереди на тест
```

**Связь с моделью**: суб-атомы оффера — обычные признаки в Bayesian GLM (§15.3). Dynamic Offer Explorer = LLM-генератор кандидатов (аналог §14 для офферов вместо креативов) + ранжирование через Thompson Sampling.

**Ограничения (жёсткие):**
- **Margin floor** (§4.3a): варианты ниже минимальной маржи не участвуют в тесте
- **Антикондиционирование**: система не должна приучать аудиторию ждать скидку. Если "скептикам" всегда давать скидку — все станут "скептиками" (§7.4)
- **Персональные цены юридически рискованны** в ряде юрисдикций (§7.4) — система тестирует офферы на уровне сегментов, не индивидов
- Финальный оффер **утверждается маркетологом** (§12.4 — уровень "Советник")

### 19.1. Основные затраты системы

| Генерация лендингов (LLM) | $0.02-0.10 / вариант |
| Видео-рендер (compute) | $0.50-2.00 / видео |

**Per-visitor (почти бесплатные):**

| Компонент | Приблизительная стоимость |
|-----------|--------------------------|
| Thompson Sampling inference | ~0 (CPU, микросекунды) |

**Фиксированные:**

| Компонент | Приблизительная стоимость |
|-----------|--------------------------|
| Инфраструктура (hosting, DB, streaming) | $500-2000 / мес |

**Вывод**: дорогие — мультимодальный разбор и рендер видео (per-creative), а не per-visitor. Real-time scoring практически бесплатен.

### 19.2. При каком бюджете система работает (вывод из первых принципов)

Ограничение Meta: один ad set должен получить **~50 событий оптимизации за 7 дней**, иначе "Learning Limited".

```
Минимальный бюджет = CPA × 50 событий/нед × кол-во ячеек × 4 недели

Ячейки: тестовые креативы + 2 якоря + staged gates (3 ворот) + scale-контур
```

Реальный подсчёт зависит от стадии. На старте (Phase 2-3) нужно меньше ячеек:

| Стадия | Ячейки | CPA $10 (лидген) | CPA $40 (e-com) | CPA $100 (B2B) |
|--------|--------|-------------------|------------------|----------------|
| Минимум (3 креатива + 2 якоря) | 5 | ~$10K/мес | ~$40K/мес | ~$100K/мес |
| Полный тест (9 креативов + 2 якоря) | 11 | ~$22K/мес | ~$88K/мес | ~$220K/мес |

**Нижняя граница зависит от CPA ниши и события оптимизации**, а не фиксированная. Если бюджет мал — можно оптимизировать на событие выше по воронке (add to cart вместо purchase), но нужно проверять, что оно предсказывает покупку (и что набирает 50+ событий/нед).

**Дополнительный расход**: подтверждающий прогон перед переносом в scale-контур (§6.5) идёт в новом ad set и требует ещё ~CPA × 50. Формула выше — только тестовый контур.

| Сегмент | Бюджет/мес | Наша роль |
|---------|------------|-----------|
| Ниже порога learning phase | < $8K | Только аналитика (Phase 1), без автооптимизации |
| Базовый | $8K-40K | Аналитика + генерация + советник |
| Основной | $40K-150K | Полный цикл с полуавтопилотом |
| Premium | $150K+ | Автопилот с выделенным онбордингом |

**⚠️ Сегменты зависят от CPA ниши**, а не только от бюджета. При CPA $100 (B2B) минимальный тест = $100K/мес, поэтому клиент с $40K попадает в "Базовый" даже если по бюджету мог бы быть "Основной". Практическое правило: `макс. ячеек ≈ бюджет / (CPA × 200)`. Если ячеек < 5 — **автооптимизация в Meta невозможна** (мало данных для staged gates), но аналитика, генерация лендингов и советник по-прежнему доступны (= уровень "Базовый").

## 20. Value Proposition — Unit Economics и экономия клиента

### 20.1. Для чего строится система

Не "автоматизировать маркетинг". **Сократить цену обучения.**

Каждый доллар, потраченный на проигравший креатив — это плата за информацию "это не работает". Сейчас эта информация стоит $2,000+ (минимум 50 конверсий × CPA). Наша система делает информацию дешевле:

| Способ получения информации | Стоимость |
|----------------------------|-----------|
| Без системы: тест до learning phase | $2,000+ на креатив |
| Предсказание модели (фильтрация до запуска) | $0 прямых, но есть opportunity cost (ложноотрицательные) |
| Staged Gate 1 (hook rate, ~5-8K показов) | ~CPM×5-8 (зависит от CPM ниши) |
| Staged Gate 2 (CTR + Landing, ~300+ кликов) | ~CPC×300 (зависит от CPC ниши) |
| Персонализация лендинга | Не стоит денег — увеличивает отдачу с того же трафика |

### 20.2. Что именно предсказывает модель

Система **не предсказывает точный ROAS конкретного креатива** (слишком много переменных, 55-65% точности). Она предсказывает, какие **атомы** работают для каждой аудитории, и фильтрует заведомо слабых кандидатов **до траты денег**.

| Предсказание | Требования к данным | Ожидаемая точность |
|-------------|---------------------|-------------------|
| "Этот **тип хука** не работает для аудитории X" | 30-50 протестированных креативов | 75-85% |
| "Этот **лендинг** лучше конвертит скептиков" | 1,000+ сессий с поведенческими данными | 70-80% |
| "Из 20 кандидатов тестировать **эти 5**" | 100+ протестированных атомов | 70-80% (ранжирование) |
| "Этот посетитель ищет цену — покажи прайс первым" | 3-5 действий в текущей сессии | 70-80% |
| "Этот конкретный креатив даст ROAS > 3.0" | Любой | 55-65% (ненадёжно) |

Точность растёт с объёмом данных. На холодном старте модель = слабый приор. После 6 месяцев = устойчивый фильтр.

### 20.3. Модель расчёта: клиент $50K/мес, CPA $40

#### Допущения (консервативные)

| Параметр | Значение | Обоснование |
|----------|---------|-------------|
| Бюджет клиента | $50,000/мес | Основной сегмент |
| Текущий blended ROAS | 2.5 | Хороший средний уровень для Meta |
| Маржинальность продукта | 50% | Типично для e-commerce |
| Стоимость системы | $3,000/мес | Гибрид: base + % от spend |

#### Текущее распределение бюджета (без системы)

Бюджет $50K — не весь одинаково эффективен:

```
Top 20% бюджета ($10K) — лучшие креативы:     ROAS 5.0 → $50,000 выручки
Mid 50% бюджета ($25K) — средние креативы:     ROAS 2.5 → $62,500 выручки
Bot 30% бюджета ($15K) — лузеры + тесты:      ROAS 0.8 → $12,000 выручки
─────────────────────────────────────────────────────────────────────────
Итого:                                         ROAS 2.49 → $124,500 выручки
```

#### Четыре эффекта системы

**Эффект 1 — Waste reduction (перераспределение от лузеров к победителям)**

Предфильтрация + staged gates сокращают Bottom с 30% до 10% бюджета. Высвобожденные $10K перераспределяются в top и mid.

```
Без системы: $15K × 0.8 = $12,000 выручки от лузеров
С системой:  $5K × 0.8 = $4,000 выручки от оставшихся тестов
Высвобождено $10K → уходит в top/mid (средний ROAS ~3.5)
Дополнительная выручка: $10K × (3.5 − 0.8) = +$27,000
```

**Эффект 2 — CVR lift от персонализации лендингов**

Конкретному посетителю — конкретный лендинг. К месяцу 6 lift ~18% CVR. Применяется к ~80% трафика (остальное — контрольная группа + необработанный).

```
Базовая выручка после эффекта 1: $124,500 + $27,000 = $151,500
CVR lift: $151,500 × 0.80 × 0.18 = +$21,816
```

**Эффект 3 — Быстрее к победителю (compound)**

Победитель найден за 2 недели вместо 4 → 2 доп. недели масштабирования.

```
Дополнительная выручка: ~$4,700/мес
```

**Эффект 4 — Улучшение креативов через обучение атомов**

Каждое поколение лучше предыдущего. К месяцу 6 средний уровень mid-tier поднимается на ~10%.

```
Mid-tier: $25K × 2.5 × 0.10 = +$6,250
```

**⚠️ Таблица B — экспертные гипотезы, не расчёт.** Ключевая разница: кривая обучения сдвигается на ~2 месяца влево (месяц 1 с universal ≈ месяц 3 без). Точные цифры зависят от зрелости универсальной модели. Для первых 5-10 клиентов платформы таблица B неприменима — они ближе к таблице A.

Рост замедляется после месяца 6 — основные эффекты реализованы, дальше тонкая настройка.

### 20.5. Конвертация ROAS → ROI

ROAS — маркетинговая метрика (выручка / расход). ROI — бизнес-метрика (прибыль / расход).

```
ROI = (Выручка × Маржа − Расходы) / Расходы × 100%
Расходы = Ad Spend + Стоимость системы
```

| Период | ROAS | Выручка | Маржа 50% | Расходы ($50K+$3K) | Прибыль | **ROI** |
|--------|------|---------|-----------|--------------------|---------| --------|
| **Без системы** | 2.50 | $125,000 | $62,500 | $50,000 | $12,500 | **25.0%** |
| Месяц 1 | 2.69 | $134,400 | $67,200 | $53,000 | $14,200 | **26.8%** |
| Месяц 3 | 3.10 | $154,700 | $77,350 | $53,000 | $24,350 | **45.9%** |
| **Месяц 6** | **3.69** | **$184,250** | **$92,125** | **$53,000** | **$39,125** | **73.8%** |
| **Месяц 12** | **3.91** | **$195,200** | **$97,600** | **$53,000** | **$44,600** | **84.2%** |

### 20.6. Ключевые цифры роста ROI

```

ROI к месяцу 6:     74%    ← рост ×2.95 (почти в 3 раза)
ROI к месяцу 12:    84%    ← рост ×3.37

Абсолютный рост ROI:   +49 п.п. к месяцу 6,   +59 п.п. к месяцу 12
Относительный рост:     +195% к месяцу 6,       +237% к месяцу 12

ROAS без системы:   2.50
ROAS к месяцу 6:    3.69   ← +48%
ROAS к месяцу 12:   3.91   ← +57%
```

### 20.10. Допущения и ограничения расчёта

**⚠️ ВСЕ ЦИФРЫ В §20 — ЭТО СЦЕНАРИЙ, НЕ ПРОГНОЗ.** Расчёт выше — базовый (оптимистичный) сценарий. Три варианта:

| Параметр | Нулевой | Пессимистичный | Базовый | Оптимистичный |
|----------|--------|----------------|---------|---------------|
| CVR lift от персонализации | 0-2% | 8% | 18% | 25% |
| Доля waste (Bottom tier) | 30% → 25% | 20% → 12% | 30% → 10% | 35% → 8% |
| Маржинальный ROAS перераспределённого бюджета | 1.5 | 2.0 | 3.5 | 4.0 |
| Предфильтрация: precision@5 lift vs random | 0 | +10 п.п. | +20 п.п. | +35 п.п. |
| ROAS к месяцу 6 | ~2.55 (+2%) | ~3.0 (+20%) | ~3.7 (+48%) | ~4.0 (+60%) |
| Доп. прибыль за год | **−$19K** (система не окупается) | ~$80K | ~$247K | ~$350K |

**Нулевой сценарий — это минус, а не ноль.** Расчёт: waste снижается на 5% = $2.5K высвобождено × маржинальный ROAS 1.5 → $1.75K доп. выручки + CVR lift ~1% ≈ $1K → суммарно ~$2.75K выручки → **~$1.4K доп. прибыли/мес** (маржа 50%). Система стоит $3K/мес → **убыток ~$1.6K/мес ≈ −$19K/год**. Это аргумент за привязку оплаты к результату: при фиксированной цене клиент в нулевом сценарии платит за ничто.

**⚠️ Сценарии написаны экспертно, не рассчитаны из параметров калькулятором.** В продукте нужен калькулятор, который выводит ROAS/прибыль из входных параметров (CVR lift, waste %, маржинальный ROAS), чтобы сценарии были воспроизводимы и настраиваемы.

**Как измерить реальный эффект**: встроить в продукт рандомизированный контроль — часть бюджета/трафика работает "как раньше". Это измеряет инкрементальный эффект и делает реальной модель ценообразования "% от подтверждённой экономии".

**Что учтено в базовом:**
- Кривая обучения (эффекты не мгновенны)
- Стоимость системы ($3K/мес)

**Что НЕ учтено (upside):**
- Экономия времени маркетолога (ручной анализ → автоматический; десятки часов/мес)
- Улучшение LTV: персонализация привлекает более качественных клиентов
- Снижение возвратов: Quality Score фильтрует кликбейт → более качественный трафик
- Cross-sell/upsell на основе поведенческих профилей
- Знания, переносимые между кампаниями (атом X работает → используем в новом продукте)

**Главные риски завышения:**
- Маржинальный ROAS < среднего (diminishing returns, §8.4). Перенаправление $10K в лучшие кампании даёт не ROAS 3.5, а меньше — эффект 1 завышен
- Эффекты 1 (waste reduction) и 3 (speed to winner) частично перекрываются
- Предфильтр "стоит $0" не учитывает opportunity cost: ложноотрицательные (ошибочно отсеянные победители) — это скрытая цена, увеличивающая реальный waste
- Реальный CVR lift может быть 8-12% вместо 18% (зависит от ниши). Источник "бенчмарка 15-25%" не верифицирован
- Не все лузеры фильтруются (модель может пропускать нестандартные провалы)
- Сезонность искажает кривую обучения
- Meta может изменить правила (Advantage+, privacy), что повлияет на часть эффектов
- Базовый ROAS 2.5 предполагает, что клиент не оптимизирует вручную (часть waste снимается обычными правилами без ИИ)

### 20.11. Ценообразование (ориентир)

На основе unit economics:

| Модель | Формула | Pros | Cons |
|--------|---------|------|------|
| **% от экономии** | 15-25% от подтверждённой экономии | Выровнены интересы; клиент платит за результат | Сложно считать; нужен рандомизированный контроль |
| **% от ad spend** | 3-7% от рекламного бюджета | Просто; масштабируется | Не привязан к ценности; в нулевом сценарии клиент платит за ничто |
| **Flat SaaS** | $1,000-5,000/мес по тиру | Предсказуемый cashflow | Не масштабируется с ценностью |
| **Гибрид с привязкой к результату (рекомендуемая)** | $500 base + 20% от подтверждённой дельты прибыли | Минимум для нас + выровнены интересы; клиент не платит за ничто в нулевом сценарии | Нужен встроенный рандомизированный контроль для измерения дельты |

**Почему привязка к результату**: нулевой сценарий (§20.10) показывает убыток −$19K/год при фиксированной цене. Привязка к дельте решает это: клиент платит $500 base (≈себестоимость инфра), а переменная часть возникает только при подтверждённом эффекте.

Пример для клиента $50K: base $500 + 20% × $26.6K доп. прибыли = ~$5.8K/мес к месяцу 6. В нулевом сценарии: $500/мес (только аналитика). **Стоимость $3K/мес в расчётах §20.3-§20.8 — это среднее за первый год по базовому сценарию.**

К месяцу 6 доп. прибыль ≈ $26.6K/мес ($39.1K с системой − $12.5K без, по таблице §20.5). Это **дешевле, чем один проигравший тест**.

## 21. Explainability — объяснимость на человеческом языке

### 21.1. Зачем

Маркетолог должен **понимать** решения системы, а не верить на слово. Это и доверие, и обучение, и контроль.

### 21.2. Принцип: статистика модели, не LLM-пересказ

**Критически важно**: объяснения должны строиться **из реальной статистики модели** (credible intervals, effect sizes, sample sizes, Thompson posterior parameters), а НЕ из свободного пересказа LLM. Иначе получается красивая постфактум-рационализация, которая выглядит убедительно, но может не соответствовать тому, что модель "думает".

LLM используется только для **форматирования** числовых данных в читаемый текст, не для интерпретации.

Пример (каждая строка — из статистики модели, чисто байесовский):

```
"Масштабируем видео #7 для аудитории 'Мамы 25-35':
 → Hook rate: 12.3% [95% credible interval: 12.07%–12.53%]
   (медиана аккаунта: 8.8%, n=82,000 показов — CI узкий, данных много)
 → CTR: 1.5% [95% credible interval: 1.42%–1.58%]
   (1,230 кликов из 82,000 показов)
 → Лендинг #3: scroll depth 68% vs 41% у #2
   (n=340 сессий, P(#3 лучше #2) = 0.97)
 → CVR: 3.8% [95% credible interval: 2.8%–5.0%]
   (n=47 конверсий из 1,230 кликов, α=48, β=1184)
 → CPA: $12.40 [95% credible interval: $9.30–$16.90]
 → P(видео #7 — лучший вариант в группе) = 0.78
 → Frequency: 1.4 (порог выгорания для этой ниши: ~2.8, выучен по истории)"
```

**Замечание**: α и β в Thompson Sampling для конверсии = successes+1 и failures+1. При 47 конверсиях из 1,230 кликов: α=48, β=1184.

**⚠️ CI в примере — биномиальные (нижняя граница ширины)**. В реальности дисперсия выше (овердисперсия: дни недели, плейсменты, динамика доставки). При Beta-Binomial или random effects интервалы будут шире, особенно для impression-level метрик. Не стоит приучать маркетологов к узким CI — это ложная уверенность. Правило «убить при P < 10%» калибровать по реальной, а не биномиальной дисперсии.

### 21.3. Автоматические отчёты

- **Еженедельный**: что работает, что выгорело, что запущено, ключевые инсайты
- **По запросу**: пост-мортем по любому креативу/кампании
- **Алерты**: аномалии, достижение порогов, рекомендации к действию

### 21.4. What-If Simulator — интерактивный симулятор решений (Phase 3+)

Превращает дашборд из пассивного отчёта в **инструмент стратегического планирования**.

**Как работает**: маркетолог видит текущие апостериоры Thompson Sampling и может менять параметры в интерфейсе:

| Вопрос маркетолога | Что делает система | Техническая реализация |
|-------------------|-------------------|----------------------|
| "Что если увеличить бюджет тестового контура на 50%?" | Прогоняет сэмплирование через предиктивную бюджетную кривую (§8.4) | Monte Carlo: sample N раз из текущих апостериоров × новый бюджет → коридор profit/ROAS |
| "Что если отключить хук-тип «вопрос»?" | Пересэмплирует без этого атома | Обнулить weight атома → re-rank оставшихся → показать новый прогноз |
| "Что если добавить рассрочку в оффер?" | Прогноз эффекта нового суб-атома (§4.3a) | Posterior predictive из иерархической модели: P(CVR↑) и E[profit change] с credible interval |
| "Сколько нужно потратить, чтобы определить победителя?" | Калькулятор мощности (§24) с текущими параметрами | Bayes Factor / expected posterior precision при заданном n |

**Стоимость реализации**: низкая — система уже сэмплирует из апостериоров для Thompson Sampling. Симулятор = тот же сэмплинг с изменёнными входными параметрами + визуализация коридоров.

**Ценность**: колоссально повышает доверие к автопилоту (маркетолог видит, что система "думает", а не чёрный ящик) и снижает churn.

### 21.5. System vs. Baseline Benchmark — доказательство эффективности (Phase 2+)

**Проблема**: главный страх CMO при покупке AI-решения — "а вдруг Meta и так бы всё это продала?". Без контрольной группы доказать ценность системы **невозможно**.

**Решение**: платформа постоянно держит **3-5% трафика на "дефолтном" управлении** — без персонализации лендингов, без динамического выбора Thompson Sampling, статичный лендинг.

```
┌──────────────────────────────────────────────┐
│  95-97% трафика: полная оптимизация          │
│  Thompson Sampling + персонализация +        │
│  динамические офферы                         │
├──────────────────────────────────────────────┤
│  3-5% трафика: контрольная группа            │
│  Статичный лендинг, без оптимизации          │
│  = baseline "как было бы без системы"        │
└──────────────────────────────────────────────┘
```

**Еженедельный отчёт**: "Благодаря алгоритму за этот месяц вы заработали на $X больше (+Y%), чем заработали бы на статичном сайте. P(система лучше baseline) = 0.98."

**Toggleable (по умолчанию ON):**
- **ON (рекомендуется)**: 3-5% holdout. При $50K/мес и CPA $200 = ~12 конверсий/мес в контроле. Потеря пренебрежима (система на 95% трафика зарабатывает больше, чем 100% без оптимизации), но **доказательство ROI бесценно** для retention и upselling
- **OFF (по запросу клиента)**: для клиентов с очень малым трафиком или после 6+ месяцев доказанного lift. При отключении — предупреждение: "вы теряете объективное доказательство ROI системы"
- **Рекомендация**: первые 3-6 месяцев — всегда ON. Это самый мощный аргумент для продления контракта

**Связь с §7.4**: "контрольная группа 5-10% со стандартным опытом" уже заложена. Benchmark формализует это как **продуктовую фичу** с отчётом для клиента.

## 22. Риски верхнего уровня

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Корреляция vs причинность (Meta delivery bias) | Высокая | Ложные выводы | Holdout-группы, Meta Experiments, изолированные тесты в тестовом контуре |
| Мало данных на ячейку | Высокая | Шум вместо сигнала | Атомизация, аддитивная байесовская модель, минимум данных перед решением |
| Сброс Learning Phase | Высокая | Деградация Meta delivery | Двухконтурная структура, новые креативы — в новый ad set, не в живой |
| Конфликт двух оптимизаторов | Высокая | Деградация Meta delivery | Чёткое разделение: тестовый контур (мы) + scale контур (Meta CBO) |
| Бан рекламного аккаунта | Низкая | Катастрофа | Compliance checker + предзапусковая сверка обещаний vs факты о продукте |
| Creative burnout | Средняя | Рост CPA | Детектор выгорания + якорный креатив + автозамена |
| Кликбейт-оптимизация | Средняя | Урон бренду | Profit-based objective (включая возвраты) + Quality Score как опережающий |
| Сезонность / внешние шоки | Высокая | Ложные решения | Якорный креатив + одновременное сравнение + модуль внешних сигналов |
| Temporal lag (возвраты через недели) | Высокая | Кликбейт получает бюджет | Staged gates + Quality Score + пересчёт reward по финалу |
| Winner's curse при переносе в scale | Высокая | Откат к среднему | Shrinkage в иерархической модели + подтверждающий прогон |
| Права на музыку в видео | Средняя | Страйк / блокировка | Библиотека royalty-free + автопроверка перед рендером |
| Маркировка AI-контента в рекламе Meta | Средняя | Отклонение / бан | Сверить с текущими требованиями Meta к AI-generated content (⚠️ ПРОВЕРИТЬ) |
| Права на людей в кадре (image rights) | Средняя | Юридический иск | Model releases для всех лиц в футажах, автодетекция лиц при монтаже |
| Event quality (dedup, EMQ) | Высокая | Ad set застревает в learning | Дедупликация pixel+CAPI по event_id, мониторинг EMQ |
| Описательное ≠ причинное (Phase 1) | Высокая | Ложные выводы | Phase 1 = гипотезы, причинные выводы только после тестового контура |
| Universal model: ложный перенос между нишами | Средняя | Вредные приоры для нового клиента | Нишевый уровень иерархии + partial pooling "отпускает" к своим данным при накоплении (§15.12) |
| Universal model: утечка данных между конкурентами | Низкая | Юр. иск, потеря доверия | Агрегированные паттерны, не сырые данные; явное согласие в договоре (§15.12.7) |
| Universal model: cold start самой universal модели | Высокая (первые месяцы) | Первые 5-10 клиентов не получают преимущества | Flywheel начинает работать после ~20-30 клиентов в нише; до этого — таблица A из §20.4 |
| Технический сбой сайта клиента (500, упавший шлюз) | Средняя | Система тратит бюджет на рекламу сломанного сайта; ложная диагностика «креативы не работают» | Site Health Guard: HTTP health check + синтетический мониторинг + автопауза рекламы (§11.4) |
| Отказ от cookies (GDPR consent) искажает данные | Высокая (20-40% в EU) | Неперсонализированные сессии засчитываются как провалы, модель недооценивает эффект персонализации | CMP-интеграция: раздельный учёт consent/no-consent сессий (§12.1a) |
| IP-нарушение в генерируемом контенте (ТМ, лица, музыка) | Низкая-средняя | Юридический иск, бан аккаунта, репутационный урон | Двухуровневая проверка: автоматическая (LLM + face detection) + ручной апрув маркетолога (§12.1a) |
| Бот-трафик и клик-фермы отравляют модель | Средняя-высокая | Модель оптимизирует под ботов: раздутый CTR + нулевая конверсия → ложный диагноз "плохой лендинг"; якоря загрязнены → не отличить фрод от рыночного шока | 4 слоя: Edge-фильтрация (Cloudflare/reCAPTCHA), поведенческий фильтр, аномалии в воронке, очистка данных модели (§12.6) |
| Каскадный провал бюджета без финансовых предохранителей | Средняя | Автопилот сжигает бюджет при серии неудачных тестов; потеря доверия клиента | Financial Circuit Breaker: L1 per-creative → L2 per-campaign → L3 per-account + gradual ramp-up (§12.5a-b) |
| Эрозия маржи при автоматическом тестировании офферов | Низкая-средняя | Система увеличивает скидки ради CVR, юнит-экономика нарушается | Жёсткий margin floor в модели; reward = profit (не revenue); маркетолог задаёт минимальную маржу (§4.3a) |
| Meta API rate limit блокирует Circuit Breaker | Средняя (растёт с числом клиентов) | При rate limit ошибке 17/613 система не может отправить команду паузы; бюджет тратится бесконтрольно 15-60 минут | Priority queue (§10.3): P0 вызовы резервируют 10% квоты; Meta Automated Rules как независимый fallback (§12.5a) |
| Компрометация OAuth-токенов клиентов | Низкая | Злоумышленник получает доступ ко всем рекламным аккаунтам и бюджетам | Vault/KMS + RLS + минимальные OAuth scopes + ротация токенов каждые 60 дней + audit log (§12.7) |
| Кросс-девайсный разрыв: bounce на мобильном = на самом деле конверсия с десктопа | Средняя-высокая | Модель недооценивает эффективность mobile-first креативов; ложные bounce искажают байесовские оценки | Identity resolution при микро-конверсии (email → crm_user_id); ретроспективная коррекция bounce (§7.4) |
| Переполнение хранилища видео-ассетов при масштабировании (Phase 4+) | Средняя | 81+ вариаций × десятки клиентов = терабайты; обычные диски/PostgreSQL не справятся | S3-compatible object storage + lifecycle policy: hot→cold→delete (§23 Phase 4, §26.5) |
| Taxonomy drift атомов между клиентами/временем | Средняя (растёт с количеством клиентов) | LLM по-разному тегирует одни и те же приёмы → разреженная матрица, shrinkage ломается, universal model деградирует | Taxonomy Alignment Layer: embedding-кластеры атомов с глобальными ID вместо текстовых категорий (§15.12.11) |
| Auction bias при тестировании офферов на креативах | Высокая | Meta показывает креативы с разными офферами разным сегментам → сравнение confounded | Тестировать офферы на лендингах (наш контроль), не на креативах; auction bias = known confound (§4.3a) |
| Конвергенция хуков в одной нише (tragedy of the commons) | Средняя (растёт с числом клиентов) | Universal model рекомендует одинаковые топ-хуки всем клиентам ниши → аудитория видит одинаковую рекламу → ускоренный burnout у всех; конкуренты в одной нише «убивают» эффективность друг друга | **Niche Creative Entropy Index**: embedding-based diversity metric (cosine similarity через §15.12.11) детектирует семантическую конвергенцию даже при разных формулировках; Diversity Penalty в Thompson Sampling при entropy ниже порога; rotation policy (не более N% клиентов используют семантически близкие хуки одновременно); «свободный слот» в брифе (§5.5) для уникальных идей |
| Скрытый «токсичный» трафик: высокая конверсия, но массовый churn/возврат | Средняя-высокая (особенно в B2B) | Креатив создаёт завышенные ожидания → покупатели возвращают товар через 30-90 дней или лид не закрывает сделку; система не видит post-purchase исход и продолжает масштабировать проблемный креатив | Delayed Churn Penalty (§6.7): CRM webhook по churn/refund → ретроспективный штраф на атомы; окно 90-180 дней для B2B; cap 30% на пересчёт |
| Запаздывание реакции на конкурентные действия | Средняя | Конкурент запускает агрессивный оффер/хук, забирает долю аудитории; без мониторинга система узнаёт об этом только по падению собственных метрик (дни/недели задержки) | Reactive Competitive Intelligence (§9.1): автодетекция в Ad Library + контр-гипотезы + alert маркетологу; human approval перед деплоем |
| Загрязнение пикселя некорректной кампанией | Средняя-высокая (особенно B2B с малыми объёмами) | Пиксель оптимизирует доставку под нецелевой профиль; все последующие кампании деградируют; "перетренировка" пикселя необратима без создания нового | 3 уровня: CAPI Quality Gate (фильтрация по CRM-качеству лида), Multi-Pixel изоляция (test/primary/product), автодетекция drift (§6.8) |

## 23. Порядок разработки (предлагаемый)

```
Phase 0 — Фундамент (параллельно со всем)
├── **Server-Side First** (обязательно): Server-Side GTM (sGTM) или собственный
│   server-side proxy для сбора событий. Pixel = fallback/дедупликация, не primary
│   source. Без серверного сбора iOS ATT + ad-blockers теряют 30-40% событий
│   → CAPI получает неполные данные → Bayesian модель обучается на biased выборке
├── Трекинг: Marketing API, CAPI (server-side events → Meta), события лендинга, CRM
├── Единый ID события (без этого ничего не работает)
├── Качество событий: дедупликация sGTM+CAPI по event_id, контроль EMQ
│   (недоучтённые события держат ad set в learning + Meta не может использовать конверсии)
├── Сбор поведенческих данных: СЫРОЙ ПОТОК событий (каждый скролл, hover, клик с таймстемпом)
│   НЕ агрегаты — пересчитать задним числом нельзя
├── Версионирование схемы событий (schema registry)
├── Propensity logging: для КАЖДОГО решения логировать кандидатов, вероятности выбора,
│   контекст. Без этого бэктест (off-policy evaluation), uplift и причинный анализ
│   невозможны — наивный replay предвзят
├── Якорные креативы (2 шт.) в аккаунте в тех же пачках и на тех же аудиториях
│   что тестовые ячейки (для детекции рыночных шоков, решение по статпорогу)
├── **Fraud Protection** (§12.6): Edge-фильтрация (Cloudflare Bot Management / reCAPTCHA Enterprise)
│   + поведенческий фильтр сессий + пометка suspicious sessions → исключение из модели
│   (без этого данные загрязнены с первого дня)
├── **Базовый Financial Circuit Breaker** (§12.5a L1): per-creative stop-loss
│   + месячный budget ceiling на уровне аккаунта
├── **Pixel Pollution Protection** (§6.8): Multi-Pixel architecture (primary/test/product)
│   + CAPI Quality Gate (отправка только подтверждённых CRM конверсий)
└── Инфраструктура: минимально-достаточная (для MVP не нужен полный feature store
    и streaming — см. §24)

Phase 0.5a — Universal Prior: подготовка (начинается до первых клиентов)
├── Юридическая модель data sharing: согласие клиентов на агрегированные данные
│   ✅ агрегаты (в нише X bounce <40% → Gate 2 в 87%) ❌ сырые данные клиента
├── Проверка Meta Platform Terms (§25 п.19): можно ли агрегировать данные из API
│   кросс-клиентски? Если нет — universal model только на first-party событиях
├── Нишевая таксономия: определить группировку клиентов по нишам (§25 п.16)
│   Слишком грубо = шум, слишком гранулярно = мало данных
└── Шаблоны договоров с явным пунктом об использовании агрегированных данных

Phase 0.5b — Universal Prior: реализация (параллельно с первыми клиентами, см. §15.12)
├── Feature store агрегированных паттернов (не сырые данные — агрегаты)
│   Хранит: нишевые бенчмарки, универсальные red flags, статистики атомов
├── Red flags детектор: ранний kill мёртвых связок за 50-100 визитов ($20-50)
│   Пороги — относительные, не фиксированные (z-score от нишевого бенчмарка, §15.12.5)
├── Нишевые бенчмарки (CTR, CVR, bounce, scroll depth) из данных платформы
├── Трёхуровневая иерархия приоров: universal → niche → client
│   (расширение §15.4; новый клиент получает сильный приор с первого дня)
└── Flywheel: каждый клиент обновляет universal и niche уровни

    (эффект заметен после ~20-30 клиентов в нише)

Phase 1 — "Мозг аналитики" (ценен сам по себе, без генерации)

├── ОПИСАТЕЛЬНАЯ диагностика + гипотезы (НЕ причинные выводы!
│   Это наблюдательные данные с Meta delivery bias = наш риск №1.
│   Причинные выводы возможны только после тестового контура в Phase 3)

└── **Скелет Creator Brief** (§5.5): шаблонный бриф для контент-мейкеров

├── Message Match с креативами
├── Event-разметка блоков
├── A/B тестирование на сайте (наш контроль, нет конфликта с Meta)
```

## 24. MVP — минимальный тонкий срез

**Предлагаемый MVP** (Phase 0 + Phase 1 описательная + Phase 2 + Томпсон на сайте):

```
MVP scope:
├── Трекинг + event quality + propensity logging (Phase 0, упрощённый)
├── Базовая фрод-защита: Edge-фильтрация + поведенческий фильтр (Phase 0, §12.6)
├── Per-creative stop-loss + месячный budget ceiling (Phase 0, §12.5a L1)
├── Multi-Pixel support + CAPI Quality Gate (Phase 0, §6.8)
├── CMP-интеграция: раздельный учёт consent/no-consent сессий (Phase 0, §12.1a)
├── Описательная аналитика загруженных креативов (Creative DNA, Phase 1)
├── Скелет Creator Brief: шаблонный бриф для контент-мейкеров (Phase 1, §5.5)
├── Генерация лендингов из конструктора (Phase 2)
├── Thompson Sampling для выбора лендинга на сайте (наш контроль)
└── Dashboard с байесовской статистикой
```

**Почему именно этот срез:**
- На сайте — **полный контроль**, нет конфликта с Meta
- Граф решений из Sales-ai ложится напрямую на выбор лендинга
- Thompson Sampling — ~100 строк кода, тяжёлая часть (мультимодальность, uplift, видео) не нужна для MVP
- Ценность для клиента с первого дня: "какой лендинг лучше конвертирует и почему"
- Всё остальное (видео-монтаж, Meta API интеграция, персонализация, предсказания) наращивается итеративно
- Фрод-защита и stop-loss с первого дня — данные чистые, бюджет защищён
- Скелет Creator Brief снижает порог входа для контент-мейкеров до Phase 4 (data-driven версия)

**Калькулятор мощности (обязательно в MVP)**:
Система должна уметь ответить "данных недостаточно для решения". Оценка минимального трафика:
```
При CVR 3% и цели увидеть прирост +20%:
n ≈ 16 × p(1−p) / δ² ≈ 13,000 посетителей на вариант (правило Лера)
4 варианта ≈ 52,000 посетителей
При CPC $0.40 ≈ $20,000 на тест

Thompson Sampling эффективнее (меньше трафика на проигравших),
но порядок величины тот же. Честный ответ "мало данных" > ложная уверенность.
```

**Инфраструктура MVP** — минимальная. НЕ нужен полный feature store и streaming на старте. Достаточно: БД для событий, простой API для Томпсона, конструктор лендингов, dashboard, калькулятор мощности.

**Tech stack MVP** — открытый вопрос (см. §25). Сам Томпсон переносить из Java необязательно: это ~100 строк, а тяжёлая часть (ML) живёт в Python-экосистеме.

## 25. Открытые вопросы для следующей сессии

### Стратегические
1. **Целевая ниша**: ~~универсальный инструмент или вертикальное решение?~~ **РЕШЕНО (v1.9.3)**: Стратегия **Vertical-First Flywheel** — начинаем с одной вертикали (B2B industrial/cosmetic ingredients, первый клиент — гидрогели), набираем 20-30 клиентов в нише для разгона Universal Model (§15.12), затем расширяемся. ⚠️ Нишу для модели определяем шире, чем "гидрогели": **"B2B manufacturing with long sales cycle"** — полимеры, косметические компоненты, промышленная химия. Иначе flywheel не наберёт 20-30 клиентов в ультра-узкой суб-нише
2. **Бизнес-модель**: SaaS ($X/мес) или % от рекламного бюджета / % от улучшения ROAS?
3. **MVP scope**: согласны ли с предложенным тонким срезом в §24?

### Технические
4. **Tech stack**: Python (ML) + Next.js (UI)? Или монолит? Java из Sales-ai или переписываем?
5. **Видео-генерация**: FFmpeg + скрипты или Remotion (React-based, дороже но гибче)?
6. **Хостинг моделей**: собственный inference или API (Claude / GPT-4V для Vision)?
7. **Cross-pollination**: если SaaS — можно ли анонимизированно использовать данные одного клиента для другого? → **Ответ в §15.12.7**: да, через агрегированные паттерны (не сырые данные). Нужна юридическая проверка и явное согласие в договоре

### Universal Cross-Niche Model (§15.12)
15. **Порог flywheel**: при скольких клиентах в нише universal model начинает давать заметное преимущество? Гипотеза: ~20-30 клиентов, но нужно верифицировать
16. **Нишевая таксономия**: как группировать клиентов по нишам? Грубо (e-com/B2B/education) или гранулярно (e-com→fashion, e-com→supplements)? Слишком грубо = шум, слишком гранулярно = мало данных на нишу
17. **Embedding поведенческих сессий**: обучать свою модель или использовать готовые (session replay tools)? Своя = лучше контроль, но нужен ML-инженер
18. **Метрика качества universal model**: как измерить, что кросс-нишевый приор реально помогает? Предложение: A/B на уровне клиентов (новый клиент с universal prior vs новый клиент с flat prior)

### Требуют проверки по документации Meta (⚠️)
8. **Learning Phase reset** — ✅ ЧАСТИЧНО ПРОВЕРЕНО: Help Center включает добавление объявлений в список "significant edits", но тесты Джона Лумера показали, что одно новое объявление в большом ad set (22 шт.) learning не перезапустило. **Вывод**: формулировку «сбрасывает» заменить на «может сбросить»; логировать статус learning до и после каждого запуска. Порог ~50 событий за 7 дней подтверждён. Рост бюджета > ~20% и пауза > 7 дней тоже сбрасывают.
9. **Conversion Lift** — ✅ ПРОВЕРЕНО: Meta делит аудиторию случайно на тестовую и контрольную, рекламодатель задаёт долю контроля и длительность. **Ключевое**: измеряет "реклама vs без рекламы", НЕ "система vs как раньше". A/B-сравнение креативов внутри Meta **не чисто причинное** (delivery bias между ветками, подтверждено исследованием авторов из Meta и университетов). Наш рандомизированный контроль для измерения эффекта системы должен быть **на уровне сайта** (наш контроль), а не через Meta Conversion Lift.
10. **Personal Attributes policy**: точные формулировки и ограничения для таргетинга — прочитать напрямую
11. **AI-generated content** — ✅ ПРОВЕРЕНО: метка "AI info" ставится автоматически по C2PA метаданным; для фотореалистичных AI-людей метка заметнее. Июнь 2025: Meta добавляет информацию к объявлениям от сторонних AI-инструментов. **Вывод**: AI-контент в рекламе разрешён с меткой, но строгость enforcement неясна. Прочитать Meta Transparency Center напрямую перед запуском.
12. **Advantage+ audience** — ✅ ПРОВЕРЕНО: кастомные аудитории = **подсказки** (suggestions), Meta может показывать за их пределами. Жёсткие ограничения только: география, языки, мин. возраст, исключения, особые категории. Ограничить кастомные аудитории до жёсткого таргета можно **только выключив Advantage+**. Для нашей системы: сегменты → Meta = подсказки, а не гарантия доставки. На сайте — полный контроль.
13. **Музыка в рекламе**: правила Meta и ответственность рекламодателя — не проверено
14. **Концентрация показов** — ✅ ПРОВЕРЕНО ПРАКТИКАМИ: алгоритм Meta склонен отдавать большую долю бюджета 1-2 объявлениям. В 2025 Meta выпустила **Creative Testing tool** — закрепляет долю бюджета за новыми объявлениями внутри существующего ad set. **Это альтернатива изолированным ad sets из §12.3.** Нужно проверить: (а) доступен ли через API, (б) насколько тест в нём чистый (bias от существующих объявлений в том же ad set).

### ⚠️ Критичные для Universal Model (§15.12)
19. **Meta Platform Terms и смешивание данных рекламодателей** — ⚠️ НЕ ПРОВЕРЕНО, P0. По стороннему пересказу Advertising Policies, использование данных рекламодателя ограничено агрегированным и анонимным видом, а смешивание данных кампаний нескольких рекламодателей может быть запрещено. **Проверить в первоисточнике**: Advertising Policies, Platform Terms, Business Tools Terms. Вопрос: можно ли обучать общую модель на данных кампаний из Marketing API, даже агрегированных? **Различие, которое может спасти план**: first-party события сайта (bounce, scroll, micro-конверсии) = наши данные → скорее безопасно. CTR/CPM/hook rate из Meta API → рискованнее. См. §15.12.7.
20. **Meta Invalid Click Rate через API** — ⚠️ НЕ ПРОВЕРЕНО. В §12.6.2 слой 4 упоминает интеграцию с Invalid Click Rate через API. Подтверждения программного доступа в официальной документации Marketing API не найдено. Проверить.
21. **Ad Library API: доступные метрики** — ⚠️ ЧАСТИЧНО ПРОВЕРЕНО. Ad Library отдаёт креативы и срок жизни объявления. Для политической рекламы — диапазоны расходов и показов. Для коммерческой — **нет CTR, кликов, конверсий, hook rate**. Ссылки на "hook rate конкурента" в §5.5.2 некорректны (исправлено в v1.9).
