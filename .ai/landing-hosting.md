# Где живёт лендинг: домен клиента, изоляция от блокировок, трекинг

**Дата:** 2026-10-21 · **Статус:** решение принято, реализация — roadmap Phase 10 (10-1…10-4)
**Связано:** `.ai/meta-api-policy.md` (стадии записей в Meta), `.ai/architecture.md` §6 (поток «клик → лендинг»), §11 (CORS, HTTPS)

---

## 1. Вопрос

Система собирает лендинг. Маркетолог должен увидеть варианты и выбрать. После выбора лендинг должен
где‑то «развернуться». Если у клиента проблемы с рекламным аккаунтом, Meta не должна зацепить наш домен,
наш IP и остальных клиентов. При этом трекинг, Thompson Sampling и формы должны работать как раньше.
Можно ли, чтобы лендинг **физически** был на сервере клиента?

Короткий ответ: **да, можно, и это не ломает трекинг**. Ниже — что именно блокирует Meta, три режима
размещения и какой из них когда выбирать.

---

## 2. Что на самом деле блокирует Meta

| Объект | Блокирует ли Meta | Что это значит для нас |
|---|---|---|
| **Домен в объявлении** (URL назначения) | Да. Это основной уровень: домен попадает в блок‑лист, любое объявление с ним отклоняется | Один общий домен `go.наш.com/l/slug` на всех клиентов = один инцидент гасит всех. **Домен должен быть у каждого клиента свой.** |
| **Рекламный аккаунт, Business Manager, страница** | Да, это уровень эскалации | Решается политикой записей (`meta-api-policy.md`) и compliance, не хостингом |
| **Пиксель / CAPI‑датасет** | Может ограничить при «загрязнении» | У каждого клиента свой пиксель (уже так: `meta_pixels`, маршрутизация §5.4 capabilities) |
| **IP‑адрес сервера** | **Нет**, как правило. Meta оценивает URL/домен и контент, а не IP хостинга; иначе были бы заблокированы все Shopify, Vercel, Cloudflare | Общий IP у нескольких клиентов сам по себе не риск. Но у клиента может быть **свое** требование (безопасность, комплаенс, «наш сайт только на нашем сервере») |
| **Контент страницы** (crawler Meta ходит по URL) | Да: обещания дохода, cloaking, несоответствие объявлению | Compliance‑проверки и probe‑модерация (capabilities §7.3–7.5) |

Вывод: защиту даёт **отдельный домен на клиента** и чистый контент. Физический сервер клиента — это
дополнительный уровень изоляции и ответ на организационные требования, а не требование Meta.

---

## 3. Три режима размещения

Все три используют одни и те же варианты, блоки, Thompson Sampling и события. Разница — кто отдаёт HTML и
по какому адресу.

### Режим A — платформенный хост (сейчас, для внутреннего использования)

```
https://go.наш.com/l/{slug}  →  наш Next.js  →  наш API / ML / БД
```

Ничего настраивать не нужно. Подходит, пока клиент — мы сами. Минус: общий домен.

### Режим B — домен клиента по CNAME (Phase 10-3)

```
DNS клиента:   invest.client.com   CNAME  landings.наш.com
               _mai-verify.invest.client.com  TXT  "<token>"
```

- Клиент добавляет домен в кабинете (Settings → Landing domains), платформа выдаёт token и целевой CNAME,
  кнопка **Verify** проверяет TXT и CNAME по DNS.
- Middleware Next.js смотрит на `Host`: платформенный хост = админка, чужой хост = только лендинги этого
  тенанта (`/l/{slug}` сверяется с tenant домена, `/` → `default_slug`, всё остальное 404).
- CORS для API формируется из таблицы `tenant_domains` (только VERIFIED), статический список остаётся
  для платформенных хостов.
- TLS: Cloudflare for SaaS (custom hostnames) или Caddy с on‑demand TLS перед Next.js — оба умеют выпускать
  сертификат на чужой домен по CNAME. Решение по TLS — на этапе выкладки в прод, код от него не зависит.

Что даёт: Meta видит домен клиента; блок одного домена не трогает остальных; пиксель и события — first‑party
для этого домена (cookie не теряются, ATT/ad‑block бьют меньше). Сервер физически наш.

### Режим C — раннер на сервере клиента (Phase 10-4)

```
Сервер клиента:   docker compose -f docker-compose.runner.yml up -d
                  https://invest.client.com  →  landing-runner (Next.js, тот же образ)
                                                   │  outbound HTTPS only
                                                   ▼
                                            https://api.наш.com
                                              /public/l/{slug}?host=…   (варианты, блоки)
                                              /public/decide            (выбор варианта, X-Runner-Key)
                                              /events, /public/form/submit, /public/reward
```

- Тот же контейнер фронтенда, запущенный в режиме `LANDING_RUNNER=1`: админка выключена, есть только `/l/*`.
- У раннера **нет** ключа ML‑сервиса, нет доступа к БД, нет секретов Meta. Есть один `RUNNER_KEY`, выданный
  в кабинете на конкретный домен (`runner_keys`, хранится hash). Ключ отзывается одной кнопкой.
- Решение «какой вариант показать» раннер получает через `POST /public/decide` на нашем API; API сам
  ходит в ML (`/decide/landing`). Снаружи ML не виден.
- События, формы, награды идут с браузера посетителя на наш API как и раньше (`NEXT_PUBLIC_API_URL`).
  Если клиент хочет, чтобы и сбор событий был first‑party, домен с `kind = COLLECT` (`t.invest.client.com`)
  по CNAME на наш API — Meta‑CAPI при этом не меняется.
- Трекинг не теряет ничего: сессия, решение, cookie, BLOCK_VIEW, формы, награды — все те же эндпоинты.
  Единственное отличие от режима B — HTML отдаёт машина клиента, и если наш хост недоступен, раннер
  покажет последнюю закэшированную версию (ISR 60 с) или 404 — трекинг в этот момент тоже недоступен.

Что даёт: домен, IP и машина — клиента. Мы по‑прежнему видим каждое событие и управляем вариантами.
Чего не даёт: «полной автономии» лендинга — без нашего API раннер не умеет выбирать вариант и не
принимает формы. Это осознанно: вся логика и данные остаются у нас, у клиента только рендер.

### Режим D — статический экспорт (не делаем)

Можно собирать вариант в статический HTML и отдавать клиенту файлами. Тогда Thompson, персонализация блоков,
формы и RLHA отключаются или переезжают в клиентский JS с публичным API. Это потеря основной ценности
продукта ради независимости от нашего сервера; оставлено как «если очень попросят», в roadmap не вносится.

## 4. Что выбирать

| Ситуация | Режим |
|---|---|
| Внутреннее использование, первый клиент — мы | A сейчас, B как только появится домен под лендинги |
| Внешний клиент, обычный | B (CNAME). Пять минут настройки DNS, ничего ставить не надо |
| Клиент требует «на нашем сервере» / свой compliance / свой IP | C (раннер). Плюс домен `COLLECT`, если нужен first‑party сбор |
| Клиент с несколькими Business Manager / sub‑аккаунтами GHL | B или C, но **по домену на каждый BM** — иначе блок одного BM утянет остальные |

Во всех режимах рекламный аккаунт защищается не хостингом, а правилами: стадии записей в Meta, compliance
до запуска, probe‑модерация, отдельный пиксель и домен на клиента.

## 5. Что сделано в коде (Phase 10)

| Пункт | Где |
|---|---|
| Сравнение вариантов, выбор, отклонение с причиной, правка с причиной (RLHA) | кабинет `/landings`; `POST /landings/generate-set`, `GET /landings/sets`, `POST /landings/{id}/reject` |
| Превью DRAFT/REVIEW для залогиненного пользователя | `/l/preview/{id}` (JWT, события не пишутся) |
| Домены тенанта, верификация DNS (TXT + CNAME), CORS из таблицы | `tenant_domains`, `/domains/*`, `GET /public/domain/{host}`, `TenantDomainCorsSource` |
| Host‑aware middleware (админка только на платформенном хосте) | `frontend/src/middleware.ts`, `PLATFORM_HOSTS` |
| Раннер на сервере клиента | `docker-compose.runner.yml`, `LANDING_RUNNER=1`, `RUNNER_KEY`, `POST /public/decide`, `runner_keys` |

Открыто (не код): выбор TLS‑прокси для custom hostnames (Cloudflare for SaaS или Caddy), домен под
`landings.наш.com`, инструкция клиенту на одну страницу.
