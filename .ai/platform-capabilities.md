**Текущий клиент:** InteliGel — привлечение аккредитованных инвесторов, средний чек $75 000, Reg D 506(c).

## 1. Для кого создана платформа

**Маркетинговые агентства**, которые ведут нескольких клиентов и хотят управлять их рекламой из единого центра с изолированными данными.

**Компании, привлекающие капитал** по правилам Reg D 506(c): платформа знает требования SEC, фильтрует некачественных лидов ещё до отправки в Meta и считает стоимость проведённого инвесторского звонка.

**B2B-компании с длинным циклом сделки**: обучаемся не на «нажатиях кнопки», а на реальном качестве лида — состоявшемся звонке, подписанном договоре, полученном переводе.

**Для всех**: платформа не может навредить рекламному аккаунту «сама» — записи в Meta включаются по стадиям с проверяемыми условиями, защитные паузы работают всегда, каждое действие в журнале (раздел 7.8).

## 2. Управление рекламными материалами

### 2.1 Загрузка и анализ
Маркетолог загружает видео или изображение — платформа автоматически извлекает «ДНК» креатива по 11 атомам: хук, структура, темп монтажа (EDIT_PACE — по сменам сцен через ffmpeg), лицо в кадре, субтитры, тон, тип доказательства (отзыв / цифры / демонстрация), музыка (MUSIC — по аудиопрофилю через ffmpeg), длительность, призыв к действию, стиль производства. Для видео при загрузке автоматически снимается транскрипт (Whisper), кадры и транскрипт анализирует Claude (модели задаются в конфиге ML-сервиса: `llm_model_vision` / `llm_model_default` / `llm_model_fast`). Каждый элемент получает оценку уверенности.

### 2.2 Единый атомный реестр
Все понятия (хук, CTA, тон) хранятся в общем реестре с векторными центроидами. Раз в неделю система объединяет близкие понятия и исключает дубли — так «живая демонстрация» и «product demo» перестают считаться разными вещами.

### 2.3 Оценка производительности
Для каждого рекламного элемента платформа показывает: сколько сессий, какой процент конверсии, какой процент заполнения формы. Четыре симптома плохой работы выявляются автоматически: высокий отказ, бросание формы, низкая конверсия, слабый призыв к действию.

### 2.4 Тестирование вариантов (A/B)
Байесовская система (Thompson Sampling) распределяет трафик между вариантами, накапливает данные и сама находит победителя — без ручного мониторинга. Победитель выбирается когда вероятность превосходства >95% и накоплено достаточно наблюдений (ESS ≥ 200).

### 2.5 Кладбище неудачных креативов
Каждый «проигравший» креатив попадает в архив с автоматическим разбором причины провала: техническая проблема, рыночный спад или слабый контент. При следующем создании система предупреждает, если новый вариант похож на уже провалившийся.

### 2.6 Эволюция — автоматическая генерация новых гипотез
Платформа берёт лучший хук из одного креатива, лучший оффер из другого, лучший CTA из третьего и предлагает гибридный вариант. Перед тем как предложить — проверяет смысловую связность (хук обещает то, что оффер обещает выполнить).

### 2.7 Оценка выгорания
Алгоритм выживаемости предсказывает, когда креатив «устанет» по частоте, начальному ROAS и типу аудитории. Предупреждение приходит заблаговременно — за N дней до предполагаемого выгорания — и автоматически создаётся задание для нового креатива.

### 2.8 ИИ-монтаж из реальных футажей клиента
Суть блока — монтаж, а не генерация: клиент загружает свои футажи (основатель, продукт, UGC), система собирает из них новые креативы к гипотезам из данных. Конвейер: транскрипция (Whisper) → разметка сцен (Claude) → план монтажа (Claude) → рендер `POST /video/render` локальным ffmpeg в форматах 9:16 / 4:5 / 1:1 с текстовыми оверлеями (drawtext) и генерацией вариаций. Субтитры: из таймкодов Whisper строятся SRT и ASS (стили white_bottom / yellow_bold / white_top / black_box, перенос до 2 строк) и вжигаются фильтром `subtitles=` (`POST /video/subtitles` отдаёт файлы отдельно). Озвучка: `POST /video/tts` — OpenAI `tts-1` (опционально ElevenLabs), режимы замены / микса дорожки с сайдчейн-дакингом; без ключа — тихая заглушка. Музыкальная подложка: библиотека лицензированных треков клиента (`/music/tracks`: лицензия royalty_free / licensed / owned, bpm, настроение), микс с дакингом, атом MUSIC из выбранного трека. Генеративной музыки нет намеренно — у провайдеров нет официального API с проверяемой коммерческой лицензией.

### 2.9 Адаптер AI-видео (не ядро продукта, выключен по умолчанию)
Не относится к сути продукта (ИИ-монтаж реального футажа) и для инвесторской аудитории не рекомендуется; оставлен за флагом на случай B2C-ниш. `POST /ai-video/generate` создаёт задание у провайдера (HeyGen v2, Synthesia v2, Runway Gen-3) и опрашивает статус; без ключа провайдера — режим MOCK, реальный вызов никогда не делается молча. Готовое видео регистрируется как креатив с флагами `is_ai_generated = true`, `has_ai_disclosure = false` (маркетолог обязан проставить дисклеймер до запуска). Включается флагом клиента `ai_video_enabled`; правило A/B перед масштабированием (P(не хуже живого) ≥ 90%, ≥ 50 сессий на плечо) обязательно. Голосовые атомы (тон, темп, тембр) выводятся из параметров синтеза.

### 2.10 Публикация креатива в Meta только через платформу (Phase 11)
Кнопка «Publish to Meta» на странице **Meta ads**: платформа проверяет готовность (стадия записей, токен, рекламный аккаунт, Page ID, файл, compliance текста объявления), загружает видео или изображение, создаёт креатив с выключенными автоулучшениями Meta и объявление **на паузе**, ставит адрес назначения на домене клиента с параметрами Meta (`mai_c={{ad.id}}` и далее) и запоминает идентификатор объявления в карте `meta_ad_map`. Включение только из кабинета после вердикта модерации; отклонение уходит в кладбище с причиной и автоматически заказывает новый бриф. Каждый час платформа читает объявления аккаунта: объявление без карты помечается «неуправляемым» (вне обучения и пар, алерт), объявление с изменённым руками адресом или видео — «расхождение». Индикатор «линковка» в чеклисте онбординга; пока он красный, запуск тестов заблокирован. Скачать файл можно, но кабинет показывает статус «не в Meta»; для внешних клиентов есть режим «только превью». Код креатива `MAI-xxxxxx` в имени объявления позволяет сопоставить даже то, что залили руками.

Результат: в клике известен креатив, решение по лендингу учитывает его, и на странице A/B появляется таблица **пар «креатив → лендинг»** с числом решений, конверсий, апостериорной оценкой и вероятностью выигрыша. Визиты без креатива (органика, рассылки) учат только лендинг.

## 3. Посадочные страницы и воронка

### 3.1 Конструктор блоков лендинга
Готовые блоки для сборки страниц:

**Общие блоки:** Hero, Проблема, Доказательство, Цена, CTA, FAQ, Social Proof

**Блоки для инвестиционной воронки:** Календарь записи (встроен GHL), Чекбокс аккредитации («Я подтверждаю, что являюсь аккредитованным инвестором» — формулировка проверена на соответствие правилам Meta), Выбор размера инвестиции (5 корзин), Дисклеймер Reg D 506(c), Социальное доказательство (только одобренные фразы)

**Блоки путей воронки B/C:** Материалы (видео основателя + документы, событие MATERIAL_VIEW), Data Room (DATAROOM_OPEN), Регистрация на вебинар (WEBINAR_REG). Всего 14 React-компонентов блоков; все рендерятся SSR из JSON варианта.

### 3.2 Персонализация блоков
Система изучает поведенческие кластеры посетителей и меняет порядок блоков для каждого — без создания нового контента, только перестановка уже одобренных блоков. Контрольная группа 7,5% всегда видит стандартный порядок.

### 3.3 Четыре пути воронки — как отдельные эксперименты
Платформа может тестировать не только содержимое страницы, но и сам путь клиента:
- **Путь A (CALL_4D)** — текущий стандарт: запись → звонок через 4 дня
- **Путь B (MATERIALS_FIRST)** — сначала видео основателя + материалы, потом приглашение на звонок (с воротами вовлечённости)
- **Путь C (TIERED_BY_TICKET)** — вебинар для инвестиций <$50K, 1-on-1 для $50-250K, прямой звонок с основателем для >$250K
- **Путь D (CALL_24H)** — координатор предлагает слот в течение 24 часов

Каждый путь — это отдельное «плечо» Байесовского бандита. Оптимизируем по числу состоявшихся звонков на 1000 просмотров страницы.

### 3.4 Отслеживание 11 этапов воронки инвестора
Каждый шаг фиксируется и отправляется в Meta:

| Этап | Описание |
|------|----------|
| CALENDAR_OPEN | Открыл страницу с календарём |
| SLOT_SELECTED | Выбрал слот |
| FORM_SUBMIT | Заполнил форму |
| BOOKED | Запись создана в CRM |
| COORD_CONFIRMED | Координатор подтвердил |
| CALL_HELD | Звонок состоялся (**ключевой этап качества**) |
| NO_SHOW | Не пришёл |
| FOLLOWUP_HELD | Повторный контакт |
| ACCRED_VERIFIED | Аккредитация подтверждена |
| INVEST_COMMITTED | Инвестор подтвердил намерение |
| FUNDS_RECEIVED | Деньги получены |

### 3.5 Выбор варианта, превью и домен клиента (Phase 10)
Система собирает несколько вариантов лендинга из одного брифа (по умолчанию три, у каждого свой угол: прямой и фактический, история, доказательства и цифры, работа с возражениями, короткий и срочный без выдуманных дедлайнов). На странице **Landings** маркетолог видит варианты рядом, правит текст слотов с указанием причины (правка уходит в обучение RLHA), отклоняет с причиной (TEXT, TONE, COMPLIANCE, OFF_BRIEF, STRUCTURE, OTHER — тоже записывается в RLHA) или выбирает: вариант уходит на REVIEW, затем чеклист compliance и запуск на странице креатива. Любой вариант, включая черновики, открывается в превью `/l/preview/{id}` для залогиненного пользователя; события при этом не пишутся.

Где лендинг живёт — три режима (`.ai/landing-hosting.md`): на хосте платформы; на домене клиента по CNAME (домен добавляется в Settings → Landing domains, проверяется по DNS TXT и CNAME, после проверки платформа отдаёт на этом хосте только лендинги этого клиента, а CORS разрешает домен автоматически); на сервере клиента — тот же образ фронтенда в режиме раннера (`docker-compose.runner.yml`): админка выключена, наружу только HTTPS к нашему API, выбор варианта через `POST /public/decide` с отзываемым ключом, никаких секретов ML, базы или Meta у клиента. Во всех режимах события, формы и награды приходят на платформу как раньше. Meta блокирует домены, а не IP хостинга, поэтому у каждого клиента (и каждого Business Manager) свой домен.

## 4. Привлечение инвестора (специализация клиента #1)

### 4.1 Онбординг-чеклист перед запуском
7 автоматических проверок готовности к запуску: настроен ли пиксель, настроен ли маппинг событий, настроена ли дедупликация, активны ли compliance-правила, готово ли плечо-контроль в follow-up, созданы ли пути воронки, настроен ли Reg CF шлюз.

### 4.2 Квалификация лида на форме
Посетитель сам указывает планируемый размер инвестиции (5 диапазонов: до $25K, $25-50K, $50-100K, $100-250K, >$250K) и подтверждает статус аккредитованного инвестора. Эти данные сразу:
- Определяют какое событие Meta получит (аккредитованный → основной пиксель; неаккредитованный → будущий Reg CF пиксель)
- Задают коэффициент ценности лида для алгоритма Advantage+
- Выбирают путь воронки (C — по размеру тикета)

### 4.3 Предсказание риска неявки
Ещё до звонка система предсказывает вероятность того, что инвестор не придёт. Учитывает 6 факторов: сколько дней до звонка, известен ли часовой пояс, размер тикета, аккредитация, тип устройства, страна. Результат — три тира риска:

- **HIGH** (вероятность неявки >45%) → предлагаем более близкий слот (1-3 дня) + координатор звонит в течение 15 минут
- **MED** → стандартное окно (1-5 дней) + SMS напоминания
- **LOW** → стандартное окно (2-7 дней) + email

Отчёт по неявкам (`GET /propensity/report?days=`): show rate по каждому тиру с 90% интервалом Jeffreys, заполняемость командных слотов (с учётом overbooking-политики), AUC модели на скользящем holdout (оценки, сделанные ≥ 1 дня до звонка; порог активации 0.70). Строки отчёта попадают в еженедельный отчёт. Атрибуция причин неявки: еженедельная ridge-логит-регрессия по признакам лида/креатива → драйверы неявок уходят в «avoid list» бриефа и в проверку кликбейта.

### 4.4 Предсказание ценности лида в день 0
В момент бронирования система рассчитывает прогнозную ценность:

> **Ценность** = P(придёт на звонок) × P(пройдёт проверку аккредитации) × P(вложит деньги | прошёл проверку) × Ожидаемый тикет

Прогноз сохраняется (`lead_value_predictions`) и сверяется с фактом; калибровка принимается при 200+ закрытых сделках и уклоне 0.8–1.2. Подстановка прогноза в CAPI-value (`predicted_value` как токен формулы) пока не подключена — в Meta уходит `base × k_accr × k_ticket` (см. раздел 16).

### 4.5 Follow-up последовательности — автоматическая оптимизация
Байесовский бандит тестирует разные сценарии дозаписи: одну последовательность с повесткой звонка, другую через WhatsApp для международных лидов, разные временны́е цепочки (48ч/24ч/2ч/15мин). Контрольное плечо (текущая последовательность клиента) никогда не паузируется — всегда есть эталон для сравнения.

Автоматическая пауза плохого плеча: если вероятность что оно хуже контроля >95% при достаточной выборке (ESS≥100).

Аудитории follow-up: NO_SHOW, BOOKED, HELD (после состоявшегося звонка — назначение уникально на пару «встреча × аудитория»). Уровни награды Thompson (L1 / L2 / корректор) задаются в настройках клиента (`reward_levels`), цель по неявкам (`noshow_target`, по умолчанию 30%) отображается в еженедельной статистике.

### 4.6 Разбор каждого звонка
Координатор фиксирует итог звонка через структурированную форму: результат (COMMITTED / INTERESTED / COLD / NO_SHOW), теги возражений (цена, таймминг, супруг(а), риски, ликвидность и др.). Система автоматически выбирает follow-up плечо:
- COMMITTED → инструкции для перевода (срочно)
- NO_SHOW → последовательность восстановления
- PRICE_CONCERN → последовательность с калькулятором ROI
- ACCRED_UNCLEAR → образовательная последовательность про аккредитацию

Агрегируется статистика: какие возражения встречаются чаще всего и какой процент из них в итоге конвертируется.

Записи звонков: вебхук `POST /webhooks/call-recordings/{tenantId}` принимает запись (Zoom / GHL), проверяет согласие по правилам штата (all-party → требуется `consent_granted`), транскрибирует через Whisper с редактированием PII, автоматически проставляет теги возражений в форму разбора; список — `GET /post-call/recordings`.

### 4.7 Архетипы инвестора
После первых взаимодействий система классифицирует инвестора по архетипу:

| Архетип | Признаки | Стратегия |
|---------|----------|-----------|
| COMMITTED_QUICK | Быстро заполнил, высокий тикет, аккредитован | Инструкции по переводу в течение 2 часов |
| RESEARCHER | 3+ просмотра материалов, открыл data room | Полный deck + Q&A звонок (12 часов SLA) |
| FENCE_SITTER | Возражения по времени/цене, несколько касаний | Целевая последовательность по возражению |
| HIGH_VALUE_QUIET | Высокий тикет, мало взаимодействий | Личный контакт от основателя (6 часов SLA) |
| DISQUALIFIED | Не аккредитован или низкий тикет | Убрать из активной последовательности |

### 4.8 Схема атомов оффера (INVESTOR_RAISE)
Оффер описывается набором атомов по схеме вертикали (`offer_atom_schemas`, для инвесторской воронки — минимальный тикет, структура раунда, срок, ликвидность, доказательство и т.д.). Валидация обязательных атомов в Java и ML, режим COMPLIANCE_PASS заменяет «пол по марже» для ценных бумаг: кандидат оффера проходит только при PASS compliance-проверки. Генерация кандидатов `POST /mmf/offers/generate-from-schema`, исследование — `/offer-schemas/{key}/explore` → `offer_candidates`.

### 4.9 Ворота по состоявшимся звонкам
Ворота тестового контура считаются по качественному этапу воронки (`is_quality_key`, для клиента #1 — CALL_HELD): Gate 2 — доля записей, Gate 3 — стоимость состоявшегося звонка и правило остановки P(show rate < якорного) > 0.9. В Quality Score креатива show rate входит с весом 0.40.

### 4.10 Несколько sub-аккаунтов GHL
Роли MAIN / AGENCY / WEBINAR / MAILING, у каждой локации свой секрет вебхука и API-ключ; статус сделки (OpportunityStatusUpdate) принимается только от MAIN. При FORM_SUBMIT в контакт GHL записываются `mai_session_id` / `mai_event_id`; связывание контакта с сессией — по custom field → email → телефон → UTM. Ежедневно в 07:15 UTC сверка целостности воронки (BOOKED в CRM vs Schedule в Meta vs FORM_SUBMIT), алерт при расхождении выше порога (`funnel_integrity_delta`, 10%).

## 6. Мультиканальная реклама

### 6.1 Meta Ads
Создание кампаний, управление статусами, синхронизация расходов, двухконтурная структура тестирования (тест → подтверждение → масштаб), автоматическая пауза по L2/L3 правилам, staged gates для автоматического отсева проигравших.

### 6.2 Google Ads (API v17)
Просмотр кампаний, получение метрик (показы, клики, расходы, конверсии), управление статусами (пауза/активация). REST-клиент написан, на живом аккаунте не проверялся.

### 6.3 TikTok Ads (Business API v1.3)
Синхронизация кампаний, аналитика, событийная интеграция. REST-клиент написан, на живом аккаунте не проверялся.

### 6.4 Единый граф решений
Одна система принимает решения по всем каналам одновременно. Один и тот же Байесовский бандит работает для Meta, Google и TikTok — с учётом канальной специфики через префикс контекстного ключа.

### 6.5 Байесовский MMM (Marketing Mix Modelling)
Инфраструктура для понимания как бюджет распределяется между каналами и какой реальный вклад даёт каждый канал с учётом adstock-трансформации (эффект с задержкой) и кривых насыщения (Hill saturation). Для полной калибровки требуется 6-12 месяцев живых данных.

### 6.6 Кросс-канальная атрибуция
Четыре модели распределения ценности между касаниями:
- **Last-touch** — вся ценность последнему касанию
- **Linear** — равномерно по всем касаниям
- **Time-decay** — больше ценности у последних касаний
- **Data-driven (Markov + Shapley)** — статистически правильное распределение по реальному вкладу каждого канала

## 7. Защита бюджета и безопасность

### 7.1 Финансовый предохранитель (три уровня)
- **L1** — дневной стоп-лосс на конкретный креатив. Срабатывает мгновенно при превышении порога.
- **L2** — байесовский триггер: если вероятность превышения целевого CPA на 50% составляет более 85%, или расходы составляют 80% потолка за 8 часов, или CPM резко вырос (z-score > 3) → предупреждение и возможная пауза.
- **L3** — экстренная остановка: если ROAS ниже точки безубыточности с вероятностью >90% или месячный потолок достигнут.

Уведомления через Telegram и Slack.

### 7.2 Автоматическое обнаружение мошенничества
Четыре слоя защиты:
1. Cloudflare Bot Score (низкий балл → подозрительно)
2. Поведенческие паттерны: нет взаимодействия после просмотра страницы, известный бот-агент, сессия менее 2 секунд
3. IP-кластеры: 50+ сессий с одного IP за час
4. Агрегированный мониторинг: если >10% сессий за 24 часа подозрительны — алерт

Подозрительные сессии исключаются из обучения модели, но остаются в знаменателе — коэффициент конверсии не раздувается.

Детектор обвала конверсии (каждые 15 минут): CTR стабилен (±20% к среднему за сутки), а CVR упал ниже 10% суточного среднего за последний час при ≥ 100 сессиях → инцидент CVR_COLLAPSE, пауза наборов объявлений через P0-очередь, алерт.

Дополнительные слои: L2 — автоматизированный тайминг кликов (σ < 50 мс), линейный скролл, кластеры IP+UA+viewport (безопасно для CGNAT), режим LOG_ONLY / ENFORCE; L3 (ежечасно) — всплеск CTR без конверсий по гео × плейсменту и ночные всплески кликов по часовому поясу клиента (`timezone`, `night_burst_threshold`, `night_burst_window_min`) → событие circuit breaker FRAUD_NIGHT_BURST. Cloudflare bot score читается из заголовка запроса; reCAPTCHA Enterprise — реальная проверка.

### 7.3 Compliance для инвестиционной рекламы (Reg D 506(c))
Автоматическая проверка рекламных текстов перед запуском по четырём правилам:

| Набор правил | Что проверяет |
|---|---|
| META_FINANCIAL | Финансовые запреты Meta: гарантии дохода, конкретные цифры, вводящие в заблуждение |
| META_PERSONAL_ATTR | «Ты аккредитованный инвестор?» — FAIL. «Открыто для аккредитованных инвесторов» — PASS |
| SEC_506C | Соответствие Regulation D 506(c) |
| CLIENT_LEGAL | Правила, добавленные адвокатом и CEO клиента |

Текст не пройдёт аппрув и не будет запущен, пока не получит статус PASS или явное разрешение с указанием причины.

### 7.4 Генерация из одобренных фраз
Весь рекламный контент генерируется только из пула фраз, одобренных юристом и CEO. Если система хочет использовать новую фразу — она попадает в список «требует правовой проверки» и не идёт в эфир без одобрения.

### 7.5 Симуляция проверки Meta (META_REVIEWER persona) и probe-модерация
До запуска каждого нового креатива система оценивает вероятность отклонения со стороны Meta на основе внутренних compliance-проверок. Это только совет — запуск никогда не блокируется автоматически. Реальный результат модерации фиксируется и сравнивается с прогнозом: тестовый батч можно запустить в режиме probe (объявления создаются на паузе), каждые 30 минут опрашиваются `effective_status` / `ad_review_feedback`, вердикт APPROVED / REJECTED пишется в журнал модерации, REJECTED → алерт и автоматический запрос нового бриефа с avoid-list заблокированных формулировок (каждые 6 часов).

Проверка медиа: детекция лиц по кадрам видео (OpenCV, опционально в Docker-образе `--build-arg INSTALL_CV=1`) — лица без model release помечаются WARN; без OpenCV проверка честно сообщает, что не запускалась.

### 7.6 Конкурентная аналитика
Еженедельный мониторинг рекламы конкурентов через Meta Ad Library. Система анализирует их рекламу и предлагает три контр-гипотезы для тестирования. **Авто-запуск без одобрения человека — запрещён.** Только человек нажимает кнопку «одобрить».

### 7.7 Защита от загрязнения пикселя
Мониторинг качества лидов: если доля лидов с состоявшимися встречами по UTM-кампании падает ниже 70% от базовой за 30 дней (при не менее 20 формах) — автоматический алерт и рекомендация приостановить кампанию.

### 7.8 Политика записей в Meta: стадии, пороги, журнал
Любая запись в Meta Marketing API (пауза, возобновление, бюджет, запуск, создание кампании или аудитории) проходит одну точку проверки — `MetaWriteGate`. Решение (разрешено / отказ / рекомендация) с причиной, инициатором (человек или джоба) и стадией пишется в журнал `meta_write_decisions`; тест на исходники не даёт добавить путь записи в обход. Защитные паузы (стоп-лосс, обвал CVR, инцидент сайта) не блокируются никогда — остановка расходов это страховка, а не оптимизация.

**Стадии клиента** (`/meta-write`, переход вперёд только при выполненных условиях по данным, понижение всегда):

| Стадия | Что разрешено | Условия перехода на следующую |
|---|---|---|
| READ_ONLY (по умолчанию) | Только защитные паузы; Marketing API читается, страховка — Automated Rules и Spending Limit в самом Meta | Токен Meta OK; CAPI живой: ≥ 50 отправленных событий за ≥ 14 дней; EMQ pre-check пройден; клиент подтвердил Automated Rules и лимит расходов |
| GUARDED_WRITES | Пауза, возобновление, бюджет в пределах порогов; запуски только как probe-модерация (объявления на паузе до вердикта Meta); создание кампаний и аудиторий запрещено | ≥ 14 дней в GUARDED_WRITES; OPE PASS ≤ 7 дней; автономия ≥ SEMI_AUTOPILOT; ни одного отказа за 7 дней |
| FULL | Всё, пороги остаются | — |

**Пороги** (настраиваются по клиенту, `meta_write_policy`): бюджет ≤ 20 % за шаг и ≥ 24 ч между шагами на один ad set; ≤ 10 записей в час на аккаунт; ad set в learning phase не редактируется (правило Meta: правка сбрасывает обучение). Превышение порога не выполняется, а становится рекомендацией для человека в `autopilot_actions` (HTTP 409); нарушение стадии — отказ (403).

**Автоматические действия (джобы, автопилот)** дополнительно требуют уровня автономии: SEMI_AUTOPILOT для паузы/возобновления/бюджета/запуска, AUTOPILOT для создания кампаний и аудиторий; ниже — действие записывается как рекомендация.

**Override**: одноразовое разрешение на конкретное действие (и при желании конкретную цель), срок до 4 часов (по умолчанию 30 минут), причина обязательна (≥ 10 символов), фиксируется в журнале вместе с решением, которое его использовало. Override не обходит learning-phase lock для бюджета. Принудительный переход стадии при невыполненных условиях — тоже только с причиной и записью в журнал.

Полное обоснование подхода (почему CAPI обязателен, где реальные риски бана, план включения по этапам) — в `.ai/meta-api-policy.md`.

## 9. Искусственный интеллект и Байесовская статистика

### 9.1 Thompson Sampling везде
Байесовский многорукий бандит работает на четырёх уровнях одновременно:
- Варианты лендинга (какой показывать следующему посетителю)
- Follow-up последовательности (какую запустить для каждого лида)
- Пути воронки (A/B/C/D)
- Рекламные кампании (какой масштабировать)

Каждый раз: автоматическая пауза проигравших, автоматическое подтверждение победителя при P(best) > 95%.

### 9.2 Байесовская GLM
Generalized Linear Model связывает атомы креатива, внешние сигналы, кластер аудитории и контекстные факторы с конверсией. Используется для: предсказания CVR нового креатива до запуска, ранжирования гибридных кандидатов, понимания какие атомы работают в каких условиях, и — с Phase 9 — как стартовый приор Thompson-плеча: новый вариант начинает не с Beta(1,1), а с Beta(α0, β0), выведенной из постериора атомов его креатива (эффективный размер ≤ 20), с усадкой к нишевому приору и с учётом экспертной оценки (1 → Beta(1,3), 5 → Beta(3,1)).

Режимы выбора плеча: стандартный Thompson или top-two Thompson (`ts_mode = top_two`, β настраивается) — претендент обязан отличаться от лидера, что ускоряет различение близких вариантов. Ценность информации (EVI): `POST /decide/evi` ранжирует эксперименты по ожидаемому снижению регрета от ещё N наблюдений и распределяет бюджет исследования пропорционально.

### 9.3 Off-Policy Evaluation (OPE)
Ретроспективная оценка политики на логе решений с propensity (IPS / SNIPS / doubly-robust, ESS, bootstrap-интервалы): по запросу (`POST /ope/evaluate`) и автоматически каждый понедельник 05:00 UTC. Это ворота автопилота: `PUT /tenants/me/autonomy` выше ADVISOR принимается только при последнем вердикте PASS не старше 7 дней (иначе 409 с причиной); FAIL на еженедельном прогоне у клиента в SEMI_AUTOPILOT / AUTOPILOT понижает уровень до ADVISOR и шлёт алерт.

### 9.4 Предсказание выживаемости
Cox Proportional Hazard / Байесовская модель выживаемости для прогноза выгорания креатива. Учитывает частоту показов, начальный ROAS, тип аудитории, сезонность. Эвристика работает как резерв при недостатке данных.

### 9.5 Бенчмарки по нише
Платформа агрегирует показатели по нишам (только первичные данные, никаких данных Meta) и позволяет сравнить результаты клиента с медианой по нише. Пол для агрегации: не менее 5 клиентов в ячейке, иначе данные скрыты.

### 9.6 Autopilot с уровнями автономности
| Уровень | Что может делать автоматически |
|---------|-------------------------------|
| OBSERVER | Только смотреть |
| ADVISOR (по умолчанию) | Рекомендации, всё вручную |
| SEMI_AUTOPILOT | Пауза/активация, масштабирование в рамках порогов |
| AUTOPILOT | Все разрешённые действия |

Переход выше ADVISOR — только после OPE PASS (≤ 7 дней); проверка встроена в `PUT /tenants/me/autonomy`, понижение всегда разрешено. Истёкший токен Meta (INVALID) автоматически переводит клиента в OBSERVER, прежний уровень восстанавливается при повторной авторизации.

Поверх уровней автономии действует стадия записей в Meta `READ_ONLY → GUARDED_WRITES → FULL` с порогами и журналом решений — см. раздел 7.8.

### 9.7 Симулятор What-If
Три сценария для планирования: «что если увеличить бюджет», «сколько сессий до значимости», «что если убрать проигрывающий вариант». Все ответы с p10/p50/p90 доверительными интервалами.

### 9.8 Портфельная оптимизация
Распределение бюджета между кампаниями / каналами по Марковицу: ожидаемый ROAS и ковариация берутся из постериорных выборок, long-only, пол 5% на актив, параметр риска λ (`POST /portfolio/markowitz`). При истории короче 6 месяцев — аллокация по Шарпу. Только рекомендация, никогда внутри CBO-кампании.

## 10. Создание рекламного контента

### 10.1 Автогенерация LLM с compliance-фильтром
Маркетолог указывает тип блока и слоты — система генерирует текст с учётом: лучших атомов за 90 дней, голоса бренда, исправлений маркетолога из предыдущих генераций (обучение на обратной связи). Любая генерация автоматически проходит compliance-проверку. FAIL — блокирует аппрув.

**Обучение от правок (RLHA, замкнутый цикл с 2026-10-20).** Каждый сгенерированный слот записывается; когда маркетолог правит текст лендинга или брифа в платформе, пара «сгенерировано → утверждено» сохраняется автоматически с классификацией изменения (тон, длина, запрещённое слово, структура, бренд) и причиной правки (тон / факты / юр. / длина / структура). Последние 8 пар по типу контента подаются LLM как примеры стиля при следующей генерации; правки по фактам в примеры не идут. Метрика блока — доля генераций, принятых без правок (цель 70 %), с недельным трендом на странице `/rlha`. Отклонение видео‑рендера с причиной (монтаж, текст, музыка, лицо, compliance, темп) попадает в avoid‑list следующего плана монтажа. Это накопление предпочтений клиента, а не дообучение модели: LoRA по нише не планируется в первый год.

### 10.2 Соответствие обещания (Message Match)
Система оценивает насколько обещание в рекламе соответствует предложению на лендинге. Низкое соответствие ухудшает качество лидов — это отслеживается и включается в недельный отчёт.

### 10.3 Задание для видеографа/дизайнера (Creator Brief)
Автоматически генерируется на основе данных: какие хуки работают, какие CTA конвертируют, какие форматы показали лучший ROAS. Включает возражения аудитории (голос клиента), anti-patterns (что не стоит повторять), бенчмарки. Обязательный «свободный слот» для нестандартной идеи от автора.

### 10.4 Голос клиента (VoC)
Маркетолог загружает цитаты из отзывов, комментариев, записей звонков. Система кластеризует их по типам возражений (цена, доверие, понимание, срочность, соответствие и т.д.) и автоматически добавляет в следующий бриеф.

## 11. Отчётность и прозрачность

### 11.1 Еженедельный авто-отчёт
Каждый понедельник в 08:00 UTC: обзор недели (сессии, конверсии, CVR, доход), топ-3 креатива, топ-5 атомарных инсайтов, аномалии воронки, статистика неявок против цели клиента, show rate по тирам риска, заполняемость слотов и AUC no-show модели, дисциплина CRM (встречи без статуса). Доставка через Telegram и/или Slack.

### 11.2 Дашборд месяц-1 (для онбординга клиента #1)
Три виджета специально для первого месяца:
- Лиды, НЕ переданные в инвестиционный пиксель (защита от загрязнения)
- Стоимость состоявшегося звонка по каждому креативу vs якорный креатив (%)
- Частота неявок по вариантам follow-up + дней до статистической значимости

### 11.3 Объяснимость каждого решения
Любое решение системы можно объяснить маркетологу: Wilson CI, P(лучший), сравнение с якорным, внешний контекст на дату. Система не говорит «доверяй мне» — она показывает числа.

### 11.4 Кросс-канальный дашборд A/B
На одном экране — сравнение вариантов по всем каналам с байесовской вероятностью победителя. Нет ложной уверенности из-за маленькой выборки — до накопления ESS ≥ 200 результат помечается как предварительный.

## 12. Безопасность и приватность данных

### 12.1 Полная изоляция данных клиентов
Row-Level Security (ENABLE + FORCE) на всех таблицах с `tenant_id`; политика через `app.current_tenant`, системные джобы работают в явном system-scope. Бэкенд подключается от имени непривилегированной роли `mai_app`, ML-сервис — от роли `mai_ml` (не владелец, NOBYPASSRLS; каждый запрос к БД идёт через `tenant_pool(tenant_id)` или `system_pool()`), миграции — от владельца `mai`. Доступ на запись в `thompson_arms` есть только у `mai_ml`: α/β пишет только ML-сервис. Ежемесячные партиции `events` создаются автоматически на 2 месяца вперёд.

### 12.2 JWT-аутентификация и ротация токенов
Каждый запрос проверяется через JWT-токен с указанием tenant_id (страница `/login`, регистрация, выход, auth-guard админки); внутренние вызовы Spring → ML и Next.js → ML защищены общим ключом (`INTERNAL_API_KEY`, fail-closed на всех ML-роутерах). Секреты третьих сторон (токены Meta, CAPI-токены пикселей, API-ключи GHL, токены Google/TikTok) хранятся запечатанными AES-256-GCM (`ENCRYPTION_KEY`; при старте старые plaintext-строки перешифровываются; без ключа — dev-режим с предупреждением). Токены Meta: с 50-го дня — реальный обмен long-lived токена через Graph API (`fb_exchange_token`, запись в аудит-журнал), с 58-го — INVALID, алерт, пауза записей в Meta и автономия → OBSERVER до повторной авторизации.

### 12.3 Управление согласием (CMP)
Интеграция с Cookiebot. Три уровня согласия: минимальный (только конверсии), аналитический (без поведения), полный. Поведенческие данные (скролл, наведение, просмотр блоков) — только с `consent_level = full`.

### 12.4 Право на удаление (GDPR/CCPA)
Один запрос — полное удаление данных субъекта из всех таблиц с подтверждающей записью в аудит-журнале.

### 12.5 Мониторинг здоровья сайта
Каждые 60 секунд — проверка доступности каждого активного лендинга. Два consecutive FAIL за 10 минут → алерт в Telegram + автоматическая пауза рекламных кампаний через P0-очередь. Каждые 30 минут — синтетическая отправка формы: headless-браузер (Playwright, опционально, `--build-arg INSTALL_PLAYWRIGHT=1`) с откатом на HTTP-проверку; режим и ожидаемый ответ задаются в настройках клиента (`form_check_mode`, `form_check_success_pattern`, `form_check_fields`). Два провала → инцидент FORM_ERROR и пауза наборов объявлений. Возобновление — только после 3 подряд успешных проверок **и** ручного подтверждения (`POST /site-health/{id}/confirm-resume`); возобновляются ровно те наборы, что были поставлены на паузу.

### 12.6 Аудит-журнал всех Meta API вызовов
Каждый запрос к Meta API записывается в append-only таблицу. Невозможно удалить или изменить запись задним числом.

## 13. Для маркетингового агентства

### 13.1 White-label архитектура
Несколько клиентов под одним агентским аккаунтом. Данные каждого клиента полностью изолированы — агентство видит только агрегаты, никогда сырые данные чужого клиента.

### 13.2 Агентский дашборд
Агрегированные KPI по всем клиентам: просмотры лендинга, состоявшиеся звонки, процент конверсии в инвестицию, средняя стоимость held call. Ранжирование клиентов по показателям — быстро видно кто растёт, а кому нужна помощь.

### 13.3 Сравнение источников креатива
Кто производит лучший результат — внутренняя команда, агентство или UGC-автор? Для каждого источника рассчитывается cost per held call с Байесовским доверительным интервалом и вероятность превосходства над другими источниками.

### 13.4 Нишевые бенчмарки
Как клиент выглядит на фоне похожих бизнесов в той же нише? Сравнение show rate, конверсии формы, дистанции до записи — анонимизированные агрегаты (минимум 5 клиентов в нише).
